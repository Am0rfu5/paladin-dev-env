<objective>
Close the producer half and the renderer half of GAP-03: make Formation populate the aggregation
fields its result type has always declared, and make all three Heralds render what a Battalion
result actually contains.

Purpose: GAP-03 is the one Phase-2 requirement whose "satisfied" ledger verdict does not survive
direct code reading, and it is this phase's largest real code change. Three findings, each read
from the tree rather than inferred: `TableHerald::format_battalion_result` ignores its result
argument entirely and renders two hardcoded placeholder rows regardless of what ran; the JSON
Herald's battalion conversion omits the strategy, the aggregate token total, the per-Paladin
tokens and the node errors; and underneath both, `FormationExecutionService` never populates
`per_paladin_times`, `per_paladin_tokens` or `total_tokens` at all — it calls the plain
constructor, which defaults them to empty and zero. `PhalanxExecutionService` already implements
exactly the aggregation Formation needs, so this is porting a shipped pattern to a second call
site, not new design.

Output: a Formation result with real aggregation, and three Heralds that read it. The end-to-end
proof that ties them together is plan 02-05.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Paladin output → Herald rendering | Paladin names and LLM-produced output text cross into rendered JSON, Markdown and terminal-table output that an operator reads |
| execution service → `BattalionResult` | Aggregated per-node timing, token and failure data crosses from the execution service into a serializable result type that is exported to telemetry files |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-13 | Spoofing | A Herald rendering invented data indistinguishable from measured data | high | mitigate | Replace the stub with a renderer that reads its argument, and pin it with a test asserting two different results render differently. An operator reading a rendered Battalion report must not be shown fabricated Paladin names, durations or token counts |
| T-02-14 | Tampering | Herald output built by string concatenation from LLM-produced text and Paladin names | medium | mitigate | JSON output is produced through `serde_json` value construction, never string concatenation, so embedded quotes and control characters are escaped by the serializer. Markdown and table output are operator-facing terminal/document text, not executable; no interpolation into a shell, SQL or HTML context occurs in this phase |
| T-02-15 | Information Disclosure | Node error text carrying provider error bodies into rendered output and telemetry files | medium | accept | Accepted for this phase: the error text is already what `AggregatedError` records and what `export_metadata` writes today; surfacing it in the Herald changes the display surface, not the data collected. Whether provider error bodies should be redacted before persistence is a separate concern with no requirement in this phase |
| T-02-16 | Denial of Service | A panic while rendering an empty or malformed result | medium | mitigate | The empty-`paladin_results` case is an explicit test; the renderer iterates rather than indexing, and keeps the existing `Result` return with `HeraldError` mapping. No `unwrap()`, `expect()` or `panic!` in the rendering path |
| T-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package-manager install and no new dependency; `comfy-table`, `serde_json`, `chrono` and `uuid` are already workspace dependencies exercised by passing tests |
</threat_model>
