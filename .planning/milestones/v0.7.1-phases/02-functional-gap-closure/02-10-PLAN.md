<objective>
Close verification gap 1: `TableHerald::truncate_text` truncates by byte index and panics on
multi-byte UTF-8 input longer than the column budget. Fix it to a char-boundary-safe, total
function, and prove it with tests that actually reach the truncation branch.

Purpose: this is the one BLOCKER standing between Phase 2 and a fully-verified ROADMAP success
criterion 3 / GAP-03. It is not a new feature — `truncate_text` has been defective since commit
`3d2dedb7` (2026-01-26) — but plan 02-04 wired the first call site that applies it to real,
execution-service-sourced Paladin names (`table_herald.rs:203`), and 02-04's own `must_haves`
committed to "renders a Paladin name containing multi-byte UTF-8 without panicking". The test it
added uses a 21-byte name that never reaches the truncation branch, so the defect shipped behind a
green suite. Independently corroborated by `02-REVIEW.md` CR-02 (Critical).

Two further reachable panic paths were found while planning this fix and are in scope, because
leaving them would close the reported gap while leaving the same defect class live:

1. `format_error` (`table_herald.rs:284`) passes `PaladinError`'s display string — which carries
   provider error bodies and other domain-controlled text — through the same helper. Its
   `-> String` signature is infallible *by ADR-0005's deliberate design*, so a panic there
   destroys the graceful-degradation property that infallibility exists to provide.
2. `max_column_width` values of 1 and 2 underflow the `usize` subtraction into an enormous index
   and panic on the out-of-bounds slice. `HeraldConfig::validate` (`src/config/herald.rs:103`)
   only rejects `0`, so both values are *accepted operator configuration*.

Output: a `truncate_text` that cannot panic for any input at any configured width, a stated unit
for the column budget, and four tests whose inputs are arithmetically guaranteed to reach the
branch they claim to prove.
</objective>
