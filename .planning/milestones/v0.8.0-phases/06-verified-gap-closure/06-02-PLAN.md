<objective>
Close WARN-01 under CLOSE-02: make Herald reachable from Campaign, Chain of Command and the
Commander router, and prove the composite Chain-of-Command flow with an executable witness.

Purpose: `formation_service.rs` and `phalanx_service.rs` carry 19 Herald references each; the other
three battalion services carry zero. `format_battalion_result` is pattern-agnostic so no
requirement's text is falsified, but the composite Chain-of-Command developer flow does not compose
without the caller invoking a Herald directly. The ROADMAP sanctions either adopting or declining
this; `06-CONTEXT.md` D-14 adopts it for all three services, and D-15 requires one end-to-end
composite test rather than a compile check.

Output: the field + setter + format-wrapper triad replicated into three services, a single
`DelegationResult` -> `BattalionResult` conversion shared with the Commander, and an integration
test that drives a real execution and formats its result through a real Herald.

**Executor note:** `.planning/config.json` sets `workflow.worktree_skip_hooks: true`. Do not
disable it — without it every commit cold-compiles the whole workspace inside the worktree.

**Spec-less probe fallback.** Stage-1 recall produced ten must-NOT candidates for the WARN-01 slice
(Herald wiring must not change execution semantics; must not reorder Paladin execution; must not
duplicate the `DelegationResult` conversion; must not swallow a Herald error; …). **Every one was
dropped at Stage-2 precision as routine engineering** — they are ordinary correctness concerns owned
by the edge probe and code review, not values/safety/ethics constraints. Per the probe protocol an
empty kept-list is the correct precision outcome, not a failure, so `must_haves.prohibitions` is an
explicit empty list here rather than a silent omission. The four routine concerns are carried as
`must_haves.truths` instead. This plan carries none of the eight edge-probe rows (they land in
06-01, 06-03, 06-05 and 06-07).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Battalion execution result -> Herald -> operator output surface | `BattalionResult` carries Paladin outputs, per-Paladin timings, token counts and node error text; a Herald renders that into a string an operator reads, logs, or ships downstream |
| caller -> `with_herald` | the Herald implementation is caller-supplied through a trait object and runs inside the service's formatting path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-02-01 | Information Disclosure | `format_result` in all three services | medium | mitigate | `format_result` returns `Ok(None)` when no Herald is configured, so formatting is opt-in and no service begins emitting Paladin output text or node error detail as a side effect of this plan. The three concrete Heralds are unchanged, so their existing redaction behaviour is preserved. |
| T-06-02-02 | Tampering | `ChainOfCommandExecutionService::to_battalion_result` vs `commander.rs`'s former inline literal | high | mitigate | Two divergent conversions would let the Commander and the service report different results for the same execution. The plan collapses them to one implementation and pins it with `test_commander_chain_of_command_uses_shared_conversion`, which asserts the Commander's post-refactor result matches the shared conversion field-for-field. |
| T-06-02-03 | Repudiation | Herald formatting-failure arm | low | mitigate | Each service maps a Herald failure to its own `BattalionError` variant with a message naming the Herald, so a formatting failure is attributable to the service that produced it rather than surfacing as a generic Formation error. |
| T-06-02-04 | Denial of Service | caller-supplied `Arc<dyn Herald>` | low | accept | A pathological Herald implementation could block inside `format_battalion_result`. This is the same exposure `formation_service.rs` and `phalanx_service.rs` already ship; the plan introduces no new trust in caller code beyond the established pattern. |
| T-06-02-SC | Tampering | npm/pip/cargo installs | low | accept | This plan adds no dependency and modifies no `Cargo.toml`; no package-manager install task exists, so the package-legitimacy gate does not apply. |
</threat_model>
