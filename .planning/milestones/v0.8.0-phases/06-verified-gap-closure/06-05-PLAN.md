<objective>
Close CLOSE-03: apply the code consequences of Phase 5's two ADRs. Both halves are documentation
only.

Purpose: ADR-0011 recorded that both vision surfaces ship deliberately and handed one open wiring
question forward — wire `EncryptionService::encrypt_image_data` into the vision path, or record the
service as a deliberately unimposed consumer-facing utility. D-16 resolves it as the latter, on a
ground stronger than ADR-0011 had: the shipped vision path never stores image bytes, so Epic 13
FR-11's premise ("encryption at rest for *temporarily stored* image data") has no storage in the
shipped design to protect. ADR-0012 recorded that the `require_api_key` panic stands and named the
one real defect: a doc comment whose opening line says the function skips while both matched arms
panic.

Output: entry-point rustdoc on both vision traits (D-18), unimposed-utility rustdoc on
`EncryptionService` (D-16), an amended ADR-0011 (D-17), and the corrected live-API doc comment plus
a documented double gate (D-19). No behaviour changes anywhere.

06-02 registers a new module there, this plan edits the module header.

disable it — without it every commit cold-compiles the whole workspace inside the worktree.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| documentation -> a downstream reader sizing security work | rustdoc and ADR text are the only signal a later reader has about whether vision image bytes are protected; a misleading sentence causes real work to be skipped |
| environment variables -> live-API test harness | `require_api_key` reads provider API keys from the process environment |
| caller-supplied image bytes -> vision adapter -> external provider | `execute_with_vision` passes caller-owned `VisionContent` straight through with no framework-side persistence |
