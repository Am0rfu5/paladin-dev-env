the concurrent-registration case the register names, then measure the module and prove it at or above
the bar.

**≥ 80% is a phase acceptance criterion, not a standing CI gate** (D-12, consistent with D-05). The
single workspace floor stays the only thing that fails a build — ADR-0006's own words are that module
targets are "never a replacement for it". This number is verified once, here, by a module-targeted
`cargo llvm-cov` run, and it does not become a gate that lives on in CI.

are not comparable anyway — ADR-0006 already warns that two coverage commands agree only when the
ignore regex, the doctest decision and the feature set all match. Record which scope produced the
module figure so nobody later reads it against the gate number as if they were the same measurement.

    Extend the same `#[cfg(test)] mod tests` block. Touch nothing above the `#[cfg(test)]` marker.

    **Authentication.** A login with the correct password succeeds and issues a token when an auth
    port is configured; a login with an incorrect password does not succeed and issues no token; a
    login for a username or email that was never registered returns the not-found-shaped variant; a
    login against a deactivated account is rejected with its own distinct variant, asserted separately
    from the wrong-password case so the two are shown to be distinguishable. If the module tracks
    login attempts, assert the counter moves on a failed attempt and what happens at its threshold;
    if it does not, record that as a path the register names but the module does not implement, in
    the justification block of Task 2.

    Every credential assertion goes through the service's own `verify_password` or `login_user`.
    Never compare a stored hash to an expected string, and never reconstruct the hash in the test —
    the constant-time comparison lives inside `argon2::PasswordVerifier` and a test that bypasses it
    is asserting against a different mechanism than the one that ships.

    **Profile lifecycle.** `update_user_profile` on an existing user changes the stored profile and
    on an unknown user returns the not-found variant. An email change: assert what the module actually
    does with verification state on change — whether it resets, preserves, or ignores it — rather than
    asserting what it arguably ought to do. `activate_user`, `deactivate_user` and `verify_user` each
    on an existing user and on an unknown id, with the resulting state read back through a query
    rather than inferred from the call's return value.

    **Queries.** `get_user_by_id` and `get_user_by_email` for a hit and for a miss, asserting `None`
    on the miss rather than an error. `count_users` on an empty repository and after N registrations.
    `find_by_active_status` and `find_by_verification_status` each in both polarities, asserting
    membership rather than only length. `list_users` after registering several users: assert the full
    set is returned, and assert whatever ordering guarantee the implementation actually provides. If
    the implementation provides no ordering guarantee, do **not** write an order-dependent assertion
    that will flake — assert set membership and record the absent ordering guarantee in Task 2's
    justification block.

    Every test asserts on behaviour, not on the absence of a panic. Reuse the existing behavioural
    snake-case naming convention.
  </action>
