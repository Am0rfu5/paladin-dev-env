<objective>
Close DEFER-03 with the half the requirement calls the genuinely valuable part: concurrency and
stress. The register's own risk note is that "event-driven systems are notoriously hard to debug;
concurrency bugs can be subtle and intermittent" — which is exactly why these cases need tests that
fail loudly rather than hang, and assertions that are exact rather than approximate.

Every concurrent test is wrapped in an explicit `tokio::time::timeout`. `ListenerOrchestrator` holds
its state behind a tokio `Mutex` and an `RwLock`; a lock-ordering problem between them manifests as a
test that never returns, and an untimed test in that state blocks a CI runner until the workflow-level
timeout kills the whole job with no useful signal. A timed test names the deadlock.

Then measure and close: `listener.rs` at or above **80% line coverage** as a **phase acceptance
criterion, not a standing CI gate** (D-12, consistent with D-05). The single workspace floor remains
the only thing that fails a build. DEFER-03's text names no figure of its own, so it inherits
DEFER-02's bar, because ROADMAP criterion 6 needs a number to be falsifiable.

Purpose: the register's Module 2 closes with a re-derived figure and a real concurrency suite.
Output: the stress suite, the exit measurement, and the justification record.

    Every test in this task runs under `#[tokio::test(flavor = "multi_thread")]` — a single-threaded

    Write the four scenarios DEFER-03 names.

    **Concurrent emission from multiple producers.** Several tasks call `process_event` simultaneously
    against one shared `Arc<ListenerOrchestrator>` with several listeners registered. Assert the total
    trigger count is the exact expected product of producers, events and matching listeners — an exact
    equality, not a lower bound. A lower-bound assertion silently tolerates a lost update, which is
    the precise bug class this test exists to catch.

    **Concurrent registration and unregistration during active processing.** One task drives events
    continuously while another registers and unregisters listeners. Assert the orchestrator remains
    consistent afterwards — `list_listeners` and `get_all_stats` agree on the surviving set, no
    listener appears in one and not the other, and no call returned a poisoned-state error. This is
    the case most likely to expose a lock-ordering problem between the listener map and the trigger
    queue, so read the acquisition order in both methods before writing it.

    **A 1000-plus event burst.** Use the shared event factory's bulk constructor to build the burst in
    one call, drive it through several concurrent producers, and assert the aggregate statistics
    counters equal the **exact** arithmetic total. This is the contract: under `Mutex` and `RwLock`
    contention a lost increment shows up as a count that is low by a small amount, which an
    approximate assertion would never notice. Assert `trigger_queue_length` and the per-listener
    `ListenerStats` counters both, so a discrepancy between the two surfaces rather than cancelling.

    **Graceful shutdown during active processing.** Drop or shut down the orchestrator while events
    are in flight, in whatever way the type actually supports — read the struct and its `Drop`
    behaviour first rather than presuming a `shutdown()` method exists. Assert that in-flight
    processing terminates without panicking and without leaving a lock held. If the type provides no
    shutdown affordance at all, assert what dropping it during active processing actually does and
    record the absent affordance in Task 2's justification block; do not add a shutdown method to
    production code inside a coverage plan.

    Where a scenario needs a time window, use `tokio::time::pause()` and `advance()` rather than a
    wall-clock wait. Note that paused time and `flavor = "multi_thread"` interact — verify each test
    behaves deterministically by running the suite repeatedly (at least twenty consecutive runs) and
    confirming a stable result before considering the task done. An intermittently-passing concurrency
    test is worse than none: it trains everyone to re-run the build.
  </action>
