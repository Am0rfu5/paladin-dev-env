## Decisions Made

- **`crate-isolation`'s ten-crate matrix left with no explicit cache key**, even though independent verification against `Swatinem/rust-cache`'s own README (`## Cache Details`: the key is `job_id` + `rustc release/host/hash` + `Cargo.lock`/`Cargo.toml` hash — no automatic per-matrix-value differentiation) shows its automatic key does **not** distinguish the ten legs, since all ten share one `dtolnay/rust-toolchain@stable` install. The plan's own Task 1 acceptance criteria explicitly assert `No Swatinem/rust-cache@v2 step in ci.yml sets a key or a path input` as a machine-checked gate covering every job in the file, with no per-job carve-out for `crate-isolation`. Followed the plan's literal, machine-verified acceptance criteria rather than deviating from them. The residual risk this leaves is cache-entry contention across the ten legs — whichever leg's `Swatinem/rust-cache@v2` save step finishes first "wins" the shared cache entry for that `Cargo.lock` generation, and the other nine either fail to overwrite it (GitHub Actions caches are immutable per key) or restore a `target/` built for a different crate. This is a *Denial-of-Service*-class inefficiency (extra rebuild time), not a correctness hazard: cargo's own fingerprint-based incremental-build system detects whatever differs from a mismatched `target/` and recompiles it, matching this phase's own `T-15.1-12` disposition (`low, accept`) rather than `T-15.1-11`'s "cache poisoning" framing, which the plan scoped to the toolchain-differentiated `test:` job's `stable`/`beta` legs specifically (where the automatic key correctly differentiates, since `rustc --version` output genuinely differs).
- **`feature-flags.yml`'s `feature-matrix` job DOES get an explicit `key: ${{ matrix.name }}`**, the one case the plan's Task 2 action text explicitly authorizes ("a feature-set string that changes what gets compiled without changing the lockfile or the toolchain"). Verified this doesn't conflict with Task 2's own acceptance criteria, which impose no file-wide "no key" restriction (only zero `actions/cache@v4`, zero `restore-keys`, and scope confinement to the two declared files) — the "no key" gate is Task 1's, scoped to `ci.yml` only.
- **`integration-tests.yml`'s three cache blocks were not touched**, exactly as the plan's own "Recorded discretion resolutions" section instructs (that file is deleted whole by plan 15.1-05).
