<objective>
Consolidate the standalone integration workflow into the main pipeline and delete it, per **D-09**.

**This is a prerequisite, not a cleanup.** Two workflows currently render the display names
`Integration Tests` and `Kubernetes Smoke Test` each, and GitHub matches required status checks by
context *name*. Requiring either name while two different jobs produce it is ambiguous: GitHub
accepts a passing report from whichever job reported last, so the gate quietly settles for the
weaker of the two. It is the same defect class as the two identically-named audit jobs a previous
milestone shipped and a later phase closed. **D-05**'s required-check set cannot be applied safely
until this is resolved, which is why this plan sits before the ruleset application.

And the two same-named jobs are **not** duplicates. The main pipeline's job runs two narrow
ignored-by-default targets; the standalone workflow runs the whole workspace suite under the
integration feature — which therefore never runs on a feature-branch push today. Consolidation gets
the broad suite running on every branch push under **D-03**, which is the early-signal goal in its own
right.

This plan also closes the second half of the ambiguity that plan `15.1-02` measured empirically: any
job whose display name is shared across its own matrix legs is disambiguated here, at source, by
parameterising the name — the pattern the crate matrix already uses.

Purpose: make every status-check context name select exactly one job, so SC2's gate means what it
says; and get the broad suite onto every branch, serving SC1 and SC6.
Output: three absorbed jobs, one deleted workflow file, unique names throughout.

**Executor note:** `workflow.worktree_skip_hooks: true` — bypass the hook when committing. This plan
changes no Rust; do not run `cargo build`, `cargo test` or `cargo clippy`. Locate every job and step
by its id or `name:` anchor, never by a line number from a planning document — this file's offsets
have already drifted from all three of them.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Workflow job names → merge gate | A job's display name is the only identifier GitHub matches a required status check against |
| CI runner → service containers | Redis and MinIO run with fixed credentials on the runner-local network for the consolidated suite |
| Deleted workflow → running pipeline | Removing a file that currently reports two required-shaped context names changes what a commit's check set looks like |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15.1-20 | Spoofing | Two jobs rendering one status-check context name | high | mitigate | The whole point of this plan. Consolidation removes the cross-workflow collision structurally rather than by policy, and Task 2 removes the within-matrix collision by parameterising the display name. An automated verify asserts global uniqueness across the directory, so a future job cannot reintroduce it silently. |
| T-15.1-21 | Elevation of Privilege | A transitional commit in which both files report the same name | high | mitigate | Absorption and deletion land in one commit, asserted by an acceptance criterion reading the commit's name-status. During any window where both exist, a required check could be satisfied by the narrower job's report — which is why the window is not permitted to exist. |
| T-15.1-22 | Tampering | Changing the service port mapping the already-required coverage job depends on | high | mitigate | The consolidated job standardises onto the mapping the coverage job already uses, and a verify asserts the two jobs' services port maps are equal after the edit. Adopting the deleted file's default-port convention instead would break a job that is already gating merges. |
| T-15.1-23 | Repudiation | Retiring the nightly cron without recording it | medium | mitigate | Retirement is a decision with a stated reason and a revisit condition — floating service-image tag drift — recorded in the summary and given a row in the trigger-policy register plan `15.1-09` writes. An unrecorded trigger removal is exactly the SC1 failure class. |
| T-15.1-24 | Denial of Service | The broad workspace suite now running on every push to every branch | low | accept | Deliberate, and the early-signal outcome D-09 wants. The file-scope concurrency group with cancellation, which the deleted file lacked entirely, bounds pile-up better than the previous arrangement did. |
| T-15.1-25 | Tampering | Smuggling a substantive change into a cluster job under cover of consolidation | medium | mitigate | The action requires keeping the existing cluster job and recording any substantive divergence rather than merging the two. Resolving that divergence is out of scope and must not ride along inside a rename. |
</threat_model>
