### Task 1 — consolidation shape, port scheme, cluster-job divergence, cron retirement

**Port/env-var conversion (T-15.1-22 mitigation).** `integration-tests.yml`'s broad suite read `REDIS_URL=redis://localhost:6379` and `MINIO_ENDPOINT=localhost:9000` (the file's own default-port services block). `ci.yml`'s `integration-tests` job already runs Redis/MinIO on remapped ports `6380`/`9010`/`9011` (matching the already-required `coverage` job — a port change there would break a job already gating merges). The absorbed broad-suite step therefore uses this job's existing `TEST_REDIS_HOST`/`TEST_REDIS_PORT`/`TEST_MINIO_ENDPOINT`/`TEST_MINIO_ACCESS_KEY`/`TEST_MINIO_SECRET_KEY` env-var names and values (`localhost`/`6380`/`localhost:9010`/`testuser`/`testpass123`) instead of adding a second services block or a second port mapping. Verified via inline script that `integration-tests` and `coverage`'s `services.*.ports` are byte-identical dicts post-edit.

Note for a future reader: the crate's own test harness (`tests/integration/mod.rs::TestEnvironment::external_services()`) defaults `TEST_REDIS_PORT`/`TEST_MINIO_ENDPOINT` to `6380`/`localhost:9010` even when unset, and also auto-detects `GITHUB_ACTIONS`/port-6380-reachable as a signal to use external services. The explicit env vars in the new step are not strictly load-bearing for that one module, but they are load-bearing for `tests/integration/cli_real_services_test.rs` (reads `REDIS_URL`/`MINIO_ENDPOINT` directly, defaulting to `redis://localhost:6380`/`http://localhost:9010` if unset — also already this job's ports) and are the explicit, self-documenting choice rather than relying on implicit per-file defaults across a suite with mixed env-var conventions.

**Docker-integration job — no cache pattern to convert.** The plan's read_first/action text warned to give the absorbed container-integration job "the same cache mechanism the rest of the file now uses... not the hand-rolled pattern it carries in the file being deleted." Read closely: `integration-tests.yml`'s `docker-integration` job carries **no** `actions/cache@v4` step at all in either file — its build happens entirely inside `docker compose -f docker/docker-compose.test.yml build integration-tests`, with no local `cargo build`/`cargo test` step for this job to cache. There was nothing to convert. Documented here rather than silently doing nothing without explanation, since the plan's prose implied a conversion this job's actual content doesn't require. Bumped `actions/checkout` from `@v4` to `@v5` for consistency with every other job in `ci.yml` (all 20 other checkout steps use `@v5`); left `docker/setup-buildx-action@v3` and all `docker compose` invocations byte-identical to the source job — this job is already flagged in `ci.yml` as untested in this environment (docker absent from the authoring environment, per the existing `docker`/`kubernetes-smoke` job comments), so no other action-version bumps were made beyond the one needed to match the rest of the file's checkout convention.

**Cluster-job divergence (T-15.1-25 mitigation) — kept, not merged.** `integration-tests.yml`'s `kubernetes-smoke-test` and `ci.yml`'s `kubernetes-smoke` are not name-only duplicates; they differ substantively in failure handling:

| Behavior | `integration-tests.yml` (deleted) | `ci.yml`'s `kubernetes-smoke` (kept) |
|---|---|---|
| Pod-not-ready | `kubectl wait ... --timeout=180s \|\| true` (soft — a timeout passes silently) | `kubectl wait ... --timeout=180s` (hard fail on timeout) |
| Unreadable start/ready timestamps | Startup-time check is skipped entirely if timestamps are empty (measures nothing, reports nothing) | Empty timestamps are a hard `::error::` + `exit 1` |
| `needs:` | none | `needs: [docker]` |

`ci.yml`'s version is already an explicitly-labeled improvement over the source job (its own comments say so: "Improvement over the copied source job... a pod that never becomes ready must fail this smoke test"). Per the plan's instruction, resolving this divergence is out of this plan's scope; `ci.yml`'s version was kept unmodified and the standalone file's copy was not imported. No dangling reference: `protect-main-branch.json` does not pin `Kubernetes Smoke Test` (D-05 excludes it by name regardless of duplication), so this decision has no ruleset consequence.

**Cron retirement (T-15.1-23 mitigation).** `integration-tests.yml`'s `schedule: - cron: '0 2 * * *'` trigger was retired, not relocated into `ci.yml`. Reasoning: under D-03 (this phase's earlier `push: branches: ['**']` change) plus this consolidation, the broad `--features integration-tests` suite now runs on every push to every branch and on every pull request — strictly more coverage than a once-daily run for any repository receiving regular pushes. Adding a `schedule:` key to `ci.yml` itself was explicitly avoided: only a handful of `ci.yml`'s jobs carry conditional gates (`if: github.event_name == 'schedule' ...`), so a bare cron there would trigger the entire pipeline, including the hour-long emulated `docker` multi-arch build. Verified via inline script that `ci.yml`'s top-level `on:` block contains no `schedule` key. **Revisit condition, recorded for plan `15.1-09`'s trigger-policy table:** the retired nightly bought one thing pushes do not — drift detection on floating service-container image tags (`redis:7-alpine`, `minio/minio:latest`) between pushes. If that becomes a live concern, a scheduled workflow targeting only those two floating tags (not the whole test suite) would be the narrower reinstatement, not resurrecting the deleted file.

**Concurrency inheritance — strict improvement.** The absorbed jobs now sit under `ci.yml`'s file-scope `concurrency: group: ci-${{ github.head_ref || github.ref }}` with `cancel-in-progress`, which `integration-tests.yml` had no equivalent of. A superseded run of the broad suite on a fast-following push is now cancelled rather than left running to completion, which the deleted file could not do.

**No `needs:` edges rewritten.** Confirmed: nothing in the tree depended on the moved jobs via `needs:`, and the pre-existing `docker` job's `needs: [lint, test]` and `kubernetes-smoke`'s `needs: [docker]` are unrelated and untouched.

### Task 2 — no rename; the plan's own duplicate-detection premise was empirically false for this job

The task's `<read_first>` names `15.1-CI-EVIDENCE.md`'s duplicate-name query as the deciding input: "If the query returned an empty array, this task is a verification only and no name is edited." Two independent evidence sources both return that empty result for `Unit Tests`:

- **`15.1-CI-EVIDENCE.md` §3** (push-event capture, commit `9f32881`): `gh api .../check-runs --jq '[.check_runs[].name] | group_by(.) | map(select(length>1))'` → `[]`. The 45-name inventory reports `Unit Tests (beta)` and `Unit Tests (stable)` as two already-distinct names, not the bare string `Unit Tests`.
- **This execution's `<live_evidence_from_earlier_waves>`** (pull_request-event capture, PR #29, five workflows, 51 contexts / 50 unique): the *only* duplicate is `Integration Tests` (x2) — resolved by Task 1. No `Unit Tests` collision.

Both sources measure the live, GitHub-rendered check-run name — which is the runtime behavior that actually governs required-status-check matching, not the literal YAML `name:` string. `ci.yml`'s `test` job's `name:` field is the fixed string `Unit Tests` with no `${{ matrix.* }}` interpolation, yet GitHub still renders two distinct check-run contexts for its two-leg `rust-version: [stable, beta]` matrix. This confirms: **GitHub auto-suffixes matrix leg values onto a job's check-run name whenever the job's own `name:` doesn't already interpolate the matrix**, independent of whether the workflow author wrote `${{ matrix.* }}` anywhere. Per the plan's explicit override clause — "Act on the recorded evidence, not on this expectation... if the observation says otherwise, the observation wins" — no rename was made. `feature-flags.yml`'s 14-leg matrix (`Build & Test (${{ matrix.name }})`) already explicitly interpolates and was unaffected either way.

**A note on the task's own embedded automated-verify scripts, for a future reader who runs them literally.** Both of Task 2's `<verify><automated>` scripts, run as written against the current (unmodified) repository state, fail:
- Script 1 (`legs>1 and '${{' not in n` → raise) flags `ci.yml`'s `test` job because its literal `name:` string has no matrix interpolation — a static-YAML check that cannot see GitHub's runtime auto-suffixing behavior described above.
- Script 2 (pinned-context-resolves-to-a-declared-job-name) flags `Unit Tests (beta)`/`Unit Tests (stable)` — the two contexts `15.1-04` already correctly pinned — as "match[ing] no job name," for the same reason: it builds its matching regex from the literal `name:` field, which for this job is just `Unit Tests`.

This is the same class of deviation `15.1-04`'s summary documented (a plan-embedded verify script tested against a source/assumption its own governing evidence record contradicts). Per Rule 1, this is **not** treated as a defect to fix by renaming `ci.yml`'s `test` job to force the scripts to pass — the payload (the already-pinned `Unit Tests (beta)`/`Unit Tests (stable)` contexts, and the unchanged `test` job) is correct as-is; the scripts' premise is what's stale. Documented here rather than silently declaring Task 2 "verified" without explaining why its own embedded checks don't pass literally.
