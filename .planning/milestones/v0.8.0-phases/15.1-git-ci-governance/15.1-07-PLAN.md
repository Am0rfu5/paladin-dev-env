<objective>
Step 2 of **D-02**'s strictly ordered cutover: fast-forward the trunk and retire the branches the old
model needed.

**D-01** settles the branching model. The trunk receives every merge through a pull request; short
branches are short; releases are tags cut from the trunk; a release branch exists only to backport
into an already-published line, never as a staging area. The stale midpoint branch is retired. The
versioned integration branch is retired once its content is on the trunk. The alternative was
rejected on evidence rather than taste: an integration branch makes the CI-exclusive suites — the
container, cluster and service-backed integration jobs — run *later*, not earlier, which is the
opposite of the stated goal; and keeping a long-lived release branch as the integration point
contradicts the invariant the release tag-source guard and the release make-target already enforce.

**The reconciliation itself is free.** The trunk is a strict ancestor of the integration branch:
every commit is a fast-forward, zero conflicts, no merge commit, and the integration branch holds
nothing the trunk needs merged into it. The stale midpoint branch is likewise an ancestor. The
success criterion frames this as a hard problem; it is one command. What makes it consequential is
not difficulty but irreversibility.

Purpose: SC4 — the branching model is not only decided and documented but applied.
Output: origin's trunk ref moved; two refs retired; one repository setting changed. No tracked file
is modified.

**Ordering is a hard constraint here, twice over.** This step comes *after* plans `15.1-01` through
`15.1-06`, because protecting a trunk with a required check that fails on every dependency change
would lock the repository against itself. And it comes *before* plan `15.1-08` applies the rulesets,
because the release-branch ruleset covers the very ref class one of these retirements deletes —
applying protection first would put a one-time retirement under a deletion rule and require a bypass
actor to execute it.

**Executor note:** `workflow.worktree_skip_hooks: true` — bypass the hook for the summary commit. Run
no `cargo` command in this plan.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local executor → `origin` | A published default branch is moved and two refs are deleted, using the authenticated user's push access |
| Local executor → GitHub REST API | Ref deletion and a repository-settings change are issued against the live repository |
| Pre-protection window | Between this plan and the next, the trunk carries all shipped work and is still unprotected |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15.1-31 | Tampering | The fast-forward silently becoming a merge if histories diverged since verification | high | mitigate | The move uses the fast-forward-only flag, which hard-fails rather than fabricating a merge commit, and the checkpoint re-runs the ancestry checks against a fresh fetch immediately before approval. A silent merge here would put a commit on the trunk that no pipeline run ever evaluated. |
| T-15.1-32 | Repudiation | Deleting a ref whose commits are not actually reachable elsewhere | high | mitigate | Each deletion is preceded by a recorded ancestry check proving the tip is reachable from the trunk, and the tip SHA is written down before the call. The decision to skip an archival tag rests on that proof, so if the proof fails the deletion does not proceed. |
| T-15.1-33 | Elevation of Privilege | Performing the retirement after protection is applied, forcing use of a bypass actor | medium | mitigate | The ordering constraint is stated in the objective, in the action, and again in plan `15.1-08`'s sequence: retire first, protect second. Executing a routine one-time deletion through an administrative bypass would establish exactly the habit D-07 removes. |
| T-15.1-34 | Denial of Service | A window in which the trunk holds all shipped work and is unprotected | medium | accept | Unavoidable and bounded: it exists only between this plan and the next, and shrinking it to zero would require applying protection before the retirement, which creates the worse problem above. The repository has a single active committer, so the exposure is a self-inflicted-mistake window rather than an adversarial one. |
| T-15.1-35 | Tampering | Enabling automatic branch deletion on merge | low | accept | Deletes only the source branch of a merged pull request, whose commits are by definition then on the trunk. The thirty stale branches on origin are the standing evidence for the setting; nothing is lost that a merge did not already preserve. |
| T-15.1-36 | Information Disclosure | Command output transcribed into the summary | low | accept | The repository is public. Recorded fields are branch names, SHAs and API response bodies for ref and settings endpoints; no token or credential is transcribed. Record responses, never raw authentication output. |

## Recorded discretion resolutions (this plan)

- **Both retired branches are deleted, not left dormant.** Leaving them preserves the old specific
  nouns beside the new general one and forces every trigger list, ruleset and guard to keep naming
  them. A dormant release-pattern ref would additionally fall under the release-branch ruleset applied
  at the next step.
- **No archival tag before deletion.** Both tips are provably ancestors of the trunk after the move,
  so every commit stays reachable; a tag would add a permanent ref recovering nothing.
- **Automatic branch deletion on merge is enabled.** Follows directly from short-lived branches;
  thirty stale branches on origin are the evidence.
- **All three merge methods stay enabled.** Not required by the branching model, and narrowing them
  would flatten the per-task conventional-commit history this project deliberately produces.
