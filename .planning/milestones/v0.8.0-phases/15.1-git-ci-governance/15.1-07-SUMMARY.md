## Mechanism Deviation from the Plan's Literal Instruction

The plan's action (Task 2) specifies: check out the trunk, fetch, `git merge --ff-only` the integration branch, then push the trunk. **The orchestrator instead** asserted the fast-forward property locally with the five ancestry commands above (`--is-ancestor` exit `0` and a reverse count of exactly `0` — which is precisely what `--ff-only` tests) and then ran `git push origin HEAD:main`, which git itself rejects unless the update is a fast-forward.

**Reasoning for the deviation, as recorded by the orchestrator:** the working tree carried unrelated uncommitted modifications, and a branch switch risked entangling them with a one-way operation. The safety property the plan cares about — hard-fail rather than silently fabricate a merge commit — was enforced twice: once locally via the explicit ancestry assertions, and once server-side by git's own non-fast-forward rejection on `push origin HEAD:main`. No force-push and no merge commit was used at any point (confirmed above: `git rev-list --count origin/main..HEAD` post-move is `0`, meaning the push output `e38d21f..d87d11e main -> main` is the two-dot fast-forward form, not the three-dot forced form `+e38d21f...d87d11e`).

This is recorded per **D-00e** — no claim in this record implies the literal `--ff-only`-merge mechanism was used; the actual command was `git push origin HEAD:main`, transcribed verbatim above.

## Decisions Made

- **No archival tag before deleting** the retired branches. Both tips are provably ancestors of the trunk after the move, so every commit stays reachable; a tag would add a permanent ref recovering nothing.
- **Automatic branch deletion on merge enabled.** Follows directly from short-lived branches; ~30 stale branches on origin (see the `git ls-remote --heads origin` output above) are the standing evidence for the setting.
- **All three merge methods stay enabled.** Not required by the branching model, and narrowing them would flatten the per-task conventional-commit history this project deliberately produces.
- **Both retired branches deleted, not left dormant.** Leaving them preserves the old specific nouns beside the new general one and forces every trigger list, ruleset and guard to keep naming them. A dormant release-pattern ref would additionally fall under the release-branch ruleset applied at the next step (`15.1-08`).
