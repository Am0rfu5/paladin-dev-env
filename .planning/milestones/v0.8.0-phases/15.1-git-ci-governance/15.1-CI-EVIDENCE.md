## 4. Finding A — the duplicate-context-name collision does not reproduce on a push event

CONTEXT.md finding 6 and decision **D-09** describe a collision: `ci.yml`'s
`integration-tests`/`kubernetes-smoke` jobs and `integration-tests.yml`'s
`integration-tests`/`kubernetes-smoke-test` jobs both render the context names `Integration Tests`
and `Kubernetes Smoke Test`. The duplicate-name query in §3 above returned `[]`, and
`Kubernetes Smoke Test` is **absent** from the 45-name list entirely (not present once, let alone
twice).

**Cause, confirmed against `15.1-01-SUMMARY.md`'s own key-files list.** Plan `15.1-01` widened the
push trigger on exactly three workflows — `ci.yml`, `feature-flags.yml` and `pre-commit.yml`.
`integration-tests.yml` was not touched and remains `pull_request`-and-cron triggered, so it never
ran on this push at all. `ci.yml`'s own `integration-tests` job did run (shown `in_progress` in
§3, not waited out) and is the sole source of the single `Integration Tests` context observed
here. With only one of the two colliding workflows firing, there is only one job per name, so no
duplicate is possible on a push.

**CONTEXT.md finding 6 and D-09 are still correct in substance** — the collision is real and D-09
(consolidating `integration-tests.yml` into `ci.yml`) is still the right fix — **but the collision
is observable only on a `pull_request` event, not on a push.** This run cannot evidence it either
way for `pull_request`, because no PR was opened against it (see §5).

**Consequence for D-05 and plan `15.1-04`, stated plainly so it cannot be missed:** the 45-name
list in §3 is a **push-event** context list. GitHub branch protection gates on the `pull_request`
event, not push. Pinning required-check contexts directly from the push-event list above risks
two distinct failure modes: (a) **omitting** a `pull_request`-only context such as
`Kubernetes Smoke Test`, which would never be reported on a push and is therefore invisible to
this record entirely; and (b) **pinning** a context — such as the three observed `skipped` on this
push (§3's reconciliation note) — that may behave differently, or not fire at all, on a
`pull_request` event. **Plan `15.1-04` must independently obtain a `pull_request`-event context
list (e.g., from an actual open PR's check-runs, not a push) before pinning any ruleset, and must
not treat the list in this record as complete for that purpose.**

## Finding B — the fine-grained PAT's scopes are insufficient for repository-configuration writes; anticipated blocker for plan `15.1-08`

**D-06** (this phase's decision governing the ruleset-application step) already recorded a
warning: `gh auth status` reports `admin: true` for `Am0rfu5`, but that reflects the *user's role*
only — the fine-grained PAT the automation uses separately needs `Administration: write`, "which
only a write attempt proves".

A write attempt has now been made in an **adjacent** scope (repository pull-request creation, not
rulesets) and was refused. See §5's verbatim `gh pr create` failure. The same token is what plan
`15.1-08` would use to `POST /repos/DF3NDR/paladin-dev-env/rulesets` — **SC2's entire deliverable**
and the concrete action D-06 describes. A token lacking one repository-write scope
(`Pull requests: write`) is evidence the token's scope grant was not built for full
repository-configuration automation; it does not by itself prove `Administration: write` is also
missing, but it is the first concrete signal in this phase that the token's scope set is narrower
than D-06 assumed. **Recorded here as an anticipated blocker for plan `15.1-08`, discovered at
plan `15.1-02` rather than at wave 7.** Recommended disposition: before `15.1-08` runs, the token
needs `Administration: write` confirmed (a write attempt is the only proof, per D-06) and, for the
dogfooding loop this phase's D-02 step 3 depends on, `Pull requests: write`.
