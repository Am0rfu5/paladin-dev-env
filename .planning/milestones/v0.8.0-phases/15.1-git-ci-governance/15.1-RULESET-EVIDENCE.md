## 6. Verified asymmetry (D-08b)

**D-08b** requires that the tag ruleset keep its administrative bypass — because it restricts tag
*creation*, and removing that bypass would make cutting any release impossible — while the trunk
ruleset must carry no bypass at all, because it gates a merge and an always-bypassable merge gate
is not a gate. This asymmetry is verified here against the live server, not only against the
committed files.

**Command (trunk ruleset detail):**

```
gh api /repos/DF3NDR/paladin-dev-env/rulesets/20868126 --jq '{name, bypass:(.bypass_actors|length)}'
```

**Output, verbatim:**

```json
{"bypass":0,"name":"Protect main branch"}
```

**Command (tag ruleset detail):**

```
gh api /repos/DF3NDR/paladin-dev-env/rulesets/20868099 --jq '{name, bypass:(.bypass_actors|length)}'
```

**Output, verbatim:**

```json
{"bypass":1,"name":"Protect release tags"}
```

**Why each is correct:**

- **Trunk (`bypass:0`)** — the applied "Protect main branch" ruleset gates the only path into
  `main`: a pull request with all 44 required checks green. A merge gate that anyone (including an
  administrator) can bypass at will is not a gate, only a suggestion; zero bypass actors is the
  correct and verified state.
- **Tag (`bypass:1`)** — the applied "Protect release tags" ruleset gates *creation* of a
  `refs/tags/v*` ref, not a merge. The single collaborator (`Am0rfu5`, per `15.1-CI-EVIDENCE.md`
  §5's collaborator read) is the account that cuts releases. Without a bypass actor, tag creation
  itself would be restricted to nobody, and no release could ever be cut. The retained bypass is
  therefore the correct disposition, not an oversight — it is what makes the tag ruleset usable at
  all rather than a self-lock.

the repository owner to delete the rulesets through the web interface instead.
