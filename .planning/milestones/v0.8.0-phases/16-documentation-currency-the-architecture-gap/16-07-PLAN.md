**Then fix each warning by its class.** Four classes, four different mechanical fixes:

- **Unresolved intra-doc link (14 of 20).** The bracketed name is not an item in scope — most often a
  crate name (`paladin-core`, `paladin-ports`) or a function the module doc mentions in passing. Fix
  by de-linking: keep the name as a plain code span rather than a doc-link. Do not add a spurious
  `use` just to make a prose mention resolve.
- **Private-item link from public docs (3 of 20).** A public doc comment links an item that is not
  public (`build_agent`, `BearerToken::expose_secret`). Fix by naming it as a plain code span. Do
  **not** widen the item's visibility to satisfy a doc link — that changes the public API surface to
  appease a lint, and `.project/current-exports.txt` is a tracked baseline.
- **Redundant explicit link target (2 of 20).** The label already resolves without the explicit path
  (`agent_controller.rs:651`, `app.rs:69`). Fix by dropping the explicit target, keeping the label.
- **Unclosed HTML tag (1 of 20).** A bare generic type in prose is parsed as an HTML tag
  (`in_memory_registry.rs:65`). Fix by wrapping the type in a code span.

**Fix the documentation, never the gate.** Do not add a lint-suppression attribute, do not delete a
doc comment to make its link disappear, and do not convert a doc example to a non-compiling fence, to
turn a warning off. If a warning appears genuinely unfixable without a real API change, stop and
record it rather than suppressing it — that is a finding, not a blocker to route around.
