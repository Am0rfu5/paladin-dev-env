<objective>
Provision the demo-recorder toolchain — `vhs`, its `ttyd` and `ffmpeg` dependencies, and `asciinema` —
locally and in **both** devcontainer images, behind a blocking human check on the two packages no
automated legitimacy gate can reach.

Purpose: D-14 chose VHS because a `.tape`-driven recording is **regenerable** rather than a
hand-performed take that goes stale the moment the example's output changes — which matters in a
phase whose entire theme is documentation that stays current. The 2026-08-24 amendment to D-14 adds
`asciinema` as a named dependency, because VHS's `Output` command supports only `.gif`, `.mp4`,
`.webm` and PNG-frame directories; `.cast` is asciinema's native format and VHS has no case for it.
Both tools are driven from checked-in source, so pairing them does not weaken D-14's reasoning.
Output: a rebuild-persistent recorder toolchain, its provenance recorded, and the artifact size
budget decided before any binary exists.

**Why this plan is not autonomous.** 16-RESEARCH.md's Package Legitimacy Audit returns `OK` for the
three crates.io packages this phase installs, but `vhs` and `ttyd` are **outside the automated gate's
ecosystem coverage entirely** — `vhs` is a Go binary distributed via Homebrew, a third-party APT
repository with a `curl | gpg --dearmor` key-install step, or `go install`; `ttyd` is a GitHub release
binary with no package registry at all. The gate cannot evaluate either. A human verifying the signing
key fingerprint out-of-band is the only check available, and it must happen **before** the install
lands in an image that every developer on this project rebuilds. This checkpoint is not
auto-approvable.

**Scope guards:** D-14 — VHS is the recorder of record and `.tape` is the source of truth; asciinema
is paired for `.cast` only. D-11's pattern — both Dockerfiles, matching the pinned-install convention
already used for `cargo-release`, `cargo-deny` and `cargo-cyclonedx`. D-00o — commit with
`--no-verify`.

**Deviation recorded:** this plan holds two checkpoints *and* the implementation they gate, which
normally would be split. Splitting them here would put the gate in a different plan from the action it
authorises, which is exactly what the security requirement forbids — the checkpoint must block the
install, not merely precede it in a wave ordering.
</objective>

  <name>Checkpoint 1: Verify the vhs and ttyd supply chain out-of-band before either lands in a devcontainer image</name>

  <what-built>
Nothing yet — this checkpoint runs **before** any install lands in a Dockerfile.

Claude has gathered, for your review, the provenance of the two packages the automated
package-legitimacy gate cannot evaluate:

- **`vhs`** (charmbracelet) — the terminal recorder D-14 selected. Not on crates.io, npm or PyPI.
  Distributed via Homebrew, `go install`, or a third-party APT repository at `repo.charm.sh` whose

  Gum and Bubble Tea.
- **`ttyd`** (tsl0922) — VHS's terminal-server dependency; VHS's own README states it must be on
  `$PATH` before VHS will run. No package registry of any kind; the only documented install path is a
  binary download from GitHub releases.

Claude has recorded in `16-DOCS-04-TOOLCHAIN.md`: the exact APT repository URL and key URL it intends
to use, the key fingerprint it retrieved, the exact `ttyd` release tag and asset filename, and the
checksum the release page publishes for that asset (or a note that the page publishes none).

Two other tools are **not** part of this checkpoint: `ffmpeg` and `asciinema` come from the base
image's own Debian repository, the same trust boundary as every `apt-get install` line already in both
Dockerfiles.
  </what-built>
  <how-to-verify>

   about to trust** — their GitHub organisation or documentation site — and compare it character by
   character against the fingerprint Claude recorded in `16-DOCS-04-TOOLCHAIN.md`. A key fetched from
   the same host it authenticates proves nothing; this out-of-band comparison is the whole check.
2. Open `https://github.com/tsl0922/ttyd/releases` and confirm the release tag Claude recorded exists,
   is not a pre-release, and that the asset filename matches. If the release publishes a checksum,
   confirm it matches Claude's recorded value; if it publishes none, decide whether an unverifiable
   binary is acceptable in these images and say so explicitly.
3. Confirm you are willing to add a third-party APT repository to **both** devcontainer images — every
   developer on this project inherits it on their next rebuild, and it stays in the image's update
   path indefinitely.

out-of-band fingerprint comparison is not an approval — that comparison is the only part of this
supply chain nothing else can check.
  </how-to-verify>

<task type="checkpoint:decision" gate="blocking">
  <name>Checkpoint 2: Decide the recordings size budget before any binary is committed</name>

  <decision>
The size budget and retention rule for the committed demo recordings — decided **before** the first
binary is produced.
  </decision>
  <context>
D-14 and FR-26.4 fix the artifact shapes: a `.gif` for embedding and a `.cast`, both under
`docs/assets/recordings/`, both regenerable from checked-in source. That part is locked and is not
what this decision is about.

What is undecided (CONTEXT.md lists it under Claude's Discretion) is **how large those binaries may
be, and what happens when one exceeds the budget**. This is asked now because it is effectively
**one-way**: once a multi-megabyte GIF is committed, removing it from the repository requires a git
history rewrite, which is disruptive for every clone. Deciding after the recordings exist means
deciding under pressure to keep what was already made.

For scale: the four demos are 30-60s, 45-90s, 60-120s and 45-90s. A terminal GIF at a typical VHS
frame rate and width runs roughly 0.5-3 MB per minute depending on how much of the screen changes;
`.cast` files are small JSON and are not the concern.
  </context>
  <options>
    <option id="option-a">
      <name>Budget per file, re-record if exceeded (recommended)</name>
      <pros>Keeps the repository small; forces short, tight demos, which is what a README-linked demo should be anyway; no new infrastructure. A `.tape` is trivially re-recordable at a smaller width, frame rate or trimmed length, so exceeding the budget has a cheap fix.</pros>
      <cons>Someone has to re-record if the first take is too big; a long demo may have to lose content to fit.</cons>
    </option>
    <option id="option-b">
      <name>Commit whatever the recordings come out as, no budget</name>
      <pros>Simplest; no re-recording step; the demos show whatever they need to show.</pros>
      <cons>Unbounded and one-way — the repository carries the result forever. This is the option that cannot be walked back.</cons>
    </option>
    <option id="option-c">
      <name>Introduce git-lfs for `docs/assets/recordings/`</name>
      <pros>Keeps large binaries out of the main history.</pros>
      <cons>Adds repository infrastructure every contributor and every CI job must have configured; a clone without LFS gets pointer files instead of demos; this is a repository-wide change well outside a documentation-currency phase's scope.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a (and state the per-file MB budget), option-b, or option-c.</resume-signal>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| third-party APT repository → both devcontainer images | `repo.charm.sh` becomes an update source every developer on this project inherits on rebuild, indefinitely. |
| GitHub release binary → both devcontainer images | The `ttyd` binary is executed inside the development environment with the developer's privileges. |
| Debian repository → both images | `ffmpeg` and `asciinema` share the trust boundary the images already have. |
| git history → every clone, forever | A committed binary is not removable without a history rewrite — hence the decision checkpoint before any binary exists. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-16-02 | Tampering, Spoofing | Charm APT repository and its `curl \| gpg --dearmor` key install | high | mitigate | A blocking, non-auto-approvable human checkpoint verifies the key fingerprint **out-of-band** before the repository is added, since a key fetched from the host it authenticates proves nothing. The key is installed to a dedicated keyring referenced by `signed-by=`, so it can authenticate only that repository and cannot sign a package claiming to be a Debian core package. `apt-key add` is asserted absent. |
| T-16-33 | Tampering | `ttyd` GitHub release binary | high | mitigate | Pinned to an explicit release tag the human confirmed exists and is not a pre-release; the published checksum is verified before install, or the absence of a checksum is recorded in the Dockerfile comment so the residual risk is visible rather than implied away. |
| T-16-01 | Tampering | unpinned installs drifting to a malicious release | high | mitigate | `vhs` is pinned to an explicit APT version and `ttyd` to an explicit tag; neither resolves to a floating "latest". `ffmpeg`/`asciinema` inherit the base image tag's pin, and that deviation is recorded with its reason rather than left unstated. |
| T-16-34 | Elevation of Privilege | a compromised recorder binary running in the dev environment | medium | accept | `vhs` and `ttyd` execute with developer privileges by design — they drive a terminal.
