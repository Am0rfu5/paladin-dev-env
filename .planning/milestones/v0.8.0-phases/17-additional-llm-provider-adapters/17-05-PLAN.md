<objective>
Ship the one build-list provider that is not OpenAI-compatible. Gemini's `generateContent` is its
own protocol — resource-oriented URL, `contents[]`/`parts[]` body, a top-level `systemInstruction`
sibling field, `x-goog-api-key` header auth, and `?alt=sse` streaming — so it is written as a
standalone module modelled structurally on `anthropic/adapter.rs`, **not** on `compat::engine`
(D-08).

**Purpose:** D-01 admits Gemini as "the one bespoke adapter worth paying for". Forcing it onto the
compatible core would mean translating a fundamentally different request shape through a
compatible-protocol engine, which is how a shared core stops being shared and starts being a
`match` on provider name.

**Output:** `crates/paladin-llm/src/gemini/`, a `gemini` Cargo feature, a registry row, and
mock-transport tests for the bespoke protocol.

**Scope guards:**
- **D-08** — Gemini is **text-only**. `supports_vision` is `false` because that is true of what
  ships; vision is a different surface (`openai/vision.rs`, `anthropic/vision.rs`, the `vision`
  feature, Sentinel) with no `LlmPort` method behind it, and a Gemini vision adapter is a recorded
  deferred idea, not scope here.
- **D-06** — `openai/`, `anthropic/`, `deepseek/` untouched. `anthropic/adapter.rs` is read as a
  structural template only.
- **D-07** — `LlmPort` unchanged; `get_provider_name()` returns `"gemini"`.
- **D-00o** — commit with `--no-verify`; crate-scoped builds only, never a workspace build.
- **D-00e** — vendor values recorded in the SUMMARY with the doc URL they were confirmed against.

## Decision resolved in this plan (RESEARCH.md Open Question 2)

**Gemini's `RESOURCE_EXHAUSTED` status — DECIDED: map conservatively to
`LlmError::RateLimitExceeded` (retryable), documented as an assumption.**

Gemini's error envelope carries an RPC-style `status` string alongside the HTTP code, unlike the
compatible four's plain status switch. `RESOURCE_EXHAUSTED` covers both a transient per-minute rate
limit and a hard billing-quota exhaustion, and 17-RESEARCH.md could not distinguish them without a
live key (Assumptions Log A4). Retrying a true quota exhaustion merely burns the bounded retry
budget; mapping a transient rate limit to the non-retryable `UsageLimitExceeded` would fail a
request that would have succeeded. The asymmetry decides it.

Record the assumption **in the adapter's own doc comment**, following the precedent
`anthropic/adapter.rs:26-33` already sets with its named, documented, narrowly-matched
`ANTHROPIC_USAGE_CAP_SIGNATURE` constant — a documented uncertainty at the point of use, not a
planning artifact nobody reads. Name the verification path: the `live-api-tests` feature with a real
`GEMINI_API_KEY`, which 17-CONTEXT.md D-15 leaves available and deliberately unused this phase.

Create the Gemini module (D-01, D-08, D-12). This adapter does **not** import anything from
`crate::compat` — it owns its own wire types, its own request builder, its own error mapping and its
own retry loop, exactly as `anthropic/adapter.rs` does for the `/messages` protocol. The only shared
code it consumes is the crate-level redaction trio.

**Module doc comment** — follow the Anthropic precedent of naming the provider's own divergences up
front: `systemInstruction` is a top-level sibling field rather than a `contents[]` entry; auth is the
`x-goog-api-key` header; the URL carries the operation as a `:generateContent` /
`:streamGenerateContent` suffix rather than a path segment; streaming requires `?alt=sse` to get SSE
framing instead of a raw JSON array.

**`GeminiConfig`** with `from_env()` / `new()` / `validate()`:
  - `api_key` — `GEMINI_API_KEY`, required (D-12).
  - `base_url` — `GEMINI_BASE_URL`, default `https://generativelanguage.googleapis.com/v1beta`.
  - `model` — `GEMINI_MODEL`, default `gemini-2.5-flash`.
  - `timeout_seconds` — `GEMINI_TIMEOUT_SECONDS`, default `60`.

**Auth** — build the `reqwest::Client` with a default header named by the constant
`GEMINI_API_KEY_HEADER` (`x-goog-api-key`). Google's docs also document an alternative form that
carries the credential as a URL query parameter named `key`; **do not use that form** — a credential
in a URL lands in proxy logs, server access logs and any diagnostic that echoes the request line,
which is precisely the class of leak this codebase's redaction pattern exists to prevent.

**Wire types** — the private structs listed in the artifacts table, with `serde` rename attributes
for Gemini's camelCase field names (`systemInstruction`, `generationConfig`, `maxOutputTokens`,
`topP`, `topK`, `stopSequences`, `candidateCount`, `finishReason`, `usageMetadata`,
`promptTokenCount`, `candidatesTokenCount`, `totalTokenCount`). Copy the struct sketch in
17-RESEARCH.md §Pattern 3 directly.

**Prompt translation** — map `PromptType::System` to the top-level `systemInstruction`, and
`User`/`Text` to `contents[]` entries with role `user`, `Assistant` to role `model`. Gemini has no
`system` role inside `contents[]`; sending one is a request the API rejects. Decide and document
what happens to a `PromptType::Function` item — Gemini's function surface is out of scope, so the
correct behaviour is to return `LlmError::InvalidPrompt` naming the unsupported prompt type rather
than silently dropping it.

**No tool surface** — omit `tools` and `toolConfig` from `GeminiRequest` entirely. `LlmRequest` has
no field to carry a tool definition (structurally confirmed by `lib.rs`'s `capability_invariants`

**`map_finish_reason`** — the exhaustive mapping in `<behavior>`. `OTHER` and `RECITATION` have no
direct `FinishReason` equivalent; map both to `FinishReason::Error` carrying the raw reason string.
Do not coerce either to `Stop`, which would report a truncated or blocked generation as a normal
completion.

**`map_error`** — switch on **both** the HTTP status and the JSON `error.status` string, because
HTTP 429 alone is ambiguous on Google APIs. Apply the `RESOURCE_EXHAUSTED` disposition recorded
above this task list, and write the assumption into the doc comment on `map_error` in the
narrowly-matched, documented form `anthropic/adapter.rs:26-33` establishes.

**Body handling** — read the response body to a `String` first and deserialize it in a separate
step, exactly as the compatible engine does; a transport failure and a schema mismatch must remain
distinguishable in the error message (17-RESEARCH.md Pitfall 3). Do not use reqwest's typed-JSON
convenience method anywhere in this file.

**`execute_with_retry`** — the same non-retryable set the rest of the crate uses
(`AuthenticationError | InvalidPrompt | EmptyCompletion | UsageLimitExceeded`), exponential backoff
with jitter. It is a separate implementation from the compatible engine's because Gemini is a
separate adapter; keep the *set* identical and say in the doc comment that the set, not the loop, is
what must stay in lockstep.

**Capabilities** — `max_context_tokens: Some(1048576)`, `temperature_range: Some((0.0, 2.0))`, and
the six booleans as in `<behavior>`. `supports_vision` is `false` and that is a *truthful* report of

**Wiring** — add feature `gemini = ["dep:reqwest", "dep:rand"]` to `crates/paladin-llm/Cargo.toml`

Confirm the base URL, the API version segment, the default model ID and the `finishReason` value set

Complete the Gemini `LlmPort` surface with its streaming path and its model-list path.

**Streaming** — POST to `{base_url}/models/{model}:streamGenerateContent?alt=sse`. The `alt=sse`
query parameter is mandatory: without it the endpoint returns a raw JSON array, not SSE frames.
Parse the `bytes_stream()` by lines, strip the `data: ` prefix, and deserialize each payload as the
same `GeminiResponse` type the non-streaming path uses (Gemini streams partial
`GenerateContentResponse` objects rather than a distinct delta type — this is a genuine divergence
from the OpenAI-compatible shape and is worth a one-line comment at the parse site). There is no
`[DONE]` sentinel; the stream ends when the body ends.

Emit one `StreamingResponse` per frame carrying the frame's text parts concatenated, with
`finish_reason: None` until a frame carries a `finishReason`, at which point emit it mapped through
the Task 1 `map_finish_reason`.

**Model list (D-13/D-14)** — `GET {base_url}/models` with the same `x-goog-api-key` header. Parse
`GeminiModelsResponse`; Google returns fully-qualified names of the form `models/gemini-2.5-flash`,
so strip the leading `models/` segment before returning, since that is the form callers pass to
`model`. Memoize with `tokio::sync::OnceCell` so exactly one fetch happens per adapter instance even
under concurrent callers. On any failure or an empty list, fall back to `GEMINI_FALLBACK_MODELS`:
`gemini-2.5-flash`, `gemini-2.5-pro`. Log the fallback at `debug`, not `error` — offline is a
supported state (PROJECT.md's graceful-degradation constraint).

**`validate_model()`** — true when the model appears in the resolved list, live or fallback. This is
deliberately different from the shipped DeepSeek pattern of gating on a hardcoded `vec!`
(`deepseek/adapter.rs:793`), which rejects any model the provider ships after release — a tolerable
limitation for DeepSeek's two entries and actively wrong for Gemini, whose catalog moves fastest of
the five (D-13). The shipped three keep their existing behaviour (D-06).

Add the streaming and model-list tests to the same `#[cfg(test)] mod tests`, all against `mockito`.
