<objective>
**Tracer plan for the Phase 17 gap-closure run.** Close **CR-01** — the one Critical finding and the
only failing must-have in `17-VERIFICATION.md` — end to end, and prove the whole
red-test → production-fix → green-reproduction loop before any of the four Warning plans expand on
it.

`crates/paladin-llm/src/provider_factory.rs`'s `get_default_provider()` (`:365-376`) and
`list_available_providers()` (`:378-390`) decide a provider's credential is "configured" with a bare
presence check that is `true` for an environment variable set to the empty string. Every adapter's
own `*Config::validate()` rejects an empty key, so `create()` then fails with `ConfigurationMissing`
for a provider these two functions just reported as available — directly contradicting
`list_available_providers()`'s own doc comment. The crate's own `provider_name_round_trip` test
module (`provider_factory.rs:714-773`) already uses the correct check and documents exactly why; the
fix was applied to a test and never to the two production call sites it was guarding against.

**Purpose:** an availability report that over-reports is the same class of defect Phase 14 paid to
fix on the LLM capability flag. It misfires in any deployment where an unrelated provider's
credential variable is present but empty — `.env` templates, Docker/K8s environments passing through
unset host variables as empty strings. This repository's own environment is an example, which is
why the failure reproduces deterministically here.

**Output:** a non-blank credential check at both production call sites, one merged test-environment
guard covering all ten variables the registry reads, and four regression tests that fail against the
current tree.

## The trap this plan exists to avoid — read before starting

The reviewer's reproduction (`cargo test --test unit --features llm-all -- provider_factory
--test-threads=1` failing `test_get_default_provider` and `test_list_available_providers`) is
**real, but the production fix alone does not turn those two tests green**, and an executor who
assumes it does will ship a half-fix. Two independent causes are tangled together in that one
failure, and this plan separates them:

1. **The test-environment cause.** Those two tests hold `CleanProviderEnv`, which clears only the
   three original credential variables, while the functions they call scan the **whole nine-row
   registry**. The ambient empty `GEMINI_API_KEY` / `XAI_API_KEY` leak straight through.
   *Merging the guards fixes the test failure without fixing the defect.* If you stop here, CI goes
   green and CR-01 is still shipped.
2. **The registry-shape cause.** Under `--features llm-all` the `ollama` row carries
   `env_var: None` (D-12 — Ollama needs no credential) and therefore **always** qualifies. So
   `assert_eq!(get_default_provider(), None)` and `assert_eq!(providers.len(), 0)` are
   arithmetically unreachable under that feature set even with a perfect fix — the correct answers
   are `Some("ollama")` and `1`. This is confirmed by the reviewer's own numbers: the reported
   `left: 3` is `gemini + grok + ollama`, and after the fix removes the two empty-credentialled rows
   the remaining `1` is Ollama.

The defect is therefore **only** provable by a test that deliberately sets a credential variable to
the empty string inside a fully-cleared environment. That test is Task 1's centrepiece. The two
legacy tests are rewritten to be registry-aware in the same task so they stop encoding a
three-provider world.

## Assumption-delta decision (advisory checkpoint, never blocking)

**Primary noun:** *provider credential environment* — the set of environment variables the factory
reads to decide what is configured.

**Signal that fired:** pluralization. The phase went from three providers to nine, and CR-01 is a
symptom of exactly that: `provider_factory`'s availability check and `CleanProviderEnv`'s
three-variable guard were both authored for a three-provider world, while the functions they serve
now scan all nine rows. The test file states the split's rationale explicitly
(`provider_factory_test.rs:294-300`: the two variable sets are disjoint, so a separate lock avoids
serializing unrelated tests) — and that rationale is **false** for any function that scans the whole
registry, which is precisely the two functions under test.

**Decision: `promote`.** The two-group model (`CleanProviderEnv` for the original three,
`CleanNewProviderEnv` for the seven newer ones) is replaced by one model: *the registry's credential
environment*, a single guard over a single lock owning all ten variables the nine rows read.

**Rationale:** the alternative the review also offered — have the two tests acquire both locks —
preserves a false distinction and introduces a lock-ordering hazard (two mutexes, no declared
acquisition order, and a future test that takes them in the opposite order deadlocks). One lock
removes that class entirely. Cost is that tests touching disjoint variables now serialise; in a
589-line file with eleven tests that is not measurable.

**Accepted debt:** the guard's variable list is hand-maintained against the registry. A tenth
provider added without extending `CREDENTIALED_PROVIDERS` reintroduces the same blind spot one row
narrower. **What would force a further promote:** a mechanism that derives the guard's list from the
registry itself (the registry's `env_var` field is private and `paladin-llm` denies `unsafe_code`,
so exporting it is its own decision, not this plan's). Recorded here rather than silently absorbed.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| process environment → `provider_factory` | Environment variables are operator-controlled input. Their *presence* is used to make an availability claim that other code and other humans act on. |
| `list_available_providers()` / `get_default_provider()` → caller | The returned names are a claim about what will work. A caller that trusts the claim and calls `create()` is the party harmed when it is wrong. |
| test process environment → `tests/unit` binary | The ambient environment of whatever machine runs the suite. An unguarded variable makes a test's verdict a property of the machine, not of the code. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-17-60 | Spoofing | `list_available_providers()` / `get_default_provider()` availability claim | high | mitigate | A blank credential variable currently lets an unconfigured provider present itself as configured, so a caller selects a provider with no usable credential and an operator is told a provider is ready that is not. Task 2 makes the predicate `is_ok_and(|v| !v.trim().is_empty())`, aligning the report with every preset's own `validate()`. Proven by three regression tests (empty, ASCII-whitespace, non-ASCII-whitespace) and one positive control. |
| T-17-61 | Information Disclosure | the credential-emptiness check and its tests | high | mitigate | The check reads the credential's value. Neither the production predicate nor any assertion message may carry that value: the predicate discards it (`!v.trim().is_empty()` yields a `bool` and drops `v`), and the plan's own prohibition forbids naming a value in a failure message — assertion text names the *variable*, never its contents. Enforced by the acceptance criterion that no new `eprintln!`/`assert!` message interpolates the value; reviewed at commit. |
| T-17-62 | Tampering | test-environment isolation | medium | mitigate | Two locks over a shared conceptual resource is a deadlock hazard the moment any test acquires both; the merged single-lock guard removes the class. The guard's `Drop` restores every variable including on unwind, so a failing assertion cannot leak state into a sibling test. Proven by identical pass counts under `--test-threads=1` and under default parallelism. |

No `[ASSUMED]` / `[SUS]` package; no legitimacy checkpoint required. |
