<objective>
Close **WR-01**: a configuration file that `LlmConfig::validate()` accepts can fail
`LlmProviderFactory::create()` with `UnknownProvider`, purely on how the operator spelled one
provider name.

`LlmConfig::get_provider_config()` (`crates/paladin-llm/src/config/llm.rs:153-166`) matches
`"openai-compatible" | "openai_compatible"` case-insensitively, and
`is_recognised_provider_field_name` (`:179-193`) accepts both spellings for `default_provider` too —
so `default_provider: "openai_compatible"` is a config file that validates. But
`LlmProviderFactory::create()` (`:352-363`) lower-cases and then matches the registry's literal
hyphenated name, so the natural composition of the two types —
`factory.create(&config.get_default_provider_name()?)` — returns `UnknownProvider` for a value the
config layer just blessed.

**Purpose:** the failure mode is a working configuration that stops working at the point of use,
with an error message that says the provider does not exist when the config layer said it does. It
is the kind of inconsistency an operator cannot debug from either side alone, because each layer is
individually self-consistent.

**Output:** one-line separator normalisation on `create()`'s lookup key, rustdoc naming both accepted
spellings, and four regression tests pinning both the merge (two spellings, one row) and the
non-merge (`openai` is not absorbed).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator config file → `LlmConfig::validate()` → `LlmProviderFactory::create()` | An operator-authored provider name crosses two independently self-consistent validation layers. A disagreement between them is a defect neither layer can see. |
| provider name string → registry lookup key | The string is transformed before it selects which vendor's endpoint the process will talk to. Any transformation broader than separator normalisation could route a request to a different vendor than the operator named. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-17-63 | Spoofing | `create()`'s lookup-key normalisation | high | mitigate | A normalisation broader than `replace('_', "-")` — prefix matching, fuzzy matching, a nearest-name fallback — could resolve an operator's typo to a *different vendor's* adapter and send their prompts and credentials somewhere they did not name. The transform is exactly one separator substitution over an already-lower-cased string; no registry row contains an underscore, so it is provably incapable of merging two distinct rows. Pinned by `create_does_not_absorb_openai_into_openai_compatible`, which also asserts the error names `OPENAI_API_KEY` and not `OPENAI_COMPATIBLE_API_KEY`. |
| T-17-64 | Repudiation | `UnknownProvider`'s message | medium | mitigate | If the error echoed the normalised key, an operator debugging a rejected name would be shown a string they never wrote, and the audit trail of what was actually requested would be lost. The error keeps `provider_name.to_string()`; enforced by a scoped `grep` acceptance criterion and by the pre-existing `test_factory_error_messages`, which asserts on the underscore-bearing literal and runs unmodified. |
| T-17-SC-13 | Tampering | npm/pip/cargo installs | high | mitigate | **No package-manager install task exists in this plan.** The fix is one `str::replace` call; the tests use only the crate's existing surface. `git diff --stat -- crates/paladin-llm/Cargo.toml Cargo.toml Cargo.lock` being empty is an acceptance criterion on Task 2, so `make deny` / `make audit` verdicts are provably unchanged. No `[ASSUMED]` / `[SUS]` package; no legitimacy checkpoint required. |

ASVS L1, `security_block_on: high`. T-17-63 and T-17-SC-13 are `high` and each carries a named
mitigation with a named test or a named absence. Nothing blocks.
</threat_model>
