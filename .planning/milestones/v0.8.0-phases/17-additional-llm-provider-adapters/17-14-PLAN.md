<objective>
Close **WR-02**: `parse_temperature_range_env`
(`crates/paladin-llm/src/openai_compatible/adapter.rs:222-248`) validates that both
`OPENAI_COMPATIBLE_TEMPERATURE_MIN` and `_MAX` are set (or neither) and that each parses as `f32`,
but never checks that `min <= max`. An operator who swaps the two — a copy-paste transposition —
gets `Some((2.0, 0.0))` accepted silently and surfaced as
`ProviderCapabilities::temperature_range`, an inverted tuple against a crate-wide convention that
the pair is always ordered (`GrokConfig`'s `Some((0.0, 2.0))`, `KimiConfig`'s `Some((0.0, 1.0))`,
and so on). Any downstream consumer that clamps a requested temperature into the range will
misbehave, and nothing anywhere reports the configuration as wrong.

**Purpose:** this function already refuses a half-declared range on the stated ground that *"a
half-declared range is not a defensible partial state."* An inverted range is the same class of
statement and is currently accepted. The function is the generic provider's only guard on a
capability D-04 requires be operator-declared and pessimistically defaulted — it is exactly where a
declaration must be checked rather than trusted.

**Purpose of the second half (the precision edge):** `"NaN".parse::<f32>()` succeeds. `NaN > x` is
`false` for every `x`, so an inversion guard written as `if min > max` lets `(NaN, NaN)` — and
`(NaN, 1.0)`, and `(1.0, NaN)` — straight through, producing a range no consumer can clamp into and
no comparison can order. `inf` and `-inf` parse too. Adding the ordering check without a finiteness
check would ship a guard with a hole in exactly the place a guard is expected to hold.

**Output:** an ordering check and a finiteness check on the both-set arm, both returning the
function's existing `Err(String)` shape, plus six regression tests including the equal-bounds
boundary control and the two half-set controls that must keep passing.
