A single transient blip opening the connection — a `NetworkError` or `Timeout` before any bytes are
streamed — fails the whole streaming call immediately, where the identical failure on the
non-streaming path is retried up to `max_retries` times. The two methods of one `LlmPort`
implementation behave differently against the same fault. The review notes the pattern is inherited
from the DeepSeek adapter the engine was extracted from, but every provider this phase added
inherits it, which is what makes it worth fixing here rather than leaving it to read as
intentional-by-omission.

**The developer chose the full fix, not the documentation-only option** (interactive scoping
checkpoint, `/gsd-plan-phase 17 --gaps`, 2026-08-18): wrap the connection-opening POST — **only** —
in the same retry helper, in both implementations.

**Purpose and its limit.** Retrying the open is the correct parity fix, and the non-retryable set is
what keeps it safe: without it, an authentication failure on stream open would become a retry loop
re-transmitting a live credential to an endpoint that has already rejected it, and every retried
open would re-send the caller's entire prompt at the caller's expense. Both of those are the reason
this plan's regression tests assert an exact attempt count in both directions — N on a transient
failure, exactly 1 on an auth failure — rather than merely asserting that a retry happens.

**Output:** the retried-open shape in both `generate_stream` implementations, six mock-transport
regression tests, and rustdoc on both methods stating what is retried, what is not, and what a retry
costs.

## The structural constraint that shapes the implementation

`execute_with_retry<F, Fut, T>` and `call_api_with_retry<F, Fut, T>` both take `F: Fn() -> Fut` — a
closure callable repeatedly — and are generic over the success type `T`. The operation must
therefore be **self-contained and re-runnable**, and it must return something that survives the loop.

That means: the retried operation performs the POST, checks the status, reads and maps the error body
on a failure, and on success returns the opened `reqwest::Response` (`T = reqwest::Response`). The
`.bytes_stream()` call and the whole SSE assembly closure stay **outside** the retry loop, run once,
on the response the loop returned. This is not a stylistic preference — consuming the body inside the
operation would move the byte stream into a closure that must remain callable, and would make the
retry cover the stream itself, which the prohibition above forbids.

## Scope guards

- **Do not change either retry helper.** `execute_with_retry` and `call_api_with_retry` keep their
  bodies, their backoff, their jitter and — critically — their non-retryable sets exactly as they
  are. This plan changes call sites only.
- **Do not change the SSE parsing.** `CompatEngine::generate_stream`'s `flat_map` assembly (and its
  load-bearing comment about multiple `data:` events per chunk) and Gemini's `parse_sse_chunk` path
  are untouched.
- **Do not touch `parse_response`** — plan 17-15 owns it and has just landed.
- **Do not touch `map_error`** in either file. Plan 17-10's `300..=399` arm and plan 17-11's
  credential discriminator must survive.
- **Do not change any preset.** D-05 puts retry in the shared core; the four compat presets and the
  generic provider inherit the fix with no per-preset edit.
- **D-06** — `crates/paladin-llm/src/{openai,anthropic,deepseek}/` untouched. The DeepSeek adapter
  the pattern was inherited from keeps its own asymmetry; migrating it is a deferred idea, not this
  plan's work.
- **D-00o** — commit with `git commit --no-verify`; crate-scoped builds only.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| provider endpoint → `generate_stream`'s connection-opening POST | The POST carries the caller's full prompt and a live credential header. Every retry re-transmits both. |
| retry helper's non-retryable set → the retry loop | The set is the only thing standing between a bounded retry and a credential-replay loop against an endpoint that has already refused. |
| opened response → SSE byte stream → caller | Once bytes are consumed the caller has observed output. Anything that re-opens from here delivers duplicate tokens the caller cannot detect. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-17-69 | Information Disclosure | retrying a stream-open authentication failure | high | mitigate | Wrapping the open in retry would, without the non-retryable set, re-transmit a live credential up to N times to an endpoint that has already rejected it — the exact harm plan 17-11 closed on the non-streaming path. Both helpers' non-retryable sets are left byte-unchanged (pinned by a `git diff` grep returning 0) and both `generate_stream_does_not_retry_an_authentication_failure_on_open` tests assert the mock records **exactly 1** request. This threat is the reason the fix is a call-site wrapper and never a helper rewrite. |
| T-17-70 | Denial of Service | prompt re-transmission cost | medium | mitigate | Each retried open re-sends the caller's entire prompt, so a transient failure multiplies billed input tokens while the caller sees one call. Bounded by the same `max_retries` the non-streaming path already uses — no new ceiling is introduced — and stated explicitly on both `generate_stream` rustdocs so the cost is documented rather than discovered on an invoice. The non-retryable set keeps definitively-answered failures out of the loop entirely. |
| T-17-71 | Tampering | duplicated stream output | medium | mitigate | Extending retry over the byte stream would deliver the same tokens twice with no marker and no way for a downstream assembler to detect it. The retried closure returns the opened `reqwest::Response` and `.bytes_stream()` runs once outside the loop — enforced structurally (the helper's `Fn() -> Fut` bound cannot hold a consumed body), by scoped greps proving `bytes_stream()` appears once and after the retry call, and by the two success tests asserting deltas arrive in order and no delta appears twice. |
| T-17-SC-16 | Tampering | npm/pip/cargo installs | high | mitigate | **No package-manager install task exists in this plan.** The fix reuses two existing private helpers and `mockito`, already a dev-dependency. `git diff --stat -- crates/paladin-llm/Cargo.toml Cargo.toml Cargo.lock` being empty is an acceptance criterion on Task 2, so `make deny` / `make audit` verdicts are provably unchanged. No `[ASSUMED]` / `[SUS]` package; no legitimacy checkpoint required. |

ASVS L1, `security_block_on: high`. T-17-69 and T-17-SC-16 are `high` and each carries a named
mitigation with a named test or a named absence. T-17-70 and T-17-71 are `medium` with named
mitigations. Nothing blocks.

**Regression surface note:** this plan edits two files carrying three previously-closed
security-adjacent findings (17-09's model-identifier guard, 17-10's redirect policy in both files,
17-11's auth classification). Their survival is an explicit set of acceptance criteria — six greps,
