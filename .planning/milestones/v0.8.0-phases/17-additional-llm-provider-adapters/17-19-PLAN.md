<objective>
Close **G-17-4b**: Kimi cannot complete a `generate()` call with its own defaults, for two
independent reasons.

1. `KIMI_DEFAULT_MODEL = "moonshot-v1-8k"` is retired — Moonshot answers
   `{"message":"Not found the model moonshot-v1-8k or Permission denied","type":"resource_not_found_error"}`.
   The live list at the 2026-08-22 measurement held `kimi-k2.6`, `kimi-k2.7-code`,
   `kimi-k2.7-code-highspeed` and `kimi-k3`.
2. Even against a live-listed model, the framework's default temperature is rejected:
   `kimi-k2.6` answers `{"message":"invalid temperature: only 1 is allowed for this model"}`,
   while `PromptParameters::default()` sends `0.7` (`paladin-core` prompt.rs:151).

Fixing the model identifier is **necessary but not sufficient**. The second cause collided with a
locked decision — 17-UAT.md's `missing` list says "enforce **or** clamp", and **ADR-0004 considered
adapter-level clamping by name and rejected it** — so the earlier revision of this plan put that
fork to the developer as a blocking checkpoint.

**That checkpoint is answered. The developer selected option (a) on 2026-08-22:** the preset
declares `temperature` as a parameter its request path does not carry, reusing the
`CompatRequestParameters` mechanism plan 17-18 builds. This plan is now autonomous; the fork is
recorded here rather than re-litigated at execution time.

**Why (a) is not the thing ADR-0004 forbids** — carry this reasoning into the code, because a
later reader meeting a Moonshot preset that drops a parameter deserves to meet a decision rather
than an unexplained asymmetry. ADR-0004's objection is specific: *"a caller who requested 1.8 and
got 1.0 silently substituted has no way to discover the substitution happened."* Under (a) no
legal value is substituted for another. The key is absent from the body, the vendor applies its
own only-legal value, and the capability declaration says exactly that. This reading was reviewed
and accepted by the plan checker.

Option (b) and option (c) were **not** taken. Option (c) — stop fabricating sampling defaults in
`PromptParameters::default()` — remains the true root cause of *both* this blocker and G-17-4a's,
and the developer has explicitly chosen not to pay it down inside a gap-closure run. It is
recorded in `<deferred>` with a named trigger, not dropped.

One consequence of (a) must be handled here rather than discovered by a user. A truthful
`temperature_range: Some((1.0, 1.0))` meets `paladin_builder::validate()`, which checks
`self.data.temperature` **unconditionally** against the provider's declared range — and
`PaladinData::default()` sets `0.7` (`paladin-core` paladin.rs:254). Left alone, option (a) would
make **every Kimi-backed Paladin fail at build time**, including one whose author never mentioned
temperature. Task 2 closes that, and it lands *before* the declaration that would otherwise trip
it.

**Purpose:** make the Moonshot preset functional out of the box without lying in
`get_capabilities()`, without silently overriding a caller, and without turning an honest
capability declaration into a denial of service.
**Output:** refreshed Kimi model constants, a measured temperature declaration, option (a)
implemented once and regression-tested on both sides of the seam.
</objective>

## Facts already established — read these, do not re-derive them

**Plan 17-18 built the seam this plan extends.** `CompatRequestParameters` on
`CompatEngineConfig` declares, per parameter, whether this preset's request path carries it;
`build_request` gates each of the five optional sampling fields on that declaration; an omitted
parameter becomes an absent JSON key via the wire type's existing `skip_serializing_if`. Kimi's
declaration currently reads `CompatRequestParameters::all()` — deliberately unchanged by 17-18
so that plan was behaviour-preserving for every vendor except xAI.

**ADR-0004 is Accepted and governs temperature (D-00q).** Its operative content, verified
against the shipped tree:

- `ProviderCapabilities::temperature_range: Option<(f32, f32)>`, **both endpoints inclusive**;
  `None` falls back to the global `[0.0, 1.0]`.
- Under *Considered Options* it rejects, by name: *"Adapter-level clamping (each LLM adapter
  silently clamps an out-of-range temperature to its own legal range before sending the request)
  — rejected. Clamping silently alters the caller's value past the point where the caller can be
  told they were wrong."*
- The provider-aware validation is **implemented and live**, not aspirational:
  `src/application/services/paladin/paladin_builder.rs` `validate()` reads
  `self.llm_port.get_capabilities().temperature_range.unwrap_or((0.0, 1.0))` and returns
  `PaladinError::ConfigurationError` naming the rejected value. It validates
  `self.data.temperature` **unconditionally** — not only when the caller called `.temperature()`
  explicitly. So a narrowed Kimi range constrains every Paladin built against Kimi, including
  ones that never mentioned temperature.
- A **degenerate range where `min == max` is already an accepted, tested configuration** — plan
  17-14 established exactly that for the generic provider (`min > max` rejected, `min == max`
  accepted).

**`crates/paladin-llm/src/lib.rs`** carries a cross-adapter invariant test,
`test_every_adapter_declares_a_temperature_range`, requiring every adapter's
`get_capabilities().temperature_range` to be `Some(_)`. `None` is not available as an answer.

**Kimi's preset today** (`kimi/adapter.rs:152-181`) declares `temperature_range: Some((0.0, 1.0))`
— which the live vendor does not honour, since only `1` is accepted.

**The builder already knows whether the caller expressed a temperature — the distinction option (c)
would have to add at the `paladin-core` level already exists one layer up.** Verified against the
shipped tree:

- `PaladinBuilder` carries a private `manual_temperature_override: bool`
  (`paladin_builder.rs:98`), initialised `false` (`:141`) and set `true` only by
  `pub fn temperature(mut self, temperature: f32)` (`:258-260`). It exists today to let an
  explicit `.temperature()` call beat auto-temperature selection.
- `validate()` (`:1107-1131`) reads
  `self.llm_port.get_capabilities().temperature_range.unwrap_or((0.0, 1.0))` and compares
  `self.data.temperature` with inclusive endpoints, returning
  `PaladinError::ConfigurationError` naming the range, the provider and the rejected value. It
  consults no flag.
- `PaladinData::default()` sets `temperature: 0.7` (`paladin-core`
  `platform/container/paladin.rs:254`). So the value `validate()` sees for a caller who said
  nothing is a framework-fabricated `0.7`, not a request.
- **A test landmine:** `test_builder_validation_invalid_temperature` (`:1394-1400`) builds the
  builder by struct literal with `temperature: 1.5` and `manual_temperature_override: false`,
  then asserts rejection. Its *intent* is "an out-of-range value the caller asked for is
  rejected", so it must express that through the flag (or through `.temperature(1.5)`) once the
  gate consults the flag. The DeepSeek range tests at `:1427-1495` all go through
  `.temperature(..)` already and are unaffected.
- `build()`'s auto-temperature branch (`:1282-1305`) assigns `self.data.temperature` *after*
  validation. Whether an auto-selected value is validated at all is a **pre-existing** question,
  not this plan's to change — read it, record the answer in the SUMMARY, and leave the path alone.

**Credential loading and probe hygiene** are unchanged from plan 17-18; see this plan's
`<executor_notes>`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Paladin process → vendor API (`api.moonshot.ai`) | The `Authorization` header carries the operator's credential outbound; an untrusted response body comes back. |
| adapter capability declaration → `paladin_builder::validate()` | The declared range decides which Paladins can be constructed at all; a wrong declaration is a denial-of-service on legitimate configurations. |
| vendor response body → logs / SUMMARY | Attacker-influenceable text this plan deliberately quotes into a durable record. |
