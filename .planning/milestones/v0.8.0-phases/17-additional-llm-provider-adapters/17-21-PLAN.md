<objective>
Close the first half of **G-17-4d**: the Qwen adapter models DashScope as a single global
endpoint, and it is not one.

**This plan previously said the opposite, and was wrong.** Its earlier revision carried a
prohibition — *"`QWEN_DEFAULT_BASE_URL` MUST NOT be changed"* — resting on the inference that a
`401` carrying Alibaba's documented error envelope proved the URL resolved correctly and
implicated only the credential. That inference does not hold. Alibaba documents that a Base URL
must be used with an API key from the same billing plan, and that **API keys are independent
across regions and cannot be used across regions**. A region-scoped key therefore returns a
well-formed `401` from *every* endpoint except its own, so the observed signature is identical for
a right URL with a wrong key and a wrong URL with a right key. The credential was valid the whole
time.

**Measured 2026-08-22 — same credential, same binary, same run, only the endpoint differing:**

- `https://dashscope-intl.aliyuncs.com/compatible-mode/v1` (the shipped default, Singapore) →
  3 models, **byte-identical to `QWEN_FALLBACK_MODELS`**, i.e. the live fetch silently failed →
  FAIL.
- `https://dashscope-us.aliyuncs.com/compatible-mode/v1` (US Virginia) → **92 live models**,
  differing from the fallback, with `QWEN_DEFAULT_MODEL` present → PASS.

G-17-4c is therefore **resolved** and is not a target of this plan or of this run. What replaces it
is G-17-4d, and the developer has made the binding call: **the shipped default becomes US
(Virginia)**.

Be clear about what that does and does not fix. It does not eliminate the region problem — it
**moves** it, from the operator whose workspace is in Virginia to the operator whose workspace is
in Singapore or on the mainland. That is why the documentation half of this task is not a
courtesy: with the default flipped, the newly-mismatched operator needs the region-scoping rule
and the endpoint list in front of them at the moment they read about `DASHSCOPE_BASE_URL`.

The other half of G-17-4d — that a region mismatch is *silent*, because `available_models()`
reports an auth failure exactly as it reports being offline — is plan 17-22's, and it is
vendor-agnostic engine work that benefits all six compat-backed adapters.

**Purpose:** an operator's shipped defaults reach a real endpoint, and the one they do not reach
is one step from being corrected.
**Output:** a Virginia default, live-verified constants and parameter declarations measured at
that endpoint, the reversal recorded so it is not undone by someone re-deriving the old argument,
and the change announced to operators.
</objective>

## Facts already established — read these, do not re-derive them

**What plans 17-18 and 17-19 built, which Qwen inherits for free:** `CompatRequestParameters` on
`CompatEngineConfig` lets a preset declare, per sampling parameter, whether its request path
carries it; `build_request` honours that declaration. Qwen currently declares
`CompatRequestParameters::all()`. If DashScope turns out to reject a parameter the way xAI rejects
`presence_penalty`, the fix is a declaration change on the preset — no engine work. Plan 17-19
additionally narrowed `paladin_builder::validate()` to temperatures the caller expressed, so a
truthful narrow `temperature_range` is no longer a build-time denial of service.

**The harness already probes Qwen twice** — model list (with the byte-for-byte fallback
discrimination) and, since plan 17-18, `generate()` with the framework's default prompt
parameters. No harness change is needed by this plan.

**The harness reports the EFFECTIVE base URL, not the constant.** This was fixed on 2026-08-22
after the first Virginia run appeared to pass while printing the intl URL — it printed
`*_DEFAULT_BASE_URL` rather than the URL the run actually used, and would have attributed a result
to the wrong endpoint. `live_vendor_smoke.rs` now reads `base_url` back off the resolved config and
flags an override explicitly. Read that reporting line before trusting any attribution.

**Qwen's preset today** declares `temperature_range: Some((0.0, 2.0))`,
`max_context_tokens: Some(131_072)`, `supports_vision: false` (deliberately — this is the text
adapter, not `qwen-vl`), and `QWEN_FALLBACK_MODELS = ["qwen-plus", "qwen-turbo", "qwen3-max"]`
with `QWEN_DEFAULT_MODEL = "qwen-plus"`. Only the default model has been seen in a live list
(present among the 92 at the Virginia endpoint); the rest are still vendor-documentation
assertions.

**The known compatible-mode regional endpoints**, from Alibaba's Base URL documentation:

| Region | Compatible-mode base URL |
|---|---|
| US (Virginia) | `https://dashscope-us.aliyuncs.com/compatible-mode/v1` |
| Singapore | `https://dashscope-intl.aliyuncs.com/compatible-mode/v1` |
| China (mainland) | `https://dashscope.aliyuncs.com/compatible-mode/v1` |

Alibaba additionally recommends workspace-dedicated domains
(`{workspace-id}.{region}.maas.aliyuncs.com`) for production. **Out of scope here** — see
`<deferred>`.

**The module's existing "Region default" rustdoc** (`qwen/adapter.rs:11-20`) already says DashScope
publishes at least five regional base URLs and that `DASHSCOPE_BASE_URL` reaches another with no
code change. What it does **not** say — and what turned a misconfiguration into five days of
misdiagnosis — is that the *credential* is region-scoped too, so the override is not optional
tuning for an operator in another region, it is mandatory. That sentence is the documentation
deliverable.

**Constants versus literals.** The Qwen unit tests (`qwen/adapter.rs:262-290`, `:473-490`) all
reference `QWEN_DEFAULT_BASE_URL` rather than repeating its value, so they follow the constant.
One place does not: `crates/paladin-llm/src/lib.rs:326` builds a cross-adapter fixture from the
literal. It will still compile and pass — it asserts capabilities, not URLs — and **plan 17-20
owns replacing it with the constant**. Leave it alone here.

**The credential import path:** the host directory `~/.config/paladin` is bind-mounted read-only
into the container, one secret per file, filename-lowercased to variable name. A file is applied
only when the variable is currently unset **or empty** — the repo `.env` declares these names with
empty values, which is why the empty-check exists. The loader trims CR/LF and surrounding
whitespace, and skips placeholder-looking values. The stored `DASHSCOPE_API_KEY` is **valid**; its
117-character length was a red herring in the original diagnosis.

**Documentation of the advertised surface is plan 17-20's**, which now runs *after* this plan so it
can quote the shipped constant rather than predict it. Do not edit `config.example.yml`,
`docs/src/getting-started/configuration.md`, `crates/paladin-llm/README.md` or `COVERAGE.md` here.

## Deferred and explicitly out of scope

- **Making a masked auth failure audible in `available_models()`** — *no longer deferred.* It was
  raised to the developer alongside the previous revision of this plan set and is now **in scope as
  plan 17-22**, the second half of G-17-4d. The D-13/D-14 fallback contract itself is unchanged

  Alibaba recommends over the shared regional endpoints for production. Out of scope: they are
  per-workspace, so they cannot be a compiled default at all — they would need a new configuration
  concept, and `DASHSCOPE_BASE_URL` already reaches one today with no code change. **Trigger:** a
  production deployment of this framework against Model Studio, or vendor guidance that the shared
  compatible-mode endpoints are rate-limited or deprecated for production use.
- **A per-region default resolved from a `DASHSCOPE_REGION`-style variable** rather than a single
  compiled endpoint. Genuinely tidier than a default that is right for one region and wrong for
  three, and genuinely a new configuration surface across nine adapters. Not taken inside a
  gap-closure run. **Trigger:** a second vendor shipping region-scoped credentials against
  region-scoped endpoints.
- **A key-gated live test in CI** — 17-CONTEXT.md's Deferred Ideas lists live key-gated tests for
