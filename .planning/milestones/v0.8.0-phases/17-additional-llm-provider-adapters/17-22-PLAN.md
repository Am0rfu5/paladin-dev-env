<objective>
Close the second half of **G-17-4d**: a region/credential mismatch is invisible.

This is the second time the silent fallback turned a misconfiguration into a healthy-looking
result. `available_models()` swallowed a `401` and returned a plausible three-model list, which is
precisely why G-17-4c was misdiagnosed for five days — the original conclusion, *"the base URL is
CONFIRMED CORRECT ... what fails is authentication"*, was reached by a competent reader looking at
a well-formed list and a well-formed error envelope and having no signal that told the two failure
modes apart.

The engine already knows the difference. `map_error` maps `401` to
`LlmError::AuthenticationError` and a connection failure to `LlmError::NetworkError`, and
`fetch_live_models` returns whichever it got. `available_models()` then throws that distinction
away, logging both at `debug` with the same sentence (`compat/engine.rs:682-701`). The fix is to
stop discarding information the call site already has.

**Scope, exactly as the developer set it.** IN: distinguishing an **auth** failure — a
misconfiguration, which warrants surfacing — from an **offline** failure — a supported state,
which stays quiet. OUT: the D-13/D-14 fallback contract itself. The method still returns the
curated list rather than erroring. Those two are separable: what the method *returns* and how
loudly it *describes* what happened are independent, and only the second changes here. If
execution finds otherwise, that is a decision to raise, not an assumption to make.

**This is shared-engine work and must stay vendor-agnostic.** `CompatEngine` backs six adapters;
all six gain the diagnostic. Nothing in the change may name a vendor or match on a host — the
classification is a function of the `LlmError` variant alone, which is what keeps D-05's boundary
intact.

**Purpose:** the next misconfiguration announces itself instead of being diagnosed five days later
from a UAT run.
**Output:** a total, tested classification; a harness that can show it; the operator-facing symptom
description corrected; and the run's final four-vendor regression record.
</objective>

## Facts already established — read these, do not re-derive them

**The call site, verified against the shipped tree** (`compat/engine.rs:678-704`):
`available_models()` wraps a `tokio::sync::OnceCell` so exactly one fetch happens per engine
lifetime even under concurrent callers, then matches on `fetch_live_models()`'s result. Three arms:
a non-empty live list is returned; an empty live list logs at `debug` and falls back; an `Err(e)`
logs at `debug` — *"live model list fetch failed ({e}); falling back to curated list (not
authoritative)"* — and falls back. The `Err` arm is the one this plan splits. The empty-list arm is
a third case and is **not** in scope: an endpoint that answers with an empty catalogue is neither
an auth failure nor an offline one.

**The error is already classified before it reaches that arm.** `fetch_live_models`
(`:637-672`) maps a transport failure to `LlmError::Timeout` or `LlmError::NetworkError`, and a
non-success status through `map_error` (`:318-355`), which gives `401 -> AuthenticationError`,
`429 -> RateLimitExceeded`, `404 -> ModelNotAvailable`, `400 -> InvalidPrompt`,
`300..=399 -> ProcessingError` with the refused-redirect message, and everything else
`-> ProcessingError`. A preset may also install an `error_override`, consulted first — Gemini and
DeepSeek-style presets use it — so the variant reaching `available_models()` is already
preset-influenced without the engine knowing which preset did it. That is the vendor-agnostic seam
this plan reads.

**Redaction is already applied.** Every non-success body passes through `diagnostic_excerpt`
(redact-then-bound) inside `fetch_live_models` before it is embedded in the mapped error, so the
`{e}` this plan logs is already redacted. What is *not* yet controlled is the base URL, which this
plan adds to the message — see the threat register.

**`log` is a first-party dependency of `paladin-llm`** (`Cargo.toml:43`, `log = { workspace = true }`),
so `log::warn!` needs nothing new. The dev-dependencies are exactly `tokio-test`, `criterion` and
`mockito` — **no log-capture crate and no logger implementation**, which is why the classification
is tested as a pure function rather than by asserting on emitted records, and why the example
carries its own writer.

**The `log` facade with no installed logger emits nothing.** `live_vendor_smoke.rs` prints with
`println!` and installs no logger, so today a `log::warn!` from the engine would be invisible in a
harness run. A `log::Log` implementation is a trait with three methods (`enabled`, `log`, `flush`)
and `log::set_boxed_logger` + `log::set_max_level` install it; writing ~15 lines of that in the
example is what makes the live demonstration possible without a dependency.

**The harness reports the effective base URL**, read back off the resolved config rather than from
the `*_DEFAULT_BASE_URL` constant, and flags an override explicitly. That is what makes the
deliberately-mismatched demonstration in task 2 attributable.

**Plan 17-21 wrote the module rustdoc's region section** and deliberately described the *current*
symptom — a plausible three-entry list rather than an error — with a note that this plan amends it.
Amend it; do not leave two descriptions of the symptom in the tree.

| Boundary | Description |
|----------|-------------|
| vendor response body → log output | An attacker-influenceable body reaches a log line that is now emitted at a level operators actually read. |
| operator configuration → log output | This plan writes the configured base URL into a log message; a base URL is operator-supplied and can in principle carry a userinfo credential. |
| engine → six adapters | One shared code path changes behaviour for every compat-backed provider at once, including the self-hosted ones D-13/D-14 were written for. |
