<objective>
Make the publishable crate set an explicit, mechanically-checked fact before any trust link is
created, and get `paladin-herald` onto crates.io so it can be trust-linked at all.

crates.io Trusted Publishing is configured per crate, so the crate list stops being an
implementation detail and becomes the security boundary: an unlisted crate is an unprotected
crate. Three sources in this tree already describe that set and one of them is wrong —
`cargo metadata` reports eleven publishable packages, `.crate-names.txt` lists eleven, and
`release.yml`'s `CRATES` array lists ten. This plan closes that, then rides the still-live token
path one last time to publish the eleventh crate, because crates.io cannot configure Trusted
Publishing for a crate that has never been published.

Purpose: every later plan in this phase depends on eleven crates existing on the registry. The
trust links in 19-03 cannot be created for a crate with no crates.io entry, and the phase's
honesty criterion forbids describing an unlinked crate as covered.
Output: a reconciled eleven-crate publish order in `release.yml`, and `19-PUBLISH-EVIDENCE.md`
seeded with the reconciliation and the bootstrap run.
</objective>

<assumption_delta_decision>
**Signal family:** pluralization (detector fired on `second`, `alongside` in the phase scope).

**The real delta:** the noun "publish credential" is singular today (one standing
`CARGO_REGISTRY_TOKEN`) and this phase transiently makes it two — the standing token and the
OIDC-minted token both able to publish during the proof window.

**Decision: promote.** The OIDC-minted, per-run credential becomes the single primary publish
credential; the standing token is not kept alongside it. That is the phase's whole thesis — the
ROADMAP states plainly that a repository holding both has widened its attack surface, not reduced
it — so `add-alongside` is the explicitly rejected option here. The two-credential state is a
window bounded by D-05's ratchet, not a steady state, and 19-04 closes it by destroying the
standing token on both sides. No accepted debt.
</assumption_delta_decision>

  <context>
    D-02 rated this reversible until the first real publish and one-way afterwards. A published
    crate version can never be deleted; yank hides, it does not remove. Publishing `paladin-herald`
    permanently claims that name on crates.io under this project's ownership and permanently
    publishes version `0.8.1-rc.1` of every one of the eleven crates.

    Research settled D-03's open question against the optimistic branch: crates.io **cannot**
    configure Trusted Publishing for a crate that has never been published. There is no
    pending-publisher feature. So there is no route in which `paladin-herald` is covered by
    Trusted Publishing at the end of this phase without a first publish happening first, and the
    only credential available for that first publish is the standing token this phase exists to
    destroy — which is precisely why D-05 orders proof before revocation.

    The bootstrap is a **prerelease**, deliberately. `0.8.1-rc.1` never wins default dependency
    resolution, so it does not clear the 0.5.1 → 0.8.0 registry backlog that CONTEXT defers to a
    later phase, and it drags in none of the half-published-recovery machinery Phase 20 exists to
    build. It also runs through CI on the existing credential path rather than from a laptop, so
    no publish-scoped token is copied onto a developer machine to accomplish it.

    What undoing costs: nothing can be undone. The versions stay. What choosing option-b costs:
    criterion 7 is satisfied by naming `paladin-herald` not-covered with its interim auth path, but
    `cargo publish -p paladin-ai` stays broken against the registry, and Phase 20's pre-publish
    gate inherits the same broken order — the outcome PUB-01 says must not happen a second time.
  </context>
