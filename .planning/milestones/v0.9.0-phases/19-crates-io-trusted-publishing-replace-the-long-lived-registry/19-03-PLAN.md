<objective>
Prove the new path can actually publish, using the registry's own provenance record rather than a
green checkmark, while the old credential is still live and still able to ship a fix.

This is the ordering criterion, not a preference. Revoking first and debugging the OIDC exchange
afterwards leaves the project unable to release until it works again — the exact failure mode
PUB-03 exists to prevent. So the ratchet runs proof first: eleven trust configurations, then one
real prerelease publish, then evidence, and only then 19-04's destruction of the old credential.

Purpose: PUB-03 is the gate every later step depends on. Nothing in 19-04 may run until this plan
has produced a recorded, non-dry-run exchange that crates.io itself attributes to Trusted
Publishing.
Output: eleven trust configurations, a real `0.8.1-rc.2` publish through the rewritten job, and the
`## OIDC Proof Event (PUB-03)` section of the evidence file filled with per-crate provenance.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| human operator → crates.io trust configuration | Eleven hand-entered configurations decide which external identity may publish; a typo in one field silently widens or breaks the trust relationship |
| GitHub OIDC claims → crates.io authorisation decision | crates.io grants publish scope purely on claim matching; the claim set is the whole authentication |
| workflow self-report → the evidence record | A green job is the cheapest and least trustworthy evidence available; the registry's own provenance is the expensive and trustworthy one |
