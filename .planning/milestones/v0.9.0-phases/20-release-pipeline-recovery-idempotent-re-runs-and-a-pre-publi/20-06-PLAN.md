Write the stuck-halfway runbook: `docs/src/appendix/release-recovery.md`, cross-linked from the two
existing release documents and registered in the book's table of contents. It answers D-13's list
concretely — how to find out what actually reached crates.io, how to complete forward, why a
published version is never retried, who may yank, and what is recorded when one happens.

`.github/workflows/` or `scripts/` today, and the half-published state has no written procedure.

the same vocabulary the log does, which is why it lands after the outcome table exists.

`release-checklist.md`.

    Create `docs/src/appendix/release-recovery.md` following `release-checklist.md`'s structure:
    an H1, then a blockquote callout linking to `release-automation.md` and `release-checklist.md`
    and stating what this document is for, then numbered sections with terse bullets. Immediately
    under the callout, put a single status line recording whether the procedure has been exercised.

    Cover, in this order:

    **Establishing what actually reached crates.io.** A copy-pasteable loop that queries the
    versioned crate endpoint for each of the eleven crates at the tag version and prints a per-crate
    verdict, sending the User-Agent header crates.io requires — without it the registry answers 403
    and the operator gets a uniformly wrong answer at the worst possible moment. Say that the same
    check is what the publish job itself performs, so the runbook and the pipeline cannot disagree.
    Mention that the sparse index is the second place to look when a version reads as present but a
    dependent crate's publish still fails on resolution.

    **Reading the run.** How to interpret the per-crate outcome table in the job's step summary:
    what each of the four states means, and that a run reporting no crate in the published-now state
    fails deliberately — the tag is already fully published and there was nothing to recover, which
    is a diagnosable red rather than a broken pipeline. Note that the workflow's overall conclusion
    can be red for reasons unrelated to publishing, and that the publish job's own table is the
    authoritative record of what moved.

    **Completing forward.** The default recovery is to re-run the same tag's existing workflow run
    from the Actions UI: "Re-run failed jobs" first, since it skips work that already succeeded, and
    "Re-run all jobs" as the fallback — both are safe because the release object is reused rather
    than recreated, the gate re-verifies, and the publish loop skips crates the registry says are
    already at the version. Explain why the documented path is a re-run of the tag-push event and
    not a dispatch: the environment's deployment policy and the OIDC subject claim both require the
    tag ref, and dispatch eligibility under Trusted Publishing has never been tested here. State
    plainly that two release runs must not be in flight against the same tag at once — the registry
    pre-checks would race and the loser sees a publish rejection that looks like a real failure — and
    that the fix is to let the in-flight run finish, or cancel one, before starting another.

    **When completing forward is not enough.** A published version is never deleted and never
    re-uploaded: crates.io does not permit it, and a retry of the same version cannot succeed. A bad
    publish is corrected by cutting a new patch version and yanking the bad one. Yanking hides a
    version from new dependency resolution; it does not remove it, and existing lockfiles keep
    resolving it.

    **Who may yank, and how it is recorded.** The crate-owner account on crates.io — the repository
    owner — is the only actor who may yank. CI does not and must not: no workflow, script or make
    target in this repository performs a yank, and the OIDC-minted publish token is deliberately not
    used for one. Give the command shape and note that it must be run for each affected crate. Then
    a "Yank register" section containing a Markdown table with columns for version, crates, reason,
    owner and date, an instruction to append a row for every yank, and an explicit note that these
    entries live here and not in `SECURITY-EXCEPTIONS.md`, whose contract is mechanically checked
    for advisory suppressions and would be corrupted by an unrelated row. Include the table header
    and separator with no data rows yet, so the first real yank has somewhere obvious to go.

    **When the gate blocks the release.** One subsection per failure mode of
    `scripts/check-release-consistency.sh`, each naming the status token or message an operator will
    see and the concrete fix: manifest versions disagreeing with the tag, a changelog missing its
    section for the version, a changelog file absent, no publishable packages discovered, a missing
    SHA on the CI path, a lookup failure, and no recorded successful CI run for the tagged commit.
    For the last one, give the two remedies the phase's decision text specifies — re-run CI on `main`
    at that commit, or fix and re-tag — and say that no tag trigger is being added to the CI workflow
    to make this go away.

    Quote the actual strings the scripts emit rather than paraphrasing them, so an operator can
    search the page for the text in front of them.
