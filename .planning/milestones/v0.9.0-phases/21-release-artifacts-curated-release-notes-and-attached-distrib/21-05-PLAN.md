now honors it, publishes the verification instructions outside the release body, and closes
ARTIFACT-05's "decided and recorded with its reasoning" clause for signing and provenance.

Add a `## Release Notes and Attached Artifacts` section, placed after the operator guide and
before the trusted-publishing material so a reader meets it in release order. It covers, in this
order:

**Body source.** The release body for `vX.Y.Z` is the root `CHANGELOG.md` `## [X.Y.Z]` section,
extracted by `scripts/extract-changelog-section.sh` — everything between that heading and the next
`## [` heading. State explicitly that a tag whose version has no such section fails the
`create-release` job, quote the remedy the job log prints
(`run make release VERSION=X.Y.Z (finalizes changelogs) before tagging`), and state that the
pipeline has no alternate body source. Note that a heading-only section is accepted, because
`scripts/finalize-crate-changelogs.sh` legitimately produces one for a quiet prerelease. Note that
the ten per-crate changelogs ship inside the published crates and contribute nothing to the
release body.

**Artifact inventory.** A table of what a release attaches: the three binaries
(`paladin`, `paladin-cli`, `paladin-server`) with the feature set they are built under
(`cli,web-server`, plus `vendored-openssl` on the aarch64 Linux leg) and the four matrix targets,
the `paladin-<os>-<arch>.tar.gz` archive naming, the per-asset checksum files, the aggregated
`SHA256SUMS`, the CycloneDX SBOM, and the container image. State the inventory as fact only for
what the pipeline produces, and cross-reference `expected_binaries_for_target` as the single place
a target's binary set is narrowed.

**Verification.** The one-command checksum verification and its macOS variant, and the
digest-pinned image pull. Show the commands a consumer runs after downloading, matching the text
`finalize-release-body.sh` composes into the body word for word so the two cannot drift.

**Assembly order.** One short paragraph: `create-release` publishes the curated notes alone; a
terminal `finalize-release-body` job appends the artifact sections from real job outputs; a leg
that failed or was skipped contributes no section, so the release never advertises an artifact the
run did not produce.

**Signing and build provenance.** Record the decision as deferred with its reasoning: adopting
cosign or GitHub artifact attestations would add new action surface plus key/identity management
in the same change that removes archived actions, and no consumer requirement demands it yet. Name
`actions/attest-build-provenance` as the natural candidate when it is taken up. State plainly, in
the consumer's own terms, that the attached artifacts carry checksums but no signature and no
build attestation — a checksum proves integrity against the release, not origin. Record the image
size figure as advisory against a 500 MB target, not a gate.

Do not restate anything about workflow triggers, and do not edit
`docs/src/contributing/branching-model.md`.

Then verify `COVERAGE.md` against the shipped tree: every INTEGRATE row must name a capability the
workflow or a script actually invokes, and no OPT-OUT row may name one it does. Correct any row
that drifted during execution and note the correction in the SUMMARY.

automation chapter rather than restating the inventory table.

a previously-failed artifact leg succeeds will add that leg's section. Note that asset uploads are
idempotent by name. Extend the existing changelog failure-code entry with a pointer to the sibling
failure now raised by the extraction step on the release-creation path, so an operator reading a
failed run finds the same remedy from either direction. Do not renumber existing sections or
