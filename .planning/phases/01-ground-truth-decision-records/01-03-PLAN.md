Author `# ADR-0004: Temperature validation` using the heading set from `PROMOTION.md`.

`## Status` body is the bare word `Accepted`, followed by a `**Date:**` prose line.

`## Context` states the question — provider-aware range or global clamp — and records the two
findings that reframe it. First: `ProviderCapabilities` at
`crates/paladin-ports/src/output/llm_port.rs:754` has **no temperature-range field at all**, so the
provider-aware position was never implementable as specified by anyone who tried. Second: the
contradiction is live in the tree, not only on paper — `src/application/services/paladin/paladin_builder.rs:1112`
clamps to `[0.0, 1.0]` while `crates/paladin-llm/src/config/llm.rs:14` documents a 0.0-2.0 default
range. Re-read all three sites before writing the citations.

`## Decision` is a bullet list carrying D-15, and it must be specific enough that GAP-07 implements
exactly one interpretation:
- Validation is **provider-aware**: a temperature range is added to `ProviderCapabilities` and the
  selected provider's range is what a requested temperature is validated against.
- Name the new field concretely — its identifier, its Rust type, and whether it is optional. State
  the endpoint contract explicitly: whether the minimum and maximum are inclusive, and that the
  comparison is a float comparison at the endpoints, so an implementer does not have to guess
  between `<` and `<=`.
- State the fallback when a provider declares no range — what happens if the field is absent or
  `None` — as a named behavior, not an implicit one.
- State the ordering: the provider range is checked first; the autonomous task-type bands
  (`temperature_service.rs`, bounds validated in `autonomous_config.rs:107-110`) stay **a layer
  above** as task-type guidance and narrow within the provider's range rather than replacing it.
  Name what happens where a band and a provider range would both constrain the same value.
- Record the consequence: this makes Epic 6 REQ-5's DeepSeek 0.0-2.0 range reachable through the
  normal Paladin path instead of unreachable by construction.
- Record the reversibility rating (`costly`) and its reason: every adapter must populate the new
  field and downstream consumers branch on it.

`## Considered Options` is one bullet per rejected option: `REQ-temperature-range-v1` and `-v2` from
REQUIREMENTS.md variant group 2; a global `[0.0, 1.0]` clamp — reject it in the words D-15 uses,
namely that it would require recording Epic 6 REQ-5 as withdrawn, which is an explicit capability
reduction; and adapter-level clamping — reject it because it clamps silently past the point where
the caller can be told they were wrong. Also name `REQ-dynamic-temperature` and state that it
interacts with, rather than competes with, this decision.

`## Code Locations` is a bulleted `file:line` list: `llm_port.rs:754`, `paladin_builder.rs:1112`,
`llm/config/llm.rs:14`, `temperature_service.rs`, `autonomous_config.rs:107-110`.

`## Code Conformance` body is the bare phrase `must change`, followed by a prose line naming
**GAP-07** in Phase 2 as the requirement that lands the ports-layer change, and stating that nothing
in this phase edits Rust source.

`## Downstream Consumers` names Phase 2 GAP-07, the three LLM adapters that must populate the new
field, and — as an explicit **sequencing note** — Phase 14's **WEB-03**, which corrects
`supports_tool_calling` on the same `ProviderCapabilities` struct. State that the two must not be
scheduled independently.
