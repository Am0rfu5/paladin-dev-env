<objective>
Make the shipped Kubernetes topology tell the truth about the in-process token store (WEB-02), without
degrading it.

D-06 is a deliberate departure from WEB-02's own "done when" text, and **the deviation is the
decision**: the requirement offers exactly two exits — pin `replicas: 1`, or build a shared-store
`AuthPort` — and neither is taken. The tree shows why. `k8s/server/configmap.yaml` disables the
bearer-token verifier and authenticates with static API keys sourced from a Secret, byte-identical in
every pod, so `k8s/server/deployment.yaml`'s shipped replica count is correct today. The correctness
edge is gated by a config flag, not by the replica count. Pinning replicas would degrade a working
deployment to guard a path the shipped configuration has turned off.

So the fix is a loud, unconditional startup warning when the constrained store is actually wired
(D-07), paired with the limitation stated in the deployment artefacts and documentation — which is
what ROADMAP criterion 2's second clause ("or the deployment artefacts and documentation say it will
not") actually asks for. The shared store itself is deferred with a named trigger by D-09 and recorded
in ADR-0041 by plan 14-05.

This plan also closes Phase 13's second hand-off item, D-15(b): `REQ-fail-closed-auth-posture` has the
code path but no test, so under this project's evidence bar it cannot be marked shipped. Both new
tests are the Wave 0 gaps `14-VALIDATION.md` records.

Purpose: an operator who turns the constrained path on cannot miss the constraint.
Output: one named warning constant and its emission, this binary's first test module with two tests,
and three artefacts stating the limitation.
</objective>

<assumption_delta_decision>
**Signal:** the `pluralization` family fired on WEB-02's multi-replica text ("…against one server
instance either verifies against another…") — a second serving instance introduced where the identity
model assumed one.

**Primary noun:** the **credential-verification scope** — the boundary within which a token issued by
this system verifies. Today that noun resolves to *the issuing process*, and the identity model
(`AuthPort` + `Principal`) is already parameterised over it: `AuthPort` is a trait, and
`InMemoryTokenAuthAdapter` is one implementation of it.

**Decision: `no-change`, with a recorded trigger.**

Rationale: the generalization the signal points at — verification scope becoming *the deployment*
rather than *the process* — is exactly the shared-store swap D-09 defers, and M9 §6.2 records that the
port was designed to permit it. The port trait is already the general representation; the in-process
store is already demoted to being one variant behind it. There is nothing to promote, because the
promotion happened at design time. Adding a second identity noun alongside `AuthPort` now would be
`add-alongside` debt with no consumer, and D-06 scopes this requirement to the credential path plus a
startup warning plus a documented limitation — not to building the store.

**Named trigger for revisiting:** the first deployment that needs more than one replica serving
`AuthPort`-issued tokens (D-09's own wording). At that point the correct move is to add a shared-store
`AuthPort` implementation, not to introduce a parallel identity concept.

**Optional, not required:** a future invariant test could encode the generalized intent — that
`AgentAuthConfig` never depends on a concrete store type, only on `Arc<dyn AuthPort>`. Suggested here,
deliberately not planned into this phase.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Kubernetes Service -> pod set | A request is routed to an arbitrary replica; the credential presented must verify identically on every one of them |
| Operator intent -> ConfigMap flag | Flipping the bearer-token flag moves the deployment from a replica-safe credential path to a per-process one, with no other signal than the startup log |
| Config -> auth state | `build_auth_config` is the single seam translating `AuthConfig` into the web layer's `AgentAuthConfig`, including the fail-closed refusal |
