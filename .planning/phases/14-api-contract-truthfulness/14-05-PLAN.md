Status: `Accepted`, dated the day the plan executes.

Context: build it from the tree, in the ADR-0035 style of numbered measured facts each carrying the
command or `file:line` that produced it. State: Milestone 9 Epic 5 §6.1's own recorded trade-off, that
tokens validate against an in-process store so a multi-process deployment would later need a shared
one, and that validation sits behind `AuthPort` precisely so the store can be swapped without touching
the web layer; the shipped `k8s/server/deployment.yaml` replica count; and the finding that changes
the shape of the question — `k8s/server/configmap.yaml` disables the bearer-token verifier and
authenticates with static API keys sourced from a Secret, which are byte-identical in every pod, so
the correctness edge is reachable only when an operator flips that flag. Name the failure mode
precisely: a token issued by one pod does not verify on another, so authenticated requests fail
non-deterministically depending on which pod they land on. State clearly that this is a correctness
question, not a scaling optimisation.

Also correct WEB-02's own manifest citation in this record (D-08): the requirement names the root
`k8s/deployment.yaml` and `k8s/service.yaml`, but the Milestone 12 Epic 7 artefacts it describes are
`k8s/server/deployment.yaml` and `k8s/server/service.yaml`. Record why the root manifest is
deliberately out of scope — it runs a placeholder image under a sleep command with its probes
commented out, so nothing in it can issue or verify a token — and note that plan 14-07 applies the
dated correction banner to WEB-02 itself.

Decision (D-06): the shared-store requirement attaches to the `AuthPort` credential path, not to the
replica count, and the replicas stay as shipped. **State the deviation as a deviation.** WEB-02's
done-when offers exactly two exits — pin the replica count to one with the reason recorded, or build a
shared-store `AuthPort` and prove a cross-instance token verification — and this record takes neither.
Give the reasoning in full: pinning would degrade a working deployment to guard a code path the
shipped configuration has turned off, and building the store is deferred by D-09. What is delivered
instead is what ROADMAP criterion 2's second clause actually asks for — the deployment artefacts and
documentation saying the limitation exists — realised as the unconditional startup warning (D-07)
plus the three artefacts plan 14-04 landed. Record why the warning is unconditional on the store being
wired rather than conditional on an observed replica count: a pod cannot read its own replica count
without Kubernetes API access, and adding a Kubernetes client to make the warning smarter was
rejected. Record that a new opt-in refuse-to-start flag was also considered and rejected as a knob
whose only job is to be typed once.

Record the deferral with its named trigger (D-09), following ADR-0035: the reintroduction condition is
the first deployment that needs more than one replica serving `AuthPort`-issued tokens, and Milestone 9
§6.2's statement that the port was designed to permit exactly this swap means the future work is an
adapter, not a redesign. State deliberately that this is **not** recorded as a permanent property of
the topology — that is ADR-0039's treatment of a different question — because the capability is wanted,
just not now.

Considered Options, as single-physical-line bullets: attach the requirement to the credential path,
warn at startup and document the limitation (chosen); pin the replica count to one (rejected —
degrades a correct deployment to guard a disabled path); build the shared-store `AuthPort` now
(deferred under D-09 with the named trigger, not rejected); add an opt-in refuse-to-start flag
(rejected); make the warning conditional on an observed replica count (rejected — requires Kubernetes
API access a pod does not have).
