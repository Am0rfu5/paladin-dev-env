<objective>
Cover `user_service.rs`'s registration, validation, password-hashing and notification-dispatch paths
— the first half of DEFER-02's scope, and the half that sits on this workspace's authentication
surface.

Two recorded premises are stale and are worked around rather than through. The register profiles this
file at 488 LOC and ~4.23% coverage; it ships at **583 lines** and already carries five
`#[tokio::test]`s built on real in-memory adapters. And the split-versus-test collision the register
describes as live is **dissolved**: ADR-0034 **withdrew** the D2 split — the split is owned by nobody,
the full relocation by the run-3 v2 tech-debt item, and the tests by this requirement. This plan sizes
against the unsplit file and does not re-open the sequencing question.

The existing fixture uses **real in-memory adapters**, not mocks — `SqliteUserRepository` over
`sqlite::memory:`, `SystemLogAdapter::new_for_test`, a real `NotificationService`, and
`InMemoryTokenAuthAdapter`. Extend that fixture; do not replace it with doubles. This is exactly why
D-10 expects `MockUserRepository` to prove unnecessary.

Purpose: the authentication-adjacent module stops being a coverage blind spot.
Output: registration, validation and dispatch tests in the existing co-located test module.

**Executor note:** `.planning/config.json` sets `workflow.worktree_skip_hooks: true`. Honor it.
**Project convention:** TDD Red-Green-Refactor is the house rule, but the behaviour under test here
already ships and is correct. These tests characterize existing behaviour. Where a test fails, the
default assumption is that the test's expectation is wrong — investigate before changing production
code, and if production code genuinely is wrong, surface it rather than silently fixing it inside a
coverage plan.
</objective>

    Cover the registration and validation half of DEFER-02's stated scope:

    **Happy path.** A valid registration persists a user, returns `Ok`, and the returned user's stored
    password field is an argon2 PHC-format hash rather than the submitted password. Assert the hash is
    verifiable by the service's own `verify_password` against the original password, and that it does
    **not** verify against a different password. Do not compare hash strings directly and do not
    re-implement any comparison — call the service's existing verification path, which is what
    performs the constant-time comparison.

    **Duplicate detection.** Registering a second user with a byte-identical email is rejected with
    the `EmailAlreadyExists` variant. Separately, register a second user whose username differs from
    an existing one only in letter case, and assert the **observed** verdict — this file's duplicate
    check is on email, so whether a case-variant username is accepted is a real property of the
    system that the test should pin down rather than presume.

    **Idempotency.** Calling `register_user` twice with the same request leaves exactly one user
    persisted (assert via `count_users` or `list_users`), and the second call returns a duplicate
    error rather than creating a second record.

    **Empty and whitespace inputs.** An empty username, a whitespace-only username, an empty email and
    an empty password each produce a `UserError` variant rather than an `Ok` or a panic. Assert the
    specific variant each produces. Where a case currently succeeds, assert that it succeeds and
    record it as a finding in the plan summary rather than changing production behaviour to make the
    test read better.

    **Unicode.** A username containing multi-byte Unicode characters. `validate_username` applies one
    length rule; read the implementation and assert against the rule it actually applies — byte length
    or character count — with a test case that distinguishes the two, so the file's real behaviour is
    pinned rather than an assumption about it.

    **Invalid email formats.** At least three distinct rejection shapes drawn from what `Email::new`
    actually validates, each asserting the resulting variant.

    Every test asserts on behaviour, not merely on the absence of a panic. A test that calls a
    function and asserts nothing about the result raises the coverage number while proving nothing,
    which is precisely the failure this phase exists to end.

    Name tests in the existing snake-case behavioural style (`delete_user_removes_the_user` is the
    model) — the name states the behaviour, not the function under test. No `unwrap()` in production
    code; inside `#[cfg(test)]` the existing module already uses `.unwrap()` on fixture setup, so
    match its style there rather than diverging.
  </action>
