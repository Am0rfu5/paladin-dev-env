<objective>
The blocking evidence gate for the tracer. Three of this phase's seven success criteria have **no
local proxy at all**; SC1 and SC5 are two of them. Their evidence is produced by observing a real CI
run, not by running a command against the working tree, and **D-00e** requires that evidence be
recorded verbatim together with the exact command that produced it.

This plan does one more thing that the rest of the phase depends on. **D-05** names its
required-check set in prose — thirteen display names, one of them a ten-leg matrix and one of them a
two-leg matrix. GitHub matches required status checks by **context name**, and a job whose `name:`
carries no matrix interpolation renders the same context name for every leg. Rather than guess which
strings GitHub actually reports, this plan reads them back from a real run and hands the literal list
to plan `15.1-04`. That also surfaces, by count, any name reported more than once — the same defect
class **D-09** exists to close, detected empirically instead of by inspection.

Purpose: turn "the tracer should work" into "the tracer was observed working, here is the run".
Output: one evidence record; no source file changes.

**Where this sits in the cutover.** **D-02** fixes a strict order — fix CI, then fast-forward, then
protect — and states that each step is only safe once the previous holds. This plan is the proof that
step 1 holds. Nothing downstream may proceed on the assumption that it does. Under **D-01** the trunk
that receives this work is the branch currently doing integration duty; the fast-forward that makes
`main` that trunk is plan `15.1-07`, deliberately after this gate, not before it.

**Executor note:** `workflow.worktree_skip_hooks: true` is set; bypass the pre-commit hook when
committing the evidence record, which is a Markdown file and would otherwise cold-compile the Rust
workspace. Run no `cargo` command in this plan.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local executor → GitHub REST API | `gh api` reads run and check-run metadata using the authenticated user's token |
| Local executor → `origin` | A branch is pushed and a pull request is merged into the branch currently serving as trunk |
| Observed CI output → phase record | Command output is transcribed into a governance artefact that a later decision is based on |

| T-15.1-06 | Tampering | A security-relevant control believed active but never observed | high | mitigate | This is the phase's central failure mode restated at its own scale: the two rulesets have been committed and unapplied since 2026-05-31 precisely because nobody read back the live state. This plan applies the countermeasure to the tracer — no CI claim is accepted from "the file says so"; every claim names the `gh` invocation that produced it, per D-00e. |

## Flagged planner assumptions

- **The required-check context names are read back, not derived.** D-05 names `Unit Tests` as a
  single entry covering both matrix legs, but that job's `name:` carries no matrix interpolation
  while its ten-leg sibling's does. Whether GitHub reports one context or two for that job is a
  behavioural question this plan answers empirically instead of the planner asserting it. Plan
  `15.1-05` carries the disambiguation task that acts on whichever answer comes back.
- **`--paginate` is specified on the check-runs query.** A full run of this pipeline reports more
  than thirty check runs once the ten-leg matrix is counted, and an unpaginated read would silently
  truncate the list that becomes the required set.
