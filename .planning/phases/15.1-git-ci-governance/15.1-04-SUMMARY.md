### D-05 — the required-check set, and why it uses the live evidence in this execution's prompt instead of D-05's prose or 15.1-CI-EVIDENCE.md

The task's `<read_first>` pointed at `15.1-CI-EVIDENCE.md`'s context-name inventory (§3) as "the source of truth for every context string." That inventory is explicitly a **push-event** capture (45 names, from `gh api .../check-runs` against a push-triggered commit), and the evidence file's own Finding A says so directly: *"GitHub branch protection gates on the `pull_request` event, not push... Plan `15.1-04` must independently obtain a `pull_request`-event context list ... and must not treat the list in this record as complete for that purpose."*

This execution's prompt (`<live_context_evidence>`) supplied exactly that: a **pull_request-event** capture — 51 job contexts / 50 unique, aggregated per-run across the five workflows that fire on `pull_request` for PR #29 (`ci.yml`, `feature-flags.yml`, `pre-commit`, `Integration Tests`, `Docs`), with the instruction *"Use THIS, not D-05's prose list, and not the push-event list in `15.1-CI-EVIDENCE.md`."* This is the authoritative source used for every pinned context below.

**Consequence for Task 1's embedded automated verify.** Task 1's second `<automated>` verify block asserts every pinned context is a literal substring of `15.1-CI-EVIDENCE.md`. Three of the 43 pinned contexts — `Build MDBook`, `Docker Integration Tests`, `End-to-End Tests` — are real, empirically-observed `pull_request`-event contexts (present verbatim in the live evidence list) that do **not** appear in `15.1-CI-EVIDENCE.md`'s push-event capture, because the `Docs` workflow and part of the integration-test surface only fire on `pull_request`, not on the push this phase's earlier evidence run captured. This is a genuine gap in the plan's baked-in verify script, not a defect in the payload: pinning these three is *more* correct (every job except the two D-05 exclusions is meant to be required), and omitting them would leave real `pull_request`-triggered CI jobs with no merge-gate signal. Ran an adapted verification during execution — reproduced the live evidence list from this execution's prompt as a local reference file and confirmed all 43 pinned contexts occur verbatim in it (`live_pr_contexts.txt`, 50 unique lines) — before committing. Documented here per Rule 1 (auto-fixed bug: the plan's automated check tests against a source the plan's own evidence record says is incomplete for this purpose) rather than silently dropping the three contexts to make a stale check pass.

### D-07 — zero approvals, bypass removed entirely

`required_approving_review_count` changed from `1` to `0`. `bypass_actors` removed entirely (the key is now absent from the file, not narrowed to a pull-request-scoped mode) — per the task's explicit instruction that removal, not narrowing, is the decision: a narrowed bypass would still let the sole admin skip the required checks inside a pull request, which defeats the same gate this plan exists to make real. The `pull_request` rule itself, and its other four parameters (`dismiss_stale_reviews_on_push`, `require_code_owner_review`, `require_last_push_approval`, `required_review_thread_resolution`), are byte-identical to their pre-edit values — a PR is still mandatory.

### D-08b — release-branch pre-emption and the retained tag bypass

`protect-release-branches.json` is new: `target: branch`, `refs/heads/release/*`, `deletion` + `non_fast_forward` + `pull_request` (0 approvals, mirroring the trunk posture), **no** `required_status_checks` rule and **no** `bypass_actors`. The ref class has zero members today, so no job mix can be measured for it yet — adding a required-check set later is a one-line change, matching the reversibility D-05 already claims for the trunk file.

`protect-release-tags.json` is unmodified — verified via `git diff` producing empty output. Its `bypass_actors` entry stays because that ruleset restricts tag *creation*; without a bypass actor able to create a matching ref, no release could ever be cut. This is the deliberate opposite of the trunk-ruleset bypass removal: one gates a merge and must not be bypassable, the other gates a creation and must be. Recorded explicitly here so a later reader does not mistake the surviving tag bypass for the same defect just removed from the trunk file.

**Ordering constraint for plan `15.1-08` (repeated from the plan, load-bearing for apply order):** `protect-release-branches.json` must be applied **after** the existing `release/v0.7.0` branch is retired at plan `15.1-07`, not before. Applying it first would put that branch's own deletion under this new ruleset's `deletion` rule, requiring a bypass actor — which this ruleset grants none of — to execute what should be a one-time retirement.
