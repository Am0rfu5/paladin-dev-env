<objective>
Close SC6 — no CI job is dark — by fixing and relocating the one job that genuinely is, per **D-08**,
and by recording the disposition of the three others that merely look like it.

The benchmark job is dark twice over. Its condition admits a scheduled event, but the workflow that
contains it declares no schedule trigger at all, so that half of its condition is unreachable and the
job is dispatch-only. And the one time it *was* dispatched it failed, panicking at settings load,
because the base configuration file it needs is gitignored and therefore absent on a bare runner. The
compile-only benchmark gate that a previous phase added cannot catch this: compiling a benchmark
structurally cannot detect a runtime panic, which is worth recording as a stated limit of that gate.

The fix already exists in the tree. A sibling non-blocking signal job seeds the base configuration
from the committed test configuration and then runs four bench targets with the test environment
selected, and it succeeds. **D-08** copies that whole step — the seeding *and* the four invocations —
rather than debugging the panic independently, and gives it a weekly cadence plus on-demand dispatch
in a dedicated workflow file. Not a schedule key on the pipeline: only a handful of the pipeline's
jobs carry conditional gates, so a cron there would run everything weekly, including the emulated
container build measured at over an hour.

Purpose: the benchmark suite stops being a job nobody has seen succeed.
Output: one new scheduled workflow; the dark job removed from the pipeline; every remaining job's
reachability recorded.

**Executor note:** `workflow.worktree_skip_hooks: true` — bypass the hook when committing. Do not run
`cargo bench` locally as a verification: it compiles and executes the whole benchmark set and is the
documented executor-stall hazard here. The job body is copied from a step already observed succeeding
in CI; its runtime proof is the dispatch described in the acceptance criteria, not a local run.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Scheduled runner → repository contents | A cron-triggered workflow executes repository code on GitHub's runners with no human in the loop |
| Runner filesystem → configuration loader | The job writes a base configuration file into the workspace before the benchmarks read settings |
| CI runner → GitHub Actions marketplace | Checkout, toolchain, cache and artefact-upload actions execute in the new workflow |
