<objective>
Step 3 of **D-02**'s cutover, and the close of SC2: apply the protection payloads to the live
repository and record what the server said.

**D-06** is emphatic about why the phase applies them itself rather than merely preparing them.
Preparing-only was rejected as reproducing the exact failure this phase exists to fix — the two
rulesets have been committed and unapplied since they were authored, and the reason nobody noticed
is that nobody ever read the live state back. So: send the payloads, then re-read the repository's
ruleset collection and record the response verbatim as the **D-00e** evidence SC2 closes against.

**D-08b** decides what gets covered: the trunk, plus a pre-emptive ruleset over the release-branch
ref class so a future backport line is born protected. The tag ruleset keeps its bypass, because it
restricts tag *creation* — removing that bypass would make cutting any release impossible. That
asymmetry must survive application and be verified on the server, not merely in the files.

This is an **outward-facing change to a real repository**, which is why the checkpoint below is
mandatory rather than advisory. A ruleset can be deleted through the same API, so the change is
reversible — but only if the rollback command is written down, which this plan requires.

Purpose: protection stops being a file and starts being a gate.
Output: three applied rulesets and one verbatim evidence record.

Run no `cargo` command. Note that from the moment the trunk ruleset applies, the evidence commit
itself must reach the trunk through a pull request with all required checks green; plan for that
rather than being surprised by it.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15.1-37 | Tampering | A request that fails on token scope while the session proceeds as if it succeeded | high | mitigate | The action requires checking the exit status and capturing the body of every request before the next is issued, and halting on the first failure. D-06's mandate to record the response verbatim *is* the mitigation here — a security control believed active but never applied is the precise failure this whole phase exists to close, and it has already happened once in this repository. |
| T-15.1-38 | Elevation of Privilege | Applying a payload that grants an always-on bypass over required checks | high | mitigate | The payload was corrected at plan `15.1-04` and the applied state is re-verified here against the server rather than against the file. | T-15.1-39 | Spoofing | A ruleset that exists but matches no ref | high | mitigate | Existence and evaluation are checked separately: the collection read proves it exists, the branch-rules read proves it evaluates against the trunk. A wrong ref condition would otherwise produce a green-looking ruleset list over an unprotected branch. |
| T-15.1-40 | Elevation of Privilege | Removing the tag ruleset's bypass by symmetry with the trunk edit | high | mitigate | Verified on the server, not only in the file: an acceptance criterion asserts the applied tag ruleset still carries a bypass actor. | T-15.1-42 | Repudiation | An irreversible-in-practice change whose rollback is undocumented | medium | mitigate | The exact deletion command with its server-assigned identifier is a required section of the evidence record. | T-15.1-43 | Information Disclosure | API responses transcribed into a committed record | low | accept | The repository is public and ruleset configuration is not secret. Transcribe response bodies for ruleset and rules endpoints only; never transcribe authentication status output, which can name token scopes and account details beyond what this record needs. |
