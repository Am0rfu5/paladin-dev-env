## Phase Boundary

Make the branching model, the branch protection rules and the CI trigger surface agree with each
other, and write that agreement down — so a broken workflow cannot survive undetected, a release
tag cannot be cut from unmerged work, and creating a feature branch is a normal thing to do rather
than something CI fails on.

**Seven success criteria (ROADMAP), regrouped into five deliverable classes:**

1. **A branching model that is chosen, applied and documented** (SC4) — GitHub Flow on `main`,
   the `main`/`develop`/`release/v0.7.0` tangle resolved, and the version/naming policy settled.
2. **Protection that actually gates** (SC2) — the two committed-but-never-applied rulesets applied
   to the live repository with a required-check set derived from the 21 jobs that exist today, and
   the API response recorded as evidence.
3. **A trigger surface that cannot go dark** (SC1, SC6) — `push: ['**']` everywhere, one
   consolidated CI workflow, the one genuinely dark job fixed and given a cadence, and the policy
   recorded and guarded.
4. **CI that a new branch does not break** (SC5) — the `--offline` + no-`restore-keys` failure
   fixed at its class, not just at its instance.
5. **The record made true** (SC3, SC7) — the stale `docs/BRANCH_PROTECTION.md` pointers redirected,
   the appendix page made current, and `RUSTSEC-2026-0249` given a governed disposition.

### The branching model (SC4)

- **D-01: GitHub Flow on `main`.** `main` is the trunk and receives every merge via PR.
  `feature/**` and `fix/**` are short-lived. Releases are **tags cut from `main`**, not branches.
  `release/0.x` branches exist only to backport fixes to an already-published line, never as a
  staging area. `develop` is retired. `release/v0.7.0` is retired once its content is on `main`.
  **GitFlow was rejected on evidence, not taste**: Atlassian now documents it as a legacy strategy
  superseded by trunk-based workflows, and — decisively for the user's stated goal — an integration
  branch makes the CI-exclusive suites (Docker, kind, Redis/MinIO integration) run *later*, not
  earlier. Keeping `release/**` as the integration branch was rejected because it contradicts the
  invariant `verify-tag-source` and `make release` already enforce.
  — **Reversibility:** costly — the branching model is stamped into six workflows' trigger lists,
  two rulesets, the release guard, the Makefile and two documentation pages; reversing it means
  touching all of them and re-deriving the required-check set.

- **D-02: The cutover is strictly ordered — fix CI, then fast-forward, then protect.**
  (1) Land D-10's cache fix so a fresh branch goes green; (2) fast-forward `main` to
  `release/v0.7.0` and retire `develop`; (3) apply the rulesets with D-05's required-check set.
  Each step is only safe once the previous holds — protecting `main` with a required check that
  fails on every dependency change would lock the repository against itself. The phase's remaining
  work then lands as PRs into `main`, dogfooding the model before the phase closes.
  — **Reversibility:** one-way at step 2 — the fast-forward moves a published default branch by 921
  commits; undoing it means a force-push to `main`, which the ruleset applied at step 3 forbids.
  **`gsd-planner` must carry this into a `checkpoint:decision` before the fast-forward task.**

- **D-03 — a match-all push branch filter on every workflow that takes a push trigger.** The
  filter is `push: branches: ['**']`. It matches every
  branch and still excludes tags, so `release.yml`'s `v*.*.*` trigger is unaffected. The existing
  `concurrency` groups with `cancel-in-progress` absorb the duplicate push+PR runs, exactly as the
  current comments already claim they do. Branch **naming** stays a documented human convention,
  deliberately not a CI gate. Rejected: enumerating sanctioned prefixes in six files, because the
  next unsanctioned prefix someone invents is dark again — which is finding 3's failure, twice.
  **Two deliberate exceptions, both recorded in D-09's table:** `docs.yml` keeps `push: [main]`
  because its `deploy` job publishes to GitHub Pages; `release.yml` stays tag-triggered.
  — **Reversibility:** reversible.

- **D-04: The branching model is documented in a new `docs/src/contributing/branching-model.md`.**
  Developer-facing: how to branch, what runs when, how a change reaches `main`.
  `docs/src/appendix/branch-protection.md` stays the admin/enforcement page and gets a currency
  pass (D-12). **No root-level `docs/BRANCH_PROTECTION.md` is reintroduced** — D-13 of Phase 15
  declined to reintroduce root files Milestone 11 deliberately removed, and finding 2 shows this is
  the identical case. Add the new page to `docs/src/SUMMARY.md` under Contributing.
  — **Reversibility:** reversible.

### What "protected" means (SC2, SC3)

- **D-05: The required-check set is every job except `Docker Build` and `Kubernetes Smoke Test`.**
  Required: `Code Quality`, `Workflow Lint`, `Security Audit`, `License & Dependency Policy`,
  `OSV Scanner`, `API Surface Tracking`, `Unit Tests` (both matrix legs), `Example Muster (Feature
  Matrix)`, `Crate Isolation` (all ten legs), `Integration Tests`, `Coverage`, `CLI Snapshot
  Tests`, `Benchmark Compile Check`. Measured critical path ≈ 7 minutes (slowest required job:
  Integration Tests, 398s). **Docker Build measured 3762s — 62.7 minutes**, the entire run's
  critical path, because it builds `linux/amd64,linux/arm64` with arm64 under QEMU; combined with
  the committed ruleset's `strict_required_status_checks_policy: true` that would serialize every
  merge behind an emulation run. Both still run on every push and PR — they simply do not block the
  merge button. The alternative (take up the native-arm64 rework so Docker could join) was offered
  with its scope cost stated and declined.
  — **Reversibility:** reversible — adding a context to the ruleset later is a one-line change.

- **D-06: The phase applies the rulesets itself, behind a blocking checkpoint.** It also records
  the API
  response verbatim. Update the two JSONs with D-05's contexts and D-07's parameters; present the
  exact payload and required-check list at a `checkpoint:decision`; `POST` via `gh api`; then
  re-read `gh api /repos/DF3NDR/paladin-dev-env/rulesets` and record the response verbatim as the
  D-00e evidence SC2 closes against. **Preparing-only was rejected as reproducing the exact failure
  this phase exists to fix** — the rulesets have been committed and unapplied since 2026-05-31.
  `gh auth status` reports account `Am0rfu5` with repo `admin: true` (verified 2026-08-13); note
  that flag reflects the *user's role*, and the fine-grained PAT additionally needs
  `Administration: write`, which only a write attempt proves.
  — **Reversibility:** reversible — a ruleset can be deleted via the same API. But it is an
  **outward-facing repository-configuration change**, which is why the checkpoint is mandatory
  rather than advisory.

- **D-07 — no required approving review, and the always-on Admin bypass is removed.**
  The ruleset sets `required_approving_review_count: 0`.
  A PR stays mandatory — checks must pass, force-push and deletion stay blocked — but no second
  human is needed. **The committed ruleset is self-defeating as written:** `Am0rfu5` is the sole
  collaborator (verified via the collaborators API), GitHub forbids self-approval, so
  `required_approving_review_count: 1` is only satisfiable through the `bypass_actors` Admin entry
  with `bypass_mode: always` — and that bypass skips the **required status checks** too. As
  committed, applying it would leave SC2's own diagnosis ("no check can block anything") true for
  the only active committer. Removing the bypass is what makes the gate gate.
  — **Reversibility:** reversible.

- **D-08b — protection covers `refs/heads/main` plus a pre-emptive release-branch ruleset.**
  That second ruleset targets `refs/heads/release/*`.
  Under D-01 `main` *is* the integration branch, so SC2's "main and the integration branch" is
  satisfied by `main`; `release/*` is the only other ref class that will ever hold shipped code, and
  protecting it now means a future backport branch is born protected. **`protect-release-tags.json`
  keeps its Admin bypass** — it restricts `refs/tags/v*` **creation** to bypass actors, so removing
  the bypass there would make cutting any release impossible. This asymmetry is deliberate and must
  be stated in the ruleset JSON and in D-12's page.
  — **Reversibility:** reversible.

### The trigger surface and the dark jobs (SC1, SC6)

- **D-08: `Performance Benchmarks` is fixed and moved to a weekly `benchmarks.yml`.** Add
  `env APP_ENV=test`, widen it to the same four bench targets `benchmark-regression-signal` already
  uses, and give it `schedule` (weekly) + `workflow_dispatch` in a **dedicated workflow file**.
  **Not a `schedule:` key on `ci.yml`** — only four of its 21 jobs carry an `if:` gate, so a cron on
  `ci.yml` would run the entire pipeline weekly including Docker's 63 minutes. The fix is one line:
  finding 8 shows `benchmark-regression-signal` already runs
  `env APP_ENV=test cargo bench --bench config_benchmarks -- --noplot` successfully, while the
  `benchmark` job runs bare `cargo bench` and panics at `benches/config_benchmarks.rs:7`.
  — **Reversibility:** reversible.

- **D-09: `integration-tests.yml` is consolidated into `ci.yml` and the file is deleted.** Move the
  broad `cargo test --workspace --features integration-tests -- --test-threads=1` run into `ci.yml`'s
  `integration-tests` job, keep one `Kubernetes Smoke Test`, bring `docker-integration` across, and
  relocate the daily cron alongside `benchmarks.yml`. **This is a prerequisite for D-05, not a
  cleanup**: finding 6 shows both workflows emit the display names `Integration Tests` **and**
  `Kubernetes Smoke Test`, and GitHub matches required status checks by context *name* — so
  requiring `Integration Tests` while two different jobs produce it is ambiguous. It is the same
  defect class as the two identically-named `Security Audit` jobs Milestone 10 shipped and Phase 12
  closed. Consolidation also gets the **broad** integration suite running on every branch push under
  D-03, which today runs only on PR and a daily cron — directly serving the early-signal goal.
  — **Reversibility:** costly — undoing means re-splitting a workflow and re-deriving the
  required-check contexts, which are name-matched.

- **D-09b: The trigger policy is a table in `branching-model.md`, backed by a guard script.** That
  script is `scripts/check-workflow-triggers.sh`. Record workflow × trigger × branch × rationale, and have
  the script parse every `.github/workflows/*.yml` `on:` block and fail on drift — the same
  register-plus-script shape as `SECURITY-EXCEPTIONS.md` + `scripts/check-advisory-register.sh`,
  which was observed passing on run `31727496744` (*"6 workflow file(s) scanned, 117 run step(s)
  examined"*). Wire it into the same job. **The case it actually catches** is a *new* workflow added
  with no policy entry, or a branch filter quietly reintroduced — `actionlint` validates syntax, not
  intent, and nothing else in the repo would notice.
  — **Reversibility:** reversible.

### CI health and the record (SC5, SC7, SC3)

- **D-10 — `Swatinem/rust-cache@v2` repo-wide, plus an explicit fetch before the offline builds.**
  The added step is `cargo fetch --locked`, ahead of the four `--offline`
  builds. Replace the 25 hand-rolled key-only cache blocks (finding 9) with the action that
  handles keys, `restore-keys` and pruning correctly, and add an explicit `cargo fetch --locked`
  step before the four `--offline` invocations so the flag **keeps its hermetic meaning** — it
  asserts nothing unexpected is pulled during the build — rather than being deleted. **`restore-keys`
  alone would not have fixed this**: a fallback cache restores an *older* registry, which by
  definition lacks the newly-added crate, so `--offline` would still fail on `adler2`. Scoping the
  fix to the `examples` job alone was rejected: 22 other jobs keep cold-rebuilding on every
  dependency change, now paid on every required check, and the broken pattern stays in the file as
  the thing to copy.
  — **Reversibility:** reversible.

- **D-11: `RUSTSEC-2026-0249` is suppressed and registered; the deny gate stays hard.** Add it to

  scope reasoning of the existing `RUSTSEC-2026-0194`/`-0195` rows (*"transitive via

  appendix is archive material: the split-by-page-type option was offered and declined for exactly

  **Concrete scope:** redirect `release.yml:65` and `Makefile:506,514` from the non-existent
