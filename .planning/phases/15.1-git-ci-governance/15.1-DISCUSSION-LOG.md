## Branching model & `main`'s 921-commit gap

### Q1 — Which branching model does the project standardize on?

| Option | Description | Selected |
|--------|-------------|----------|
| main as trunk, short-lived feature/** | main receives PR merges continuously; release/** cut only at release time; revives the two main-keyed dark jobs for free | ✓ (after discussion) |
| main + develop, GitFlow proper | develop as long-lived integration branch; already exists on origin and is already named in all six workflows' trigger lists | |
| Keep release/** as the long-lived integration branch | Document current practice; rename to match the 0.8.0 manifests | |

**User's choice:** Free-text first, then "Go with your recommendation."

**Notes:** The user did not pick from the list initially. They raised a distinct concern: *"It is
also important to consider the importance of running a full test suite, particularly tests that are
not available locally such as the Docker build tests, when new feature/bugfix branches are
completed… We may want to build out releases with various features/bugfix with each feature or
bugfix running the tests that are exclusive to the CI Pipeline as early as possible… In general we
want to follow whatever is considered best practice for an open source project like this."*

Three things were checked and reported back before recommending:

1. **The early-signal goal is already structurally met.** `docker:766`, `kubernetes-smoke:888`,
   `integration-tests:400`, `coverage:515`, `cli-tests:694` and `bench-check:730` carry no `if:`
   gate, so every CI-exclusive suite already runs on the first push to a `feature/**` branch. The
   blocker is the `examples` cache failure and the absence of any required check — not the model.
2. **An integration branch makes those suites run *later*, not earlier**, which cuts against the
   user's own stated priority.
3. **Best practice was researched rather than asserted** — Atlassian documents GitFlow as a legacy
   strategy superseded by trunk-based workflows, with the honest caveat that GitFlow retains an
   argument for versioned releases with external contributors; the Rust/crates.io resolution is
   GitHub Flow, which is what the existing `verify-tag-source` guard and `make release` already
   assume.

The decisive fact: `git merge-base --is-ancestor origin/main origin/release/v0.7.0` returns true, so
the 921-commit reconciliation is a **fast-forward with zero conflicts**. The user then approved the
recommendation.

## What "protected" means + the admin handoff

### Q1 — Which checks become required to merge into main?

| Option | Description | Selected |
|--------|-------------|----------|
| Everything except Docker Build and Kubernetes Smoke | ~7 min critical path; the two container jobs still run but do not block | ✓ |
| All of them, Docker Build and Kubernetes Smoke included | Strongest gate; ~63 min per PR, serialized by strict_required_status_checks_policy | |

**Notes:** Decided against measured data rather than intuition — Docker Build 3762s versus a

free `ubuntu-24.04-arm` runners are genuinely available; the scope cost of taking that on was stated
plainly and the option declined.

## Trigger-surface policy & the three dark jobs

### Q1 — What happens to the Performance Benchmarks job?

| Option | Description | Selected |
|--------|-------------|----------|
| Fix it and move it to its own weekly benchmarks.yml | env APP_ENV=test, widen to four bench targets, schedule + dispatch in a dedicated file | ✓ |
| Delete it | benchmark-regression-signal already runs a strict superset on every PR | |
| Fix it and leave it dispatch-only, recorded as deliberate | Minimal change; arguably neither a cadence nor removal | |

**Notes:** Diagnosed before asking. `ci.yml`'s `on:` has no `schedule:` key at all, so the job's
`schedule` condition is unreachable; its single dispatch (run `31708837418`) panicked at
`benches/config_benchmarks.rs:7:47` on `Settings::new().expect("load settings")`. The fix was found
in the neighbouring job: `benchmark-regression-signal` already runs
`env APP_ENV=test cargo bench …` successfully. Also recorded: `bench-check` passed in the same run,
because `cargo bench --no-run` compiles and cannot catch a runtime panic. Adding `schedule:` to
`ci.yml` was rejected because only 4 of 21 jobs carry an `if:`, so a cron would run Docker's 63
minutes weekly.

### Q2 — What happens to integration-tests.yml and its two name collisions with ci.yml?

| Option | Description | Selected |
|--------|-------------|----------|
| Consolidate into ci.yml and delete the file | Clears both collisions; broad integration suite starts running on every push | ✓ |
| Keep the file, rename its jobs to disambiguate | Surgical; broad suite still never runs on a feature-branch push | |
| Keep the file but move the broad suite into ci.yml | Split by cost; two workflows still to keep in sync | |

**Notes:** Found while checking whether the two workflows were duplicates. They are not —
`ci.yml`'s job runs two narrow `--ignored` targets, `integration-tests.yml:113` runs the whole
`--features integration-tests` workspace suite. But both emit the display name `Integration Tests`,
and both emit `Kubernetes Smoke Test`, and GitHub matches required checks by context name — so this
directly threatened the required-check set agreed in the previous area.

## New-branch cache miss + the two record fixes

### Q1 — How does the examples job stop failing, and how far does the cache fix reach?

| Option | Description | Selected |
|--------|-------------|----------|
| Swatinem/rust-cache repo-wide, plus cargo fetch --locked before the offline builds | Fixes the fatal case, cuts wall-clock on every required check, removes 25 hand-maintained blocks | ✓ |
| Minimal: add restore-keys everywhere and drop --offline | Smallest diff; loses --offline's hermetic guarantee | |
| Fix the examples job only | Tightest scope; 22 other jobs keep cold-rebuilding | |

**Notes:** The audit found **25 of 26** `actions/cache` blocks with no `restore-keys`, and only four
`--offline` invocations, all in the `examples` job — which is why only that job dies rather than
merely rebuilding cold. It was flagged before asking that `restore-keys` alone would **not** fix it,
since a fallback cache restores an older registry that lacks the newly-added crate by definition.
Also recorded: the failure reproduces on `release/v0.7.0` itself, so SC5's "first run of every new
branch" framing understates it.

### Q2 — How does the phase handle a new upstream advisory blocking all merges?

| Option | Description | Selected |
|--------|-------------|----------|
| Accept it — register the smartstring row and keep the gate blocking | The governance model ADR-0024/ADR-0036 deliberately chose | ✓ |
| Split the classes: vulnerability blocks, unmaintained warns | Mirrors cargo audit's own behaviour; contradicts M10 Epic 4 FR-1 step 5 | |
| Keep it blocking, plus a scheduled advisory-refresh early warning | Additive; another scheduled workflow | |

**Notes:** The advisory ID `RUSTSEC-2026-0249` was recovered from CI logs rather than guessed — it
appears nowhere in the tree. The dependency chain
`smartstring ← rxml ← minidom ← rust-s3 ← paladin-storage` was traced from `Cargo.lock`, showing the
same upstream as the already-registered quick-xml rows. The new operational edge — that making the
deny job a required check means a newly-published upstream advisory blocks all merges with no repo
change — was raised explicitly and accepted rather than discovered later.
