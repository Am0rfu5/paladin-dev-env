### `scripts/check-workflow-triggers.sh` (NEW — guard script)

**Primary analog:** `scripts/check-workflow-suppressions.sh` (structural template — same file type
parsed, same library, same job).
**Secondary analog:** `scripts/check-advisory-register.sh` (contributes only the reporting/exit-code
convention and the "register vs. mechanical-surface" governance shape — it parses TOML, not YAML,
so it is NOT the structural analog RESEARCH.md's `<code_context>` §Reusable Assets implies via
CONTEXT.md's citation. **RESEARCH.md's correction is confirmed correct** by this session's own read
of both scripts.)

**Why `check-workflow-suppressions.sh` wins on structure** (verified by direct read,
`scripts/check-workflow-suppressions.sh:1-100`):
- Parses `.github/workflows/*.yml`/`*.yaml` with PyYAML (`import yaml`), the same file type and
  library D-09b's script needs — `check-advisory-register.sh` parses TOML via `tomllib` instead.
- Already wired into the exact same job (`cargo-deny`, display name `License & Dependency Policy`)
  D-09b targets (verified `ci.yml:132-134`).
- Shares the "report everything, never short-circuit," "no default-empty pass," and "parse
  structurally, never scrape raw text" house rules verbatim in its header comment — the discipline
  D-09b's script must also follow.

**Header/contract block to copy the shape of** (`scripts/check-workflow-suppressions.sh:1-87`):
```bash
#!/usr/bin/env bash
# check-workflow-triggers.sh
#
# The D-09b regression guard: fails if a workflow's `on:` push-trigger branch
# filter drifts from the recorded trigger-policy table in
# docs/src/contributing/branching-model.md, or if a new workflow file has no
# corresponding table row. `check-workflow-suppressions.sh` already proved this
# register-plus-guard shape for advisory-suppression governance; this script
# applies the identical discipline to trigger-surface governance.
#
# This script is offline and makes no network call. It parses workflow YAML
# structurally with PyYAML -- it never scrapes raw file text -- and reports
# every violation it finds rather than stopping at the first. It only reads.
#
# Usage:  ./scripts/check-workflow-triggers.sh [workflows-dir] [policy-table-file]
# Exit:   0 if every workflow file has a table row and every row's recorded
#         trigger surface matches the YAML; non-zero otherwise.

set -euo pipefail

WORKSPACE_ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
WORKFLOWS_DIR="${1:-${WORKSPACE_ROOT}/.github/workflows}"
POLICY_TABLE="${2:-${WORKSPACE_ROOT}/docs/src/contributing/branching-model.md}"

if ! command -v python3 >/dev/null 2>&1; then
    echo "ERROR: python3 is required for YAML parsing." >&2
    exit 1
fi
```

**Core parsing pattern to copy** (`scripts/check-workflow-suppressions.sh:100-133`, the Python3
heredoc idiom — `python3 - "${WORKFLOWS_DIR}" <<'PY' ... PY`):
```python
import glob
import os
import re
import sys

import yaml

workflows_dir = sys.argv[1]

failures = []

files = sorted(
    set(glob.glob(os.path.join(workflows_dir, '*.yml')))
    | set(glob.glob(os.path.join(workflows_dir, '*.yaml')))
)

if not files:
    print('ZERO_FILES')
    print(f'FAIL: no *.yml or *.yaml files found under {workflows_dir} -- a '
          'broken glob or an empty workflows directory is a named failure, '
          'never a silently-empty pass that reports success over nothing.')
    sys.exit(0)
```
For D-09b, replace the `jobs.*.steps[].run` walk with a walk over `data.get("on", {})` — extract
`push.branches` (list or absent, meaning bare) and compare against the policy table row for that

Markdown-table row parser (split each `| ... |` row on `|`, `.strip()` each cell) reading
`branching-model.md`'s trigger-policy table — there is no existing local pattern for this, note it
as the one genuinely new piece.

**Failure-naming convention to copy** (mirrors `CLAUSE1_FAILURES`/`CLAUSE2_LOCATIONS` naming in
`check-workflow-suppressions.sh` and `CLAUSE2_UNCOVERED` in `check-advisory-register.sh`): use
`CLAUSE_UNCOVERED` for a workflow with no table row, `CLAUSE_DRIFT` for a row whose recorded

**Job body to copy verbatim** — confirmed live this session at `ci.yml:1086-1130`
(`benchmark-regression-signal`), re-verified matching RESEARCH.md's citation of `:1108-1130` (job
start shifted slightly, content identical):
```yaml
  benchmark-regression-signal:
    name: Benchmark Regression Signal (Non-Blocking)
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v5

      - name: Install Rust toolchain
        uses: dtolnay/rust-toolchain@stable

      - name: Cache dependencies
        uses: actions/cache@v4
        with:
          path: |
            ~/.cargo/registry
            ~/.cargo/git
            target
          key: ${{ runner.os }}-cargo-bench-signal-${{ hashFiles('**/Cargo.lock') }}

      - name: Run critical-path benchmarks for signal
        run: |
          set -euo pipefail
          mkdir -p benchmark-signal
          LOG=benchmark-signal/criterion-output.log

          # The config benchmarks call `Settings::new()`, which requires a base
          # `config` file. `config.yml` is gitignored (it can hold secrets), so it
          # is absent in CI -- seed it from the committed `config.test.yml` so the
          # benchmark can load settings. APP_ENV=test also overlays config.test.
          if [ ! -f config.yml ]; then
            cp config.test.yml config.yml
          fi

          {
            env APP_ENV=test cargo bench --bench config_benchmarks -- --noplot
            env APP_ENV=test cargo bench -p paladin-battalion --bench battalion_benchmarks -- --noplot
            env APP_ENV=test cargo bench -p paladin-memory --bench garrison_benchmarks -- --noplot
            env APP_ENV=test cargo bench -p paladin-llm --bench llm_serialization_benchmarks -- --noplot
          } | tee "$LOG"
```
**Copy the seeding step (`cp config.test.yml config.yml`), not just `APP_ENV=test`** — RESEARCH.md's
root-cause note (§3) is correct: `APP_ENV=test` only makes `Settings::new()` load an *overlay*;
without a base `config.yml` file present, load still fails on a bare runner. This is the actual bug
at `benches/config_benchmarks.rs:7`'s `Settings::new().expect("load settings")` — confirmed present
in the current job's comment. Use `actions/upload-artifact@v4` for `benchmark-results`/`target/criterion/`
matching the old `benchmark` job's upload step.
