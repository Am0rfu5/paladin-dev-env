## Summary

This phase's deliverables are almost entirely YAML, JSON, shell and Markdown — not Rust — so the
research below is organized around **mechanics that are easy to get subtly wrong**: the exact shape
GitHub's rulesets API expects, what `Swatinem/rust-cache@v2` actually caches versus what the 25
hand-rolled blocks cache today, how a new register-plus-guard script must be built to match the
established local pattern exactly, and the ordering hazards in the fast-forward/protect sequence.

Two established local patterns dominate the mechanics: **`scripts/check-advisory-register.sh`**
(TOML-parsing register-vs-config guard, Python3 + `tomllib`, report-everything-don't-short-circuit)
and — more directly relevant to D-09b — **`scripts/check-workflow-suppressions.sh`** (YAML-parsing
guard over `.github/workflows/*.yml`, Python3 + PyYAML, walks `jobs.*.steps[].run`, already wired
into the `cargo-deny` job and into `Makefile`'s `check-gates`/`test-shell-guards` targets). D-09b's
`check-workflow-triggers.sh` should be built as a structural sibling of the suppressions script, not
the register script — it parses the same file type (workflow YAML) using the same library
(PyYAML, confirmed present: `python3 -c "import yaml"` succeeds, version 6.0), not TOML.

**Primary recommendation:** treat `check-workflow-suppressions.sh` as the literal template for
`check-workflow-triggers.sh` — same header block style, same `WORKSPACE_ROOT`/positional-override
pattern, same Python3-heredoc-with-`sys.argv` structure, same "report every failure, never stop at
the first" discipline, same `Makefile` wiring (`.PHONY` target + `check-gates` inclusion +
dedicated `tests/scripts/*_test.sh` — but wire the test into CI this time; the existing
`test-shell-guards` target for `check-workflow-suppressions_test.sh` is **not** invoked by any
workflow, a gap this phase should not repeat for its own new script).

Nine of CONTEXT.md's `file:line` citations were re-verified this session against the live tree;
one has drifted (`deny.toml`'s advisories block, flagged in Pitfalls below). One new fact not in
CONTEXT.md's twelve findings surfaced during verification: `cargo deny check advisories` also emits
a non-blocking `warning[yanked]` for `spin 0.9.8` — out of this phase's scope (not an advisory, not
gated), but worth a one-line note so a future run doesn't mistake it for a second SC7 blocker.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cargo dependency caching with correct fallback | A hand-rolled `actions/cache@v4` block with `restore-keys` | `Swatinem/rust-cache@v2` | `restore-keys` alone restores an *older* cache that by definition lacks a newly-added crate — the exact SC5 bug. The action implements Cargo-aware key generation (rustc version/host/hash + `Cargo.lock` hash) and its own multi-generation fallback, plus `target/` pruning of stale/incremental artifacts the hand-rolled blocks never clean up |
| Workflow trigger-drift detection | Ad-hoc grep in a pre-commit hook, or trusting `actionlint` | A structural PyYAML guard modeled on `check-workflow-suppressions.sh` | `actionlint` validates syntax, not intent (CONTEXT.md D-09b) — it cannot know that a new workflow *should* carry a policy-table entry, or that a branch filter was quietly reintroduced. A grep-based check is exactly the "scrapes raw file text" anti-pattern both existing guards explicitly reject in their own header comments |
| RustSec suppression governance | A bare comment in `deny.toml`'s `ignore` array | `SECURITY-EXCEPTIONS.md`'s eleven-field register + `check-advisory-register.sh` | A TOML array element can carry a trailing comment but never a queryable owner/review-date/scope/compensating-control field — exactly the gap the register exists to close (`SECURITY-EXCEPTIONS.md:1-9`) |
| Applying a GitHub ruleset from the UI | Manual "Import a ruleset" click-through | `gh api --method POST ... --input <file>.json` | The UI path is Option A in `docs/src/appendix/branch-protection.md` and works, but D-06 requires the exact request/response recorded verbatim as evidence (D-00e) — only the `gh api` invocation produces a machine-transcribable request and response |

**Key insight:** Every "don't hand-roll" item in this phase already has a working sibling

### `required_status_checks` schema

```json
{
  "type": "required_status_checks",
  "parameters": {
    "strict_required_status_checks_policy": true,
    "required_status_checks": [
      { "context": "Code Quality" },
      { "context": "Security Audit" }
    ]
  }
}
```
Each array item's field is **`context`** (string, required — "the status check context name that
must be present on the commit") plus an **optional** `integration_id` (integer — restricts which
GitHub App/integration must be the one reporting that context; leave unset unless a specific
Check Run source needs pinning) [CITED: docs.github.com/en/rest/repos/rules, fetched this session].
Matching is by **context name** (the job's `name:` field, not its YAML key) — this is exactly the
mechanism behind CONTEXT.md finding 6 (`ci.yml`'s `integration-tests` and
`integration-tests.yml`'s `integration-tests` both render the context `Integration Tests` and
collide). `strict_required_status_checks_policy: true` means a PR branch must be tested with the
latest `main` (an up-to-date-branch requirement) before merge — it does **not** by itself serialize
unrelated jobs; it only affects whether a stale branch can merge. The committed
`protect-main-branch.json` already sets this `true` (Claude's Discretion notes it can stay).

### `pull_request` rule parameters

```json
{
  "type": "pull_request",
  "parameters": {
    "required_approving_review_count": 1,
    "dismiss_stale_reviews_on_push": true,
    "require_code_owner_review": false,
    "require_last_push_approval": false,
    "required_review_thread_resolution": false
  }
}
```
D-07 changes only `required_approving_review_count` to `0`; the other four fields are unaffected.

### `bypass_actors` shape

```json
{
  "actor_id": 5,
  "actor_type": "RepositoryRole",
  "bypass_mode": "always"
}
```
`actor_id: 5` under `actor_type: "RepositoryRole"` is the well-known value for the built-in
**Admin** repository role [CITED: GitHub REST API rules documentation, cross-checked via
`docs.github.com/en/rest/repos/rules` and community discussion #152059 — `actor_id` 5 = "Repository
admin" is a stable, documented mapping, not an opaque numeric ID guessed from the committed file].
`bypass_mode` is one of `always` (bypass on every push, including direct pushes) or
`pull_request` (bypass only applies within a PR context). The committed JSON already uses `always`
for both rulesets; D-07 removes this entry from `protect-main-branch.json` entirely (not just
changes its mode), while D-08b explicitly retains it, unmodified, in `protect-release-tags.json`.

### Other rule types used

`deletion` and `non_fast_forward` take **no parameters** — bare `{"type": "deletion"}` blocks
branch/tag deletion; `{"type": "non_fast_forward"}` blocks force-push. `creation` (used only in
`protect-release-tags.json`, restricting who may create a matching ref) also takes no parameters.

### Permission requirements and failure mode

A fine-grained PAT must carry **repository permission "Administration" set to Write** to create or
update a ruleset via this endpoint [CITED: docs.github.com/en/rest/repos/rules — "Fine-grained
personal access tokens require the Administration repository permissions (write)"]. `gh auth
status`'s `admin: true` flag reflects the *authenticated user's* role on the repo
(`Am0rfu5`/organization-admin, confirmed via `gh api /repos/DF3NDR/paladin-dev-env` →
`"permissions":{"admin":true, ...}`), which is a necessary but not sufficient condition — the
token itself needs the separate `Administration: write` fine-grained scope. **Detect the failure
mode early**: a `POST` with insufficient token scope returns HTTP 403 with a message naming the
missing permission, not a silent no-op; run the `POST` against `protect-release-tags.json` (the
cheaper, less consequential of the two) first as a scope smoke-test before applying
`protect-main-branch.json`.

### Org vs. repo context note

`DF3NDR` is an **Organization**, not a personal user account [VERIFIED:
`gh api /repos/DF3NDR/paladin-dev-env` → `"owner":{...,"type":"Organization"}`]. The
`RepositoryRole`/`actor_id: 5` bypass-actor shape is repo-scoped and works identically under an
org-owned repository; no org-level ruleset endpoint (`/orgs/{org}/rulesets`) is needed for this
phase's scope (both target rulesets are `target: "branch"`/`target: "tag"` at the repository, not
org, level — confirmed by the committed JSON's absence of any org-level fields).

## 2. `Swatinem/rust-cache@v2` Migration Mechanics (D-10)

### Inputs (from the action's own `action.yml`, fetched live this session)

| Input | Default | Relevant use here |
|-------|---------|---------------------|
| `shared-key` | none | Use for jobs that should share one cache across runs regardless of job id (e.g., if `benchmark-compile-check` and `benchmark-regression-signal` should draw from the same warm cache) |
| `key` | none | Additional differentiator alongside the automatic job-based key — useful for `crate-isolation`'s ten legs if a shared base cache plus a per-crate key is desired, though the existing per-crate `${{ matrix.crate }}` key already differentiates |
| `prefix-key` | `v0-rust` | Bump this to force a clean cache reset without touching every job |
| `cache-targets` | `true` | Leave `true` — caches dependency build artifacts under `target/` |
| `cache-workspace-crates` | `false` | Leave `false` — workspace-owned crate artifacts are pruned by design (incremental builds of the crate under test are typically unreliable to cache; this matches the existing hand-rolled blocks' behavior of not special-casing workspace crates) |
| `cache-on-failure` | `false` | Consider `true` for the `examples`/`integration-tests` jobs specifically — a job that fails after successfully fetching dependencies still benefits future runs from a warm registry cache |
| `save-if` | `true` | Leave default; per-branch restriction not needed since D-01/D-03 make every branch a first-class CI citizen |
| `workspaces` | none (defaults to repo root) | Not needed — this is a single-workspace `Cargo.toml`, no override required |
| `add-rust-environment-hash-key` | `true` | Leave default — includes rustc version/host in the key, correctly invalidating cache across the `test:` job's `stable`/`beta` matrix legs |

Source: [CITED: `raw.githubusercontent.com/Swatinem/rust-cache/master/action.yml`, fetched live
this session].

### What it caches vs. what the 25 hand-rolled blocks cache

The action caches `~/.cargo` (registry, `bin/`, git checkouts) plus `./target`, and — critically —
implements **fallback restoration from a previous `Cargo.lock` generation automatically**: "the
action will try to restore from a previous Cargo.lock version as well" [CITED:
`raw.githubusercontent.com/Swatinem/rust-cache/master/README.md`]. This is the same *class* of
fallback `restore-keys` would provide on a hand-rolled `actions/cache@v4` block, and **it has the
same fundamental limitation CONTEXT.md finding 9 already names**: a fallback-restored cache from an
older `Cargo.lock` generation still lacks a crate that generation didn't have. `Swatinem/rust-cache`
does not solve the `--offline` problem by itself — see Pitfall 3.

The 25 hand-rolled blocks today cache `~/.cargo/registry` (sometimes split into `registry` and
`git` as two separate `actions/cache@v4` steps, e.g. `ci.yml:282-300`'s three-block pattern) plus
`target/`, all keyed **only** on `hashFiles('**/Cargo.lock')` with **no fallback of any kind**
(confirmed: `grep -rn "restore-keys" .github/workflows/*.yml` returns exactly one match, in
`pre-commit.yml`) [VERIFIED this session].

### Matrix interaction

`Swatinem/rust-cache@v2`'s automatic job-based key already differentiates by job name — for the
`test:` job's `[stable, beta]` matrix and `crate-isolation`'s ten-crate matrix, the automatic key
plus `add-rust-environment-hash-key: true` (which folds rustc version into the key) is sufficient
without an explicit `key:`/`shared-key:` override, matching what the current hand-rolled
`${{ matrix.rust-version }}` / `${{ matrix.crate }}` key suffixes already achieve manually.

### The `cargo fetch --locked` placement (critical — this is what keeps `--offline` meaningful)

The four `--offline` invocations are all in the `examples` job [VERIFIED:
`grep -n -- "--offline" .github/workflows/ci.yml` → lines 311, 314, 317, 320]. D-10 requires an
explicit
```yaml
- name: Fetch dependencies
  run: cargo fetch --locked
```
step placed **after** `Swatinem/rust-cache@v2`'s restore step and **before** the first
`--offline` build step in the `examples` job. This is not redundant with the cache action: even
with a warm cache restored, `cargo fetch --locked` is the only step that *guarantees* every crate
`Cargo.lock` names is present locally before `--offline` is asserted — the cache action's own
fallback-restore path can still land a job on an older cache generation (e.g., first run after
`prefix-key` bump, or a cache-eviction edge case), and `--offline` would then fail exactly as it
does today. `cargo fetch --locked` uses the network exactly once per job run (respecting
`Cargo.lock` exactly, never touching it), after which every subsequent `--offline` step in the
same job is genuinely hermetic — assert nothing unexpected is pulled during the *build* step,
which is the property `--offline` exists to prove.

## 4. `scripts/check-workflow-triggers.sh` Mechanics (D-09b)

`scripts/check-advisory-register.sh` is **not** the closest model — it parses TOML with `tomllib`.

### Parsing approach

- `python3 -c "import yaml"` succeeds in this environment (PyYAML `6.0`) [VERIFIED]. No `yq` binary
  is present (`which yq` → not found) [VERIFIED] — do not depend on `yq`.

3. Table parsing: since the table lives in a Markdown file (`branching-model.md`), not a fenced TOML

## Workflow Consolidation Mechanics (D-09)

### `services:` block — byte-identical Redis/MinIO pattern to reuse

`ci.yml:400-514`'s `integration-tests` job and `integration-tests.yml`'s `integration-tests` job
declare **near-identical but not byte-identical** `services:` blocks:

| | `ci.yml` (port) | `integration-tests.yml` (port) |
|---|---|---|
| Redis | `6380:6379` | `6379:6379` (no port remap) |
| MinIO | `9010:9000`, `9011:9001` | (different values — not re-verified in this session; re-check before consolidating) |

`ci.yml`'s job already runs `--ignored`-tagged narrow tests via the remapped `6380`/`9010` ports
(avoiding collision with a host-level Redis/MinIO if one happens to be running on the default
ports); `integration-tests.yml`'s job runs the **broad** `--features integration-tests` suite on
unmapped default ports. D-09 consolidating the two into one job means picking **one** port mapping
(the `6380`/`9010` non-default mapping is the safer choice — it is what the currently-required
`Coverage` job at `ci.yml:515+` also already uses, confirmed by its own `services:` block reusing
the same `6380`/`9010` pair) and updating the broad suite's connection env vars
(`TEST_REDIS_PORT`, `TEST_MINIO_ENDPOINT`) to match, exactly as `ci.yml`'s existing narrow job
already does at `ci.yml:483-491`.

### `needs:` graph implications

`docker:` currently declares `needs: [lint, test]` [VERIFIED:
`grep -n "needs:" .github/workflows/ci.yml`]. Nothing in the tree currently depends on
`integration-tests` or `kubernetes-smoke` via `needs:` — consolidation does not need to rewrite any
downstream `needs:` edge, only add the absorbed jobs' `needs:` (if any existed in
`integration-tests.yml`, none were found in the section read this session) as-is.

### Concurrency-group implications

`ci.yml`'s existing concurrency group (`ci-${{ github.head_ref || github.ref }}`,
`cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}`) already absorbs what would have been
two separate concurrency groups (`integration-tests.yml` currently has no explicit `concurrency:`
block at all [VERIFIED: not found in the file's first 30 lines], meaning today's daily-cron and
PR-triggered runs of that workflow can pile up unbounded). Consolidating into `ci.yml` is a strict
improvement here — the absorbed jobs inherit `ci.yml`'s existing, already-correct concurrency
discipline for free.

### Required-check-context implication of deleting the file

Because GitHub matches required status checks by **context name**, not by originating workflow
file, deleting `integration-tests.yml` has **no direct effect** on any *already-applied* ruleset's
required-check list — the context name `Integration Tests` continues to be satisfied by `ci.yml`'s
own job of that name, which is exactly why D-09 is a *prerequisite* for D-05/D-06 rather than an
independent cleanup: applying the ruleset **before** consolidating would have left the
`Integration Tests` context ambiguous between two job sources (CONTEXT.md finding 6), and GitHub
would accept a passing report from *either* source, silently weakening the gate for the six months
until someone noticed. Consolidating first removes the ambiguity structurally rather than by
policy.

## Common Pitfalls

### Pitfall 1: `deny.toml` line-number drift (verified this session — CONTEXT.md's own citation is stale)

**What goes wrong:** Editing `deny.toml:20-36` as CONTEXT.md's `<canonical_refs>` literally states
edits the `[licenses] allow` array instead of the advisories block.
**Why it happens:** The file has grown since CONTEXT.md's underlying research was last aligned to
it — CONTEXT.md itself warns "re-verify every line number in the ROADMAP entry... this
generalises," and this is exactly that generalization in action, this time against CONTEXT.md's own
citation rather than ROADMAP's.
**How to avoid:** Use `deny.toml:115-130` (re-verified this session, §5 above) for the `[advisories]
ignore` block; insert D-11's new line between `:129` and the closing `:130`.
**Warning signs:** `cargo deny check` continues failing on `RUSTSEC-2026-0249` after the edit, or
`git diff deny.toml` shows a change inside a `# Licenses:` comment block instead of a `# Advisories:`
one.

### Pitfall 2: `Swatinem/rust-cache@v2` alone does not fix `--offline` (D-10's explicit `cargo fetch --locked` step is load-bearing, not optional)

**What goes wrong:** Treating the action's built-in "restore from a previous `Cargo.lock` version"
fallback as equivalent to the missing `restore-keys` CONTEXT.md finding 9 already says would not
have fixed the bug.
**Why it happens:** The action's README markets this fallback as solving cache misses generally, and
it's easy to read that as solving *this specific* bug.
**How to avoid:** Keep the explicit `cargo fetch --locked` step (§2 above) immediately before every
`--offline` invocation regardless of the cache action's own fallback behavior — it is what
guarantees hermeticity, not the cache action.
**Warning signs:** A fresh branch's first `examples` job run still fails with
`error: failed to download <crate> ... --offline was specified` after the `Swatinem/rust-cache@v2`
migration but before `cargo fetch --locked` lands.

### Pitfall 3: mdbook builds green with a missing `SUMMARY.md` entry

**What goes wrong:** D-04's new `branching-model.md` page is written and committed, but the
`SUMMARY.md` edit is missed; `docs.yml`'s `Build MDBook` job passes anyway because mdbook silently
excludes unreferenced files rather than erroring.
**Why it happens:** No default-on mdbook warning exists for this case (verified via mdBook's own
issue tracker, §7 above).
**How to avoid:** Treat the `SUMMARY.md` line addition as its own explicit, separately-verified task
step (`grep -q branching-model.md docs/src/SUMMARY.md`), not something the mdbook build's green
checkmark can be trusted to confirm.
**Warning signs:** The page exists in `git ls-files docs/src/contributing/` but does not appear in
the deployed GitHub Pages navigation.

### Pitfall 4: two workflows still emitting the same status-check context name during a transitional window

**What goes wrong:** If D-09's consolidation and D-06's ruleset application are not sequenced
strictly (D-02 already mandates this ordering, but it's easy to lose sight of *why*), a
half-migrated state briefly has both `ci.yml` and a not-yet-deleted `integration-tests.yml`
reporting `Integration Tests`, and a required check silently passes off the *narrower* of the two
jobs.
**Why it happens:** GitHub's context-name matching has no concept of "which workflow file"; it is
purely a string match against whichever job last reported that name.
**How to avoid:** Delete `integration-tests.yml` in the same commit/PR that lands the consolidated
`ci.yml` job (not a follow-up), and apply the ruleset only after that PR is merged to `main` — this
is exactly D-02's ordering, restated with the specific hazard it prevents named.
**Warning signs:** `gh api /repos/DF3NDR/paladin-dev-env/commits/{sha}/check-runs` shows two
distinct `check_suite` entries both reporting a check named `Integration Tests` for the same commit.

### Pitfall 5: the existing `check-workflow-suppressions_test.sh` gap, silently inherited by the new script

**What goes wrong:** D-09b's new `check-workflow-triggers_test.sh` is written (following the
existing sibling's excellent fixture-cleanup pattern) but, like its sibling, is never actually
invoked by any CI workflow — so a future regression in the guard script itself goes undetected
until a human happens to run `make test-shell-guards` locally.
**Why it happens:** `test-shell-guards`'s own Makefile comment says "(not part of check-gates)" —
this was seemingly a deliberate choice at the time `check-workflow-suppressions_test.sh` was
authored, but nothing in the tree documents *why*, and no workflow step invokes it.
**How to avoid:** Either add a CI step invoking `make test-shell-guards` (covering both scripts'
regression tests in one motion) as part of this phase's work, or explicitly record the omission as
a deliberate, dated decision (per D-00g's "code-settled defects get ledger rows" convention) rather
than silently repeating it a second time.
**Warning signs:** None automated — this is precisely the point; the gap is invisible until someone
goes looking, which is the same failure class SC1 exists to close for workflow triggers generally.
