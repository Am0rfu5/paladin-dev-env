## Post-Verification Amendment (2026-08-15)

**A defect reached `main` that this report did not catch, was found in production use the next
day, and is fixed.** Recorded here per **D-00d** rather than by rewriting the verdicts above.

### What happened

PR #31 (this very report's own PR) hung with **97 checks complete, 0 pending, and still
`BLOCKED`**. Diagnosis: `docs.yml` filtered its `pull_request` trigger by
`paths: [docs/**, crates/doc-examples/**, .github/workflows/docs.yml]`, while `Build MDBook` was
one of the 44 **required** status-check contexts. GitHub blocks a pull request until every
required context reports, and a path-filtered workflow never reports on a PR that touches no
matching path. PR #31 changed only `.planning/` files, so `Build MDBook` never ran — leaving the
PR permanently unmergeable **with no failing check to explain why**.

Blast radius: 1 of 44 pinned contexts, but it would have hit routinely, since most PRs touch no
docs. Verified by audit that no other pinned context was exposed — `ci.yml`, `feature-flags.yml`
and `pre-commit.yml` all carry unfiltered `pull_request` triggers, and `benchmarks.yml` /
`release.yml` own zero pinned contexts.

Root cause of the mis-pin: plan `15.1-04` derived the required set from an observed
`pull_request` run on PR #29, which happened to change `.github/workflows/*.yml` and therefore
*matched* `docs.yml`'s filter. The observation was real; it just wasn't representative.

### Why the guard did not catch it

`check-workflow-triggers.sh`'s context clause (clause 3) asserts that every pinned context
**resolves to a declared job name**. `Build MDBook` resolved perfectly — the job existed and was
named correctly. It simply never ran. Clause 3 is structurally incapable of detecting this: name
resolution and runtime reachability are different properties.

### The fix (merged in PR #31, commit `6e84972`)

1. **`docs.yml`'s `pull_request` paths filter removed**, so the required check always reports.
   Its `push` trigger keeps both `branches: [main]` and its paths filter — the GitHub Pages
   deploy should not run on every branch, and that exception (D-03) was never the problem.
2. **New clause 4, `CLAUSE_REACHABILITY`**, added to `scripts/check-workflow-triggers.sh`: a
   pinned context whose owning workflow path-filters its `pull_request` trigger, or declares no
   `pull_request` trigger at all, now fails CI with an actionable message naming both remedies
   (drop the filter, or unpin the context).
3. **Three new test cases** in `tests/scripts/check-workflow-triggers_test.sh`: path-filtered
   fires, no-`pull_request` fires, and — importantly — unfiltered stays **silent**, so the clause
   cannot pass by merely firing whenever a pinned context exists.
4. **`branching-model.md`'s policy row corrected.** It had claimed the book was built "on every PR
   regardless of branch", which the path filter made untrue at the time it was written.

### Corrections to statements made above

- **§SC1** quotes the guard's summary line as `coverage, drift and context clauses all pass`.
  That output is now `coverage, drift, context and reachability clauses all pass.`
- **§SC1** records `✅ 8 assertion(s) passed.` for the test harness. It is now
  `✅ 11 assertion(s) passed.`
- **§Job-Name Uniqueness** is reinforced, not corrected. On PR #31, `Kubernetes Smoke Test`
  appeared **twice**, both `IN_PROGRESS` — a push-event run and a pull_request-event run of the

  confirmation that CONTEXT.md finding 6 was wrong to list it as a duplicated context, and it
  vindicates D-05's decision to exclude it from the required set: had it been pinned, every PR
  would wait on a ~5½-minute emulated smoke test for no gating value.

written down before the ruleset was applied, and because the checkpoint was presented to a human
rather than auto-approved. The guard gap it exposed is now closed by a test-covered clause.
