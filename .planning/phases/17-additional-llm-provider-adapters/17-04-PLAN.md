<objective>
Ship the generic operator-configured OpenAI-compatible provider (D-03): `base_url` + key + model +
declared capabilities, pointed at any compatible endpoint with no new code. This is the decision
that changes the disposition of the rest of the candidate field — Groq, Together, Mistral,
Fireworks and Bedrock are **rejected as already covered** rather than deferred (recorded in
ADR-0045 by plan 17-02), so a future request for any of them is answered by configuration instead
of a new phase.

**Purpose:** Without this adapter, every future OpenAI-compatible endpoint is a phase. With it, the
five named presets carry *curation* (correct capabilities, correct model lists) and the generic
provider carries *access*.

**Output:** `crates/paladin-llm/src/openai_compatible/`, an `openai-compatible` Cargo feature, a
registry row, and a registry-wide provider-name round-trip invariant test.

**Scope guards:**
- **D-04** — capabilities are operator-declared with pessimistic defaults. Unset means the
  conservative answer. The adapter must never claim a capability nobody asserted; Phase 14 already
  paid once to fix a capability flag that over-reported, and an adapter pointed at an unknown

  `"openai-compatible"`, a wire-protocol term of art, deliberately not medieval-military (D-00h
  binds coined domain nouns, not protocol terms).
- **D-05** — the adapter is a `CompatEngine` consumer; it implements no transport of its own.
- **D-06** — the shipped three are untouched.
- **D-00o** — commit with `--no-verify`; crate-scoped builds only.

## Assumption delta: the provider-identity noun

**Signal.** A second case of "a provider" was introduced where the identity model assumed one. The
shipped assumption is `LlmPort::get_provider_name() -> &'static str`
(`crates/paladin-ports/src/output/llm_port.rs:1291`): **one static name per adapter type.** The
generic adapter breaks it — two instances pointed at different endpoints are the same type and
therefore report the same name.

**The noun that is now primary.** *Provider identity* has generalised from "the adapter type" to
"the configured endpoint the adapter is pointed at". A curated preset is now the special case
(identity is fixed at compile time); the generic adapter is the general case (identity is a runtime
configuration fact).

**Decision: `add-alongside` — accepted debt, per D-07.** The generic adapter returns the fixed
literal `"openai-compatible"` alongside the five preset literals; `LlmPort` is not widened to
`-> &str`. This is deliberately *not* the usual correct move (promote the general case, demote the
specific one to a detail of one variant). The reason is cost, and it is recorded rather than
assumed: widening the trait is a breaking change to a **public port trait** that moves every adapter
signature, the mock, and `.project/current-exports.txt` — the `api-surface` guard DEBT-01 repaired
and this project has already paid to fix once. Leaking the configured name out of a `&'static str`
was also considered and rejected as requiring a leak or an intern table.

**Accepted cost, stated plainly.** Two generic adapters pointed at different endpoints are
indistinguishable in logs, metrics and error messages. An operator running one generic adapter
against a vLLM gateway and another against Bedrock's compat mode sees `"openai-compatible"` for
both.

**What would force a later promote.**
1. Any phase already making a breaking `LlmPort` change — the marginal cost of widening
   `get_provider_name()` at that moment is near zero (17-CONTEXT.md records this as the deferred
   idea's own trigger).
2. The first operator-visible incident where two generic instances cannot be told apart in
   diagnostics — at which point the debt has been paid for in an outage rather than in a refactor.

**Invariant test (Task 3).** A registry-wide round-trip test — for every row in
`PROVIDER_REGISTRY`, constructing that row and calling `get_provider_name()` returns that row's own
`name` — encodes the generalized intent. It goes red the instant a future phase reintroduces the
singular assumption by, for example, having a second generic row reuse the same literal.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator configuration → request destination | `base_url` is entirely operator-supplied and determines where the request, **carrying the configured API key**, is sent. This is the widest new trust boundary in the phase. |
| Remote endpoint → capability report | A compatible endpoint could return metadata that looks like a capability declaration; the adapter must never act on it. |
| Operator configuration → capability declaration | The only legitimate source of capability truth for this adapter. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-17-18 | Information Disclosure | operator-supplied `base_url` carrying the API key (SSRF-adjacent) | high | mitigate | The key is only ever sent to the host the operator configured, and the adapter follows no redirect to a different host: Task 2 builds the engine with `reqwest`'s redirect policy set to none for this adapter, so a `302` to an attacker-chosen host cannot carry the `Authorization` header. The residual case — an operator who deliberately configures an internal address — is documented in the module rustdoc as the operator's own trust decision. 17-RESEARCH.md flags this as "not addressed by any locked decision"; this is the plan's disposition of it. Paladin's deployment model is single-tenant with operator-controlled config (PROJECT.md), so no allowlist is introduced. |
| T-17-19 | Elevation of Privilege (of capability) | `get_capabilities()` | high | mitigate | Capabilities are read **only** from operator configuration.
