<objective>
Close **WR-03**: Gemini's `map_error` misclassifies the credential-failure shapes Google's
Generative Language API actually returns.

Two concrete defects, both at `crates/paladin-llm/src/gemini/adapter.rs:389-417`:

1. `AuthenticationError` is produced only for `401 | 403` **paired with**
   `rpc_status == Some("PERMISSION_DENIED")`. Any `401`/`403` carrying a different status — e.g.
   `UNAUTHENTICATED` — or no parseable envelope at all falls through to the final catch-all arm,
   which returns the **retryable** `LlmError::ProcessingError`.
2. Google commonly reports an invalid or malformed API key as **`400` with
   `status: "INVALID_ARGUMENT"`** and a message such as *"API key not valid. Please pass a valid API
   key."* Under the current mapping that lands on the `INVALID_ARGUMENT` arm and returns
   `InvalidPrompt`, telling the caller their *prompt* is malformed rather than their *credential*.

**Purpose:** the retryable classification is the security-adjacent half. `execute_with_retry`
already treats `AuthenticationError` as non-retryable and `ProcessingError` as retryable, so a
misclassified auth failure means the adapter retries a doomed request three more times, each attempt
re-transmitting a live `x-goog-api-key` to an endpoint that has already rejected it. PROV-02
requires that *"rate-limit and auth failures are distinguishable by the caller"* — today, for the
most common real-world shape, they are not. This is the class of protocol-mapping error the phase's
own context flagged as plausible for the one adapter never verified against a live endpoint (D-08,
17-05 coverage D7).

**Output:** a rewritten `map_error` arm set, a named `GEMINI_CREDENTIAL_MESSAGE_SIGNATURES` constant
with a narrow discriminator, and six regression tests including an end-to-end proof that an auth
failure is attempted exactly once.

**Scope guards:**
- **WR-06 is out of scope.** Gemini's missing truncated/empty-completion detection is a separate
  deferred finding. Do not add it while in `parse_response`.
- The `RESOURCE_EXHAUSTED` → `RateLimitExceeded` mapping and its documented assumption (17-05's
  recorded decision, verification path: `live-api-tests` with a real key) are **preserved
  verbatim**. This plan does not re-litigate it.
- The `300..=399` arm added by plan 17-10 and the `validate_model_identifier` guard added by plan
  17-09 must both survive the rework.
- **D-06** — `openai/`, `anthropic/`, `deepseek/` untouched. `compat/engine.rs`'s own `map_error` is
  untouched; the compat presets already map `401` unconditionally.
- **D-00o** — commit with `--no-verify`; crate-scoped builds only, never a workspace build.
</objective>

**1. The signature constant.** Add a module-level private constant next to the file's other
`GEMINI_*` constants, following the `ANTHROPIC_USAGE_CAP_SIGNATURE` precedent:

  `const GEMINI_CREDENTIAL_MESSAGE_SIGNATURES: &[&str] = &[ ... ];`

  Its entries, all lowercase, all narrow: `"api key"`, `"api_key"`, `"unauthenticated"`,
  `"invalid authentication"`, `"credential"`.

  Its `///` doc comment must record two things:
  - **Why it exists:** Google's documented invalid-key response is HTTP `400` with
    `status: "INVALID_ARGUMENT"`, not a `401`, so the HTTP status alone cannot separate a bad key
    from a bad prompt. Cite WR-03 and `17-REVIEW.md`.
  - **Why the hyphenated header name is deliberately absent:** an echoed request body carries the
    header's *name* for reasons unrelated to credential validity, and matching on it would send an
    operator to rotate a working key. `map_error_400_echoing_the_api_key_header_name_still_maps_to_invalid_prompt`
    is the test that pins this. State that any future addition to this list must come with a
    corresponding over-trigger control test.

**2. The discriminator.** Add a private module-level free function next to `candidate_text` /
`map_finish_reason`:

  `fn is_credential_failure_message(message: &str) -> bool`

  It lowercases the input **once** into a local `String` and returns whether any signature is
  contained in it. No regex, no new dependency, no `unwrap()`.

**3. Rewrite `map_error`'s arm set**, in exactly this order:

  1. `401 | 403 => LlmError::AuthenticationError(...)` — **unconditional**, replacing the current
     `if rpc_status == Some("PERMISSION_DENIED")` guard. This is the arm that removes the
     fall-through to a retryable classification.
  2. `400 if rpc_status == Some("INVALID_ARGUMENT") && is_credential_failure_message(raw_message)
     => LlmError::AuthenticationError(...)` — message wording distinct from arm 1's, naming that
     the provider rejected the configured key.
  3. `400 if rpc_status == Some("INVALID_ARGUMENT") => LlmError::InvalidPrompt(excerpt)` —
     unchanged behaviour, now reached only when arm 2 does not match.
  4. `404 if rpc_status == Some("NOT_FOUND") => LlmError::ModelNotAvailable(excerpt)` — unchanged.
  5. `429 => LlmError::RateLimitExceeded` — unchanged.
  6. `_ if rpc_status == Some("RESOURCE_EXHAUSTED") => LlmError::RateLimitExceeded` — unchanged,
     including its documented assumption.
  7. `300..=399 => ...` — **preserve the refused-redirect arm added by plan 17-10 verbatim.**
  8. `_ => LlmError::ProcessingError(...)` — unchanged catch-all.

  **The raw/excerpt split is load-bearing:** `is_credential_failure_message` reads `raw_message`,
  because `bounded_excerpt` truncates at `RESPONSE_EXCERPT_CHAR_BUDGET` and a signature appearing
  past that boundary would be missed. But **only `excerpt` is ever emitted** — never `raw_message`.
  Put that reasoning in a comment on arm 2, because the two-variable split otherwise reads like an
  oversight.

**4. Update `map_error`'s doc comment.** It currently documents only the `RESOURCE_EXHAUSTED`
disposition. Add the credential-classification reasoning and keep the `RESOURCE_EXHAUSTED`
paragraph byte-identical. The new text must state:
  - a `401`/`403` is always a credential failure regardless of RPC status, because the alternative
    is a retryable classification and `execute_with_retry` would then re-transmit a live credential
    to an endpoint that has already rejected it;
  - `400`/`INVALID_ARGUMENT` is ambiguous between a bad key and a bad prompt, and the named
    signature list is how the two are separated;
  - the asymmetry that decides the default: a bad prompt misread as a bad key costs the operator a
    wasted credential rotation, while a bad key misread as a bad prompt costs three extra
    transmissions of a live secret — so the discriminator errs narrow and the unmatched case stays
    `InvalidPrompt`.

**5. Verify the retry coupling explicitly.** `execute_with_retry`'s non-retryable set already
contains `AuthenticationError`, so no change is needed there. Add a one-line comment at arm 1
recording that this arm is what makes that existing policy correct, so a future edit to either side
sees the coupling.

Commit as a single `fix(17-11):` commit with `--no-verify` (D-00o), naming WR-03.
