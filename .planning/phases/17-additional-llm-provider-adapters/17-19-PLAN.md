<objective>
Close **G-17-4b**: Kimi cannot complete a `generate()` call with its own defaults, for two
independent reasons.

1. `KIMI_DEFAULT_MODEL = "moonshot-v1-8k"` is retired — Moonshot answers
   `{"message":"Not found the model moonshot-v1-8k or Permission denied","type":"resource_not_found_error"}`.
   The live list at the 2026-08-22 measurement held `kimi-k2.6`, `kimi-k2.7-code`,
   `kimi-k2.7-code-highspeed` and `kimi-k3`.
2. Even against a live-listed model, the framework's default temperature is rejected:
   `kimi-k2.6` answers `{"message":"invalid temperature: only 1 is allowed for this model"}`,
   while `PromptParameters::default()` sends `0.7` (`paladin-core` prompt.rs:151).

Fixing the model identifier is **necessary but not sufficient**. The second cause is the
interesting one, because the obvious remedy collides with a locked decision: 17-UAT.md's
`missing` list says "enforce **or** clamp", and **ADR-0004 considered adapter-level clamping by
name and rejected it**. Task 1 puts that fork to the developer rather than letting the planner
quietly reinterpret an Accepted ADR.

**Purpose:** make the Moonshot preset functional out of the box without lying in
`get_capabilities()` and without silently overriding a caller.
**Output:** refreshed Kimi model constants, a measured temperature declaration, and the chosen
resolution implemented and regression-tested.
</objective>

## Facts already established — read these, do not re-derive them

**Plan 17-18 built the seam this plan extends.** `CompatRequestParameters` on
`CompatEngineConfig` declares, per parameter, whether this preset's request path carries it;
`build_request` gates each of the five optional sampling fields on that declaration; an omitted
parameter becomes an absent JSON key via the wire type's existing `skip_serializing_if`. Kimi's
declaration currently reads `CompatRequestParameters::all()` — deliberately unchanged by 17-18
so that plan was behaviour-preserving for every vendor except xAI.

**ADR-0004 is Accepted and governs temperature (D-00q).** Its operative content, verified
against the shipped tree:

- `ProviderCapabilities::temperature_range: Option<(f32, f32)>`, **both endpoints inclusive**;
  `None` falls back to the global `[0.0, 1.0]`.
- Under *Considered Options* it rejects, by name: *"Adapter-level clamping (each LLM adapter
  silently clamps an out-of-range temperature to its own legal range before sending the request)
  — rejected. Clamping silently alters the caller's value past the point where the caller can be
  told they were wrong."*
- The provider-aware validation is **implemented and live**, not aspirational:
  `src/application/services/paladin/paladin_builder.rs` `validate()` reads
  `self.llm_port.get_capabilities().temperature_range.unwrap_or((0.0, 1.0))` and returns
  `PaladinError::ConfigurationError` naming the rejected value. It validates
  `self.data.temperature` **unconditionally** — not only when the caller called `.temperature()`
  explicitly. So a narrowed Kimi range constrains every Paladin built against Kimi, including
  ones that never mentioned temperature.
- A **degenerate range where `min == max` is already an accepted, tested configuration** — plan
  17-14 established exactly that for the generic provider (`min > max` rejected, `min == max`
  accepted).

**`crates/paladin-llm/src/lib.rs`** carries a cross-adapter invariant test,
`test_every_adapter_declares_a_temperature_range`, requiring every adapter's
`get_capabilities().temperature_range` to be `Some(_)`. `None` is not available as an answer.

**Kimi's preset today** (`kimi/adapter.rs:152-181`) declares `temperature_range: Some((0.0, 1.0))`
— which the live vendor does not honour, since only `1` is accepted.

**Credential loading and probe hygiene** are unchanged from plan 17-18; see this plan's
`<executor_notes>`.

<task type="checkpoint:decision" gate="blocking">
  <decision>How Kimi's fixed-temperature constraint is honoured, given that ADR-0004 explicitly rejects adapter-level clamping and the builder validates every Paladin's temperature against the declared range.</decision>
  <context>
Moonshot's current models accept exactly one temperature: `1`. The framework's default prompt
parameters send `0.7`, so `KimiAdapter::generate()` fails today with default parameters even
against a live-listed model. 17-UAT.md's remedy list says "enforce **or** clamp", leaving the
fork open — and clamping is the one option ADR-0004 already ruled out by name.

Three consequences make this a real fork rather than a formality:

- Declaring `temperature_range: Some((1.0, 1.0))` is the **truthful** capability answer PROV-02
  demands, but because `paladin_builder::validate()` checks `self.data.temperature`
  unconditionally, it also means **every Paladin built against Kimi with any temperature other
  than exactly 1.0 fails at build time** with a `ConfigurationError` — including one whose author
  never set a temperature at all.
- Declaring a comfortable range Kimi does not honour keeps the builder quiet but re-opens exactly
  the optimistic-capability defect Phase 14 spent a phase closing.
- The root enabler is that `PromptParameters::default()` fabricates `Some(0.7)`, so nothing
  downstream can distinguish "the caller chose 0.7" from "nobody said anything". No amount of
  adapter-level cleverness recovers that distinction.
  </context>
  <options>
    <option id="option-a">
      <name>Preset declares temperature as a parameter its request path does not carry; capability declaration stays truthful</name>
      <pros>
        Kimi works out of the box for any caller reaching the adapter directly, including the live
        harness: the parameter is simply absent from the body and the vendor applies its only legal
        value, which is by definition the same value a truthful range declares. Reuses plan 17-18's
        mechanism with no new engine concept. Nothing is clamped — no legal value is substituted for
        another legal value — so ADR-0004's stated objection does not apply on its own terms.
        `temperature_range: Some((1.0, 1.0))` remains truthful and keeps the builder's ADR-0004 check
        meaningful and actionable.
      </pros>
      <cons>
        A caller who reaches the adapter directly and explicitly sets 0.5 has their value dropped
        without being told anything louder than a `debug` log — the spirit, if not the letter, of
        ADR-0004's objection. Through the Paladin builder path, a Kimi-backed Paladin must set
        `.temperature(1.0)` explicitly or fail to build, which is actionable but is not
        "out of the box" for that path.
      </cons>
    </option>
    <option id="option-b">
      <name>Engine enforces the declared range and rejects out-of-range values, including the fabricated default</name>
      <pros>
        The literal reading of ADR-0004, extended down into the engine so the direct-adapter path is
        guarded exactly as the builder path already is. The caller is always told. No value is ever
        dropped or substituted. The clearest possible diagnostic: a local `LlmError::InvalidPrompt`
        naming the legal range, instead of a vendor error the operator must decode.
      </pros>
      <cons>
        Kimi still does not work with default parameters — `generate()` fails locally instead of at
        the vendor. G-17-4b's truth as written ("using its default model **and default parameters**")
        would close as "documented vendor constraint plus an actionable error", not as
        "works out of the box", and the developer would have to accept that narrower closure
        explicitly.
      </cons>
    </option>
    <option id="option-c">
      <name>Stop fabricating sampling defaults at the source: PromptParameters::default() supplies None</name>
      <pros>
        Fixes the root cause rather than its symptoms, and would have prevented the Grok blocker too:
        nothing is sent that the caller did not ask for, so each vendor's own default applies and no
        per-preset declaration is needed for either quirk. The cleanest long-term shape.
      </pros>
      <cons>
        Widest blast radius by a distance: it changes the request every one of the nine adapters
        sends, including the three shipped before this phase, and `max_tokens: Some(1000)` would stop
        being sent — removing a generation bound is an unbounded-cost change, not a neutral one. It
        edits `paladin-core`, needs its own ADR under D-00g, and is out of proportion to closing one
        gap. Recorded as the right idea at the wrong scope.
      </cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c. Planner's recommendation is **option-a** — it is the only option that makes Kimi work with default parameters while keeping `get_capabilities()` truthful, and it does not do the specific thing ADR-0004 forbids. If option-c is selected, stop this plan and raise a new ADR first.</resume-signal>
</task>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Paladin process → vendor API (`api.moonshot.ai`) | The `Authorization` header carries the operator's credential outbound; an untrusted response body comes back. |
| adapter capability declaration → `paladin_builder::validate()` | The declared range decides which Paladins can be constructed at all; a wrong declaration is a denial-of-service on legitimate configurations. |
| vendor response body → logs / SUMMARY | Attacker-influenceable text this plan deliberately quotes into a durable record. |
