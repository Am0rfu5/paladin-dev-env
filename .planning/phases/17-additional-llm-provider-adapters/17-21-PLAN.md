<objective>
Reach a recorded resolution for **G-17-4c**, the one gap in this run that no code change can
close.

Both DashScope endpoints — `https://dashscope-intl.aliyuncs.com/compatible-mode/v1/models` and
`https://dashscope.aliyuncs.com/compatible-mode/v1/models` — return `401 invalid_api_key` in
Alibaba's documented OpenAI-compatible error envelope. That is **positive evidence the base URL
is correct**: it resolves, TLS-terminates and answers in the vendor's own schema. What fails is
authentication. The stored token is a structurally clean single 117-character string with no `=`,
whitespace or newline, so the import loader is not corrupting it; DashScope keys are
conventionally `sk-` plus roughly 32 hex characters, so the file most likely holds a different
secret entirely.

So this plan is a **verification step with a human precondition**, not a code fix. It ends one of
two ways, and both are acceptable outcomes — what is not acceptable is leaving the gap ambiguous:

1. A valid key arrives, Qwen is held to exactly the bar Grok and Kimi were held to, and the gap
   closes on evidence.
2. No key arrives, and the gap closes as an explicitly developer-accepted deferral carrying the
   evidence above and a named trigger.

**Purpose:** close the run without a gap whose status nobody can state.
**Output:** either a live-verified Qwen preset, or a recorded deferral — plus the phase's final
four-vendor regression record either way.
</objective>

## Facts already established — read these, do not re-derive them

**What plans 17-18 and 17-19 built, which Qwen inherits for free:** `CompatRequestParameters` on
`CompatEngineConfig` lets a preset declare, per sampling parameter, whether its request path
carries it; `build_request` honours that declaration. Qwen currently declares
`CompatRequestParameters::all()`. If DashScope turns out to reject a parameter the way xAI rejects
`presence_penalty`, the fix is a declaration change on the preset — no engine work.

**The harness already probes Qwen twice** — model list (with the byte-for-byte fallback
discrimination) and, since plan 17-18, `generate()` with the framework's default prompt
parameters. No harness change is needed by this plan.

**Qwen's preset today** declares `temperature_range: Some((0.0, 2.0))`,
`max_context_tokens: Some(131_072)`, `supports_vision: false` (deliberately — this is the text
adapter, not `qwen-vl`), and `QWEN_FALLBACK_MODELS = ["qwen-plus", "qwen-turbo", "qwen3-max"]`
with `QWEN_DEFAULT_MODEL = "qwen-plus"`. None of these has ever been checked against a live
endpoint.

**Region matters.** `QWEN_DEFAULT_BASE_URL` is the international compatible-mode endpoint. The
module's own "Region default" rustdoc records that DashScope publishes at least five regional base
URLs and that an operator in another region reaches theirs with `DASHSCOPE_BASE_URL` and no code
change. A key issued in one region is not accepted by another's endpoint — so a fresh key that
still returns 401 is a region question before it is a code question.

**The credential import path:** the host directory `~/.config/paladin` is bind-mounted read-only
into the container, one secret per file, filename-lowercased to variable name. A file is applied
only when the variable is currently unset **or empty** — the repo `.env` declares these names with
empty values, which is why the empty-check exists. The loader trims CR/LF and surrounding
whitespace, and skips placeholder-looking values.

**Plan 17-20 has already rewritten the surrounding documentation** with a per-vendor verification
status, recording Qwen as still unverified with its reason. This plan updates **only Qwen's rows**,
in whichever direction the outcome requires.

## Operational facts for this repository — non-negotiable

1. **Commit with `git commit --no-verify`.** `workflow.worktree_skip_hooks` is `true` in
   `.planning/config.json` (D-00o).
2. **Load credentials by sourcing, never by piping.**

   ```bash
   . /workspace/.devcontainer/paladin-env.sh
   paladin-keys
   ```

   `. script | head` runs in a subshell and silently discards every export — the symptom is
   "unset" credentials next to readable key files.
3. **Never print a credential.** No `set -x`, no `curl -v`. `paladin-keys` reports character
   counts, never values. Keep the key out of the process argument list by feeding the header
   through `curl --config -`:

   ```bash
   BASE=https://dashscope-intl.aliyuncs.com/compatible-mode/v1
   printf 'header = "Authorization: Bearer %s"\n' "$DASHSCOPE_API_KEY" \
   | curl -s --config - "$BASE/models" | head -c 600

   MODEL=<the chosen default, confirmed present in the live list>
   for P in '"temperature":0.7' '"max_tokens":16' '"top_p":1.0' \
            '"frequency_penalty":0.0' '"presence_penalty":0.0'; do
     echo "=== $P"
     printf 'header = "Authorization: Bearer %s"\n' "$DASHSCOPE_API_KEY" \
     | curl -s --config - \
         -H 'Content-Type: application/json' \
         -d "{\"model\":\"$MODEL\",\"messages\":[{\"role\":\"user\",\"content\":\"ping\"}],$P}" \
         "$BASE/chat/completions" \
     | head -c 400
     echo
   done
   ```

   Inspect each response before quoting it into the SUMMARY; quote only the error envelope.
4. **The mainland endpoint, if the region question arises:**
   `https://dashscope.aliyuncs.com/compatible-mode/v1`. Reach it for a run with
   `DASHSCOPE_BASE_URL`; **do not** change `QWEN_DEFAULT_BASE_URL` in source.
5. **Run the harness with all four features:**

   ```bash
   cargo run -p paladin-llm --example live_vendor_smoke --features kimi,qwen,grok,gemini
   ```

   A non-zero exit is expected and correct if Qwen was deferred — the harness is reporting an
   unverified vendor honestly, which is what it was built to do. Record the exit code either way.
6. **Never run `make coverage`, `make test-all`, or any Docker-dependent target** as part of this
   plan.
