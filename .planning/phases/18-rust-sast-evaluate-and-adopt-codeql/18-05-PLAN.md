<objective>
Produce the numbers a required check may be pinned on, over real diffs from this repository, and
without idling on calendar time.

`workflow_dispatch` rejects a bare commit SHA as a ref, so the historical sample cannot be
dispatched against old merge commits directly. Instead the backfill uses the workflow's own
match-all push trigger: push a disposable branch whose tip is a sampled historical commit, let the
scan fire naturally on that exact tree state, record, delete. A short live period over the pull
requests this phase itself generates supplies the organic half.

A scanner is pinned on measured behaviour, never on a vendor's claim. This plan is where the
measurement happens.

Purpose: SAST-03 forbids promoting an unmeasured scanner; the promotion in 18-06 reads only what
this plan records.
Output: `18-CODEQL-EVIDENCE.md` gains an observation-window section carrying the backfill table,
the live table and the complete D-15 metric block, with every false positive dispositioned in the
governed register.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| disposable branches → shared CI capacity | Every push to any branch fires several match-all workflows, including a multi-architecture container build measured at over an hour |
| alert triage judgement → recorded rate | A human decision about each alert becomes a number the promotion decision rests on |
| measured metrics → promotion threshold | The thresholds were fixed in advance; the risk is editing them after seeing the numbers |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-18-21 | Denial of Service | Backfill pushes triggering the whole pipeline | high | mitigate | Branches are pushed one at a time and every non-`codeql.yml` run on the ref is cancelled immediately after the push; each branch is deleted once its CodeQL run reaches a terminal state; pushed and deleted counts must be equal and are asserted against `git ls-remote`. |
| T-18-22 | Repudiation | A cancelled run counted as a measurement | high | mitigate | Only runs whose conclusion is `success` or `failure` contribute; a `cancelled` row is labelled excluded and the commit is re-run. |
| T-18-23 | Repudiation | A zero-alert window read as a clean result | high | mitigate | Zero alerts records an undefined false-positive rate with the alert count beside it; the acceptance criterion rejects a percentage in that case. |
| T-18-24 | Repudiation | Untriaged alerts absorbed into a favourable rate | high | mitigate | `untriaged` is a first-class disposition recorded in its own metric line; it is never folded into either the true-positive or false-positive count. |
| T-18-25 | Tampering | Thresholds edited to fit the measurement | high | mitigate | `## Promotion Criteria` was written and dated in 18-01 and must remain byte-identical; the comparison sentence quotes the measured numbers against it. |
| T-18-26 | Repudiation | Convenient dismissal of an inconvenient true positive | high | mitigate | Every false-positive disposition requires a governed register row with a named owner, a dated review and a compensating control, enforced by the guard from 18-04 in a required check. |
| T-18-SC | Tampering | Package-manager installs | high | mitigate | This plan installs nothing. RESEARCH.md's Package Legitimacy Audit records no `[SLOP]` and no `[SUS]` verdicts for this phase. |
</threat_model>
