<objective>
Land the pre-publish consistency gate as one thin, production-quality path that runs end to end:
a repo script → a make target → a new `release.yml` job → a `needs` edge that `publish-crates`
cannot bypass. This tracer carries exactly one of D-08's clauses (tag version vs every publishable
manifest version) so the whole wiring is proven before the remaining clauses are added on top of it
in plan 20-02.

Purpose: PUBOPS-01's binding claim is "no crate is published until the tag, every manifest version
and every changelog agree". The `needs` edge is what makes that claim true; the clauses are what
make it useful. Proving the edge first means a wrong architecture surfaces after one commit rather
than after the whole gate is written.

Output: `scripts/check-release-consistency.sh`, `tests/scripts/check-release-consistency_test.sh`,
a `check-release-consistency` make target, and a `check-release-consistency` job in `release.yml`
wired into `publish-crates`'s `needs`.
</objective>

<assumption_delta_decision>
**Noun:** *release run per tag* (detector fired on the pluralization family: "must be safe to run a
**second** time on the same tag").

**Decision:** `promote`.

**Rationale:** the pre-Phase-20 pipeline is built on a singleton assumption — one workflow run per
tag, one `cargo publish` attempt per crate, one `ci.yml` run per SHA. Every defect this phase closes
is that assumption failing: `create-release@v1` 422s because a second run finds the first run's
release; the publish loop's tolerance is unreachable because a second run never gets there; and
Pitfall 4 shows the same SHA can carry several `ci.yml` runs. The plural case is promoted to the
primary case throughout: releases are created-or-reused, publication state is read from the registry
rather than from what this run remembers doing, and run selection sorts a *set* of runs rather than
taking the only one. No `add-alongside` debt is accepted.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| git tag ref → `release.yml` job shell | A tag name is attacker-influenceable by anyone who can push a tag; it flows into the new job's `run:` block |
| `workflow_dispatch` input → `release.yml` job shell | The `tag` input is free-form operator-supplied text |
| repo working tree → gate verdict | The gate's answer is derived from files in the tree; a tree state that yields no packages must not read as a pass |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-01 | Tampering | `check-release-consistency` job `run:` step | high | mitigate | Tag-derived version reaches the shell only through an `env:` key (CR-01), never through direct `${{ }}` interpolation inside `run:`; the script quotes every expansion and rejects unknown flags |
| T-20-02 | Elevation of Privilege | `check-release-consistency` job `permissions:` | high | mitigate | Job declares `permissions: contents: read` exclusively — no `id-token: write`, no `contents: write`; asserted mechanically in Task 1's `<verify>` |
| T-20-03 | Spoofing | Gate verdict over an empty package set | high | mitigate | Zero discovered publishable packages emits the `ZERO_PACKAGES` token and exits non-zero; a broken enumeration can never present as `OK` |
| T-20-04 | Tampering | `publish-crates` `needs` edge | high | mitigate | The gate job is added to `publish-crates`'s `needs`; the assertion in Task 1's `<verify>` fails the plan if that edge is missing, so the gate cannot be quietly detached |
| T-20-05 | Denial of Service | Gate blocking every release on a false mismatch | medium | accept | Exact-string comparison can only fail when the tree genuinely disagrees with the tag; the remediation block names the fix. Accepted because a fail-closed gate is the requirement (PUBOPS-01), not a defect |
| T-20-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package installs in this plan — `20-RESEARCH.md` records the Package Legitimacy Gate as not applicable (zero new dependencies); if any install appears during execution, stop and run the gate protocol before proceeding |
</threat_model>
