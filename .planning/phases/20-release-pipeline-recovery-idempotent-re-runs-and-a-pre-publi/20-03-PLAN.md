<objective>
Make the `create-release` job safe to run twice on the same tag — the single defect that makes the
whole recovery path unreachable today — by replacing the archived `actions/create-release@v1` step
with a create-or-reuse script driven by `gh api`, preserving the job's `upload_url`/`version`
outputs exactly. Also expose the release commit SHA that `verify-tag-source` already computes, so
the consistency gate can resolve CI's conclusion for that commit.

Purpose: PUBOPS-03 says idempotency is a property of every job between the tag and `cargo publish`.
`create-release` is the job that breaks it: a 422 on a tag that already has a release means
`publish-crates` — which `needs` it — never runs, so the publish loop's own tolerance is dead code
on exactly the run that needs it.

Output: `scripts/create-or-reuse-release.sh`, its regression harness, and a rewritten
`create-release` job plus a `sha` output on `verify-tag-source`.
</objective>

    Fixture-driven with a stubbed `gh` binary (a shell script on a scratch PATH, selected through
    the `GH_BIN` seam) so no assertion touches the network:
    - Lookup returns HTTP 200 with a body carrying an `upload_url`: exit 0, emits that `upload_url`, and the stub records that no create call was made.
    - Lookup returns HTTP 404, create returns 201 with a body carrying an `upload_url`: exit 0, emits that `upload_url`, and the stub records exactly one create call.
    - Lookup returns HTTP 500: exit non-zero, the message names the status, and the stub records that no create call was made.
    - Lookup returns HTTP 401: exit non-zero, no create call.
    - Lookup returns 404 and create returns 422: the script re-fetches by tag; if that second lookup returns 200 it exits 0 reusing the release, and if it returns 404 it exits non-zero.
    - Lookup returns 200 with a body lacking `upload_url`: exit non-zero (malformed response is a loud failure, not an empty output).
    - `GITHUB_OUTPUT` pointed at a scratch file: after a successful run that file contains both an `upload_url=` line and a `version=` line.
    - A body file containing a line that is exactly `EOF`, and one containing backticks and `$(...)`: the value reaches the API payload literally, and the run still succeeds.
  </behavior>
  <action>
    Create `scripts/create-or-reuse-release.sh` following the same house shape as
    `scripts/check-release-consistency.sh` (header comment documenting the decision table,
    `set -euo pipefail`, flag parsing, a remediation block on failure, and a
    `CREATE_OR_REUSE_RELEASE_LIB_ONLY` guard so the harness can source it).

    Flags: `--tag <vX.Y.Z>` (required), `--repo <owner/name>` (defaults to `$GITHUB_REPOSITORY`),
    `--body-file <path>` (optional; empty body when absent), `--name <title>` (defaults to
    `Release <tag>`), `--prerelease <true|false>` (defaults to true when the tag version contains a
    hyphen, matching the existing `contains(version, '-')` expression the workflow uses today).
    Resolve the `gh` executable through a `GH_BIN` variable defaulting to `gh`, which is the seam the
    harness stubs.

    Decision logic: request the release by tag with the response headers included so the HTTP status
    is readable, and branch on the status explicitly — `200` reuses, `404` creates, and anything else
    is a hard failure naming the status and exiting non-zero. This is the point of the task: an
    exit-code-only check cannot tell a 404 from a transport failure, and the failure mode is that a
    healthy-but-flaky run tries to create a release that already exists and produces exactly the 422
    this phase removes.

    On the create path, build the request payload structurally with `jq -n` from `--arg` values
    (tag name, release name, body read from the body file, draft false, prerelease flag) and feed it
    to the create call on stdin. Do not assemble the payload by interpolating text into a command
    line: the body is commit-subject text and must be treated as data. If the create call returns
    422 — a concurrent run created the release between the lookup and the create — re-fetch by tag
    once and reuse if it now exists, failing loudly if it still does not.

    Extract `upload_url` from the response with `jq -e` so a null or missing field fails rather than
    emitting an empty output. Emit `upload_url=<value>` and `version=<tag>` to stdout, and append the
    same two lines to `$GITHUB_OUTPUT` when that variable is set and non-empty.

    Write `tests/scripts/create-or-reuse-release_test.sh` first, covering every case in
    `<behavior>`, using the `mktemp -d` + `trap cleanup EXIT` fixture lifecycle, `FAILED`/
    `ASSERTIONS` counters, and `assert_fire`/`assert_silent` helpers that pin which message fired.
    The `gh` stub should read a scripted status/body from files in the scratch dir and append a line
    to a call log for each invocation, so assertions can check both the outcome and whether a create
    was attempted.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| git commit subjects → GitHub API request body | Arbitrary contributor-authored text becomes the release body |
| git tag ref / dispatch input → `run:` shell | Attacker-influenceable version string reaches a command line |
| GitHub REST API response → job outputs | `upload_url` flows onward into two other jobs |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-11 | Tampering | Release body construction | high | mitigate | Payload built with `jq -n --arg` and fed on stdin; commit text is never interpolated into a command line, and the `$GITHUB_OUTPUT` heredoc that could be injected by a commit subject of `EOF` is replaced by a file path |
| T-20-12 | Tampering | `create-release` / gate job `run:` steps | high | mitigate | Every tag- and SHA-derived value reaches the shell through `env:` (CR-01); asserted by the acceptance criterion forbidding `${{` inside modified `run:` bodies |
| T-20-13 | Denial of Service | Create-or-reuse branch on a transient API error | high | mitigate | The branch is chosen by explicit HTTP status; a non-200/404 status fails loudly with zero create attempts, so a flaky lookup cannot manufacture the 422 that blocks the publish path |
| T-20-14 | Elevation of Privilege | Gate job token scope | medium | mitigate | The gate job keeps `permissions: contents: read` and receives only `GITHUB_TOKEN`; listing workflow runs requires no broader scope, and no `id-token` is granted outside `publish-crates` |
| T-20-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package installs and no new GitHub Action in this plan (D-01 forbids one); if any appears, stop and run the Package Legitimacy Gate protocol first |
</threat_model>
