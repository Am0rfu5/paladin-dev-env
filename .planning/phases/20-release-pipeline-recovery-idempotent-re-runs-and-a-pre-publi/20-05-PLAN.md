<objective>
Replace the publish loop's two guesses with two reads: a crates.io query decides whether a crate is
already at the tagged version, and a bounded poll of the sparse index decides when it is safe to
publish the next dependent. Then make the job's report honest — each of the eleven crates ends in
exactly one named state, and a run that moved nothing fails.

Purpose: PUBOPS-03's second criterion and PUBOPS-04 in one place. The current loop decides
"already published" by matching crates.io's error wording, which is not an API contract, and waits
a fixed interval between crates, which is the flake that produces the half-published state this
phase exists to recover from. And with every crate already at the version it warns and ends green —
externally indistinguishable from a release that worked.

Output: `scripts/publish-crates.sh` carrying the whole loop (locally inspectable and unit-testable
against stubs), its regression harness, and a `publish-crates` job reduced to a thin invocation.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| crates.io HTTP response → publish decision | A third-party response decides whether a crate is uploaded |
| crates.io index body → readiness of the next publish | A response body gates the next crate in the order |
| OIDC-minted registry token → job environment | A short-lived publish credential lives in the job for the whole loop |
| tag-derived version → `run:` shell | Attacker-influenceable string reaches a command line |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-17 | Tampering | Already-published decision | high | mitigate | Decided by HTTP status against the versioned crate endpoint, not by matching a command's output text; an unhandled status is a per-crate failure rather than an assumption that the crate is unpublished |
| T-20-18 | Tampering | Registry/index response parsing | high | mitigate | Fields extracted with `jq -e` so a malformed or unexpected body fails loudly; the index check never reads an absent field as "not yet visible" indefinitely because the poll is bounded |
| T-20-19 | Information Disclosure | crates.io calls from a job holding a registry token | high | mitigate | No redirect-following option on any call, per `security.instructions.md`; the registry token is never passed as a header on these calls, only to `cargo publish` through its own environment variable |
| T-20-20 | Elevation of Privilege | `crates-io` environment and `id-token: write` scope | high | mitigate | The environment binding and the permission block are preserved byte-for-byte; the OIDC subject claim depends on the environment name, so no step may run the publish outside it |
| T-20-21 | Tampering | Version string reaching the publish shell | high | mitigate | The version arrives through `env:` (CR-01), never interpolated into the `run:` body; the script quotes every expansion and validates its numeric arguments before use |
| T-20-22 | Repudiation | A release that published nothing reporting success | high | mitigate | A real run with zero `published-now` exits non-zero with a self-diagnosing message; the outcome table records the state of every crate so the run's effect is auditable from the log and the step summary |
| T-20-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package installs in this plan; the only registry interaction is publishing this workspace's own crates. If any install appears, stop and run the Package Legitimacy Gate protocol first |
</threat_model>
