<objective>
Build the binaries the release advertises, assert they exist before archiving them, and move the
asset upload path onto maintained tooling.

Purpose: `[[bin]] paladin` declares `required-features = ["cli"]`, `cli` is absent from
`default`, and `build-binaries` runs a bare `cargo build --release --target <triple>`. Cargo
silently skips a binary whose required features are unmet, so the release attaches none of the
three declared binaries and the first thing to notice is a strip step failing on a missing path.
Fixing that also surfaces a second, previously-masked defect: GNU `sha256sum` does not exist on
GitHub's macOS runner images, and the two macOS legs have never reached that line. In the same
pass the three archived-action upload steps and the URL plumbing that exists only to serve them
are removed.

Output: `scripts/package-release-binaries.sh` (assert → strip → archive → portable checksum), its
regression harness, and a `build-binaries`/`sbom` pair that upload through the `gh` CLI.
</objective>

Create `scripts/package-release-binaries.sh` with the house header shape: purpose comment naming
ARTIFACT-02/ARTIFACT-05, an explicit `Usage`/`Output`/`Exit` contract block, `set -euo pipefail`,
and a `PACKAGE_RELEASE_BINARIES_LIB_ONLY=1` sourcing seam exposing
`package_release_binaries_main`.

Contract: `--target <triple>` (required), `--release-dir <path>` (required — the
`target/<triple>/release` directory), `--archive-name <name>` (required — e.g.
`paladin-linux-amd64`), `--strip-cmd <cmd>` (optional, default `strip`). An unrecognised flag is a
usage error.

The script owns the per-target expected-binary manifest as data: a single function
`expected_binaries_for_target` returning `paladin paladin-cli paladin-server` for every currently
shipped triple, with a comment stating that narrowing a target's set is an edit to this one
function and must be accompanied by a recorded reason (RESEARCH open question 2 — the aarch64
`cross` leg is unproven until the rehearsal runs). An empty list for a known target is a hard,
named failure, not a silent no-op.

Behaviour in order: (1) resolve the expected list for `--target`, failing loudly on an unknown
triple; (2) for each expected name, test for a regular file at `<release-dir>/<name>` by exact
byte-string name — accumulate every missing name, then, if any are missing, emit
`::error::expected binaries not built for <target>: <names>` and exit 1 before creating anything;
(3) run `<strip-cmd>` on each present binary; (4) `tar czf <archive-name>.tar.gz` from inside
`--release-dir`, passing the expected names in manifest order so member order is deterministic;
(5) write `<archive-name>.tar.gz.sha256` using a `sha256_cmd()` helper that runs `sha256sum` when
`command -v sha256sum` succeeds and `shasum -a 256` otherwise. Print the archive and checksum paths
to stdout and append them to `$GITHUB_OUTPUT` as `archive_path=` / `checksum_path=` when that
variable is set and non-empty.

Create `tests/scripts/package-release-binaries_test.sh` with the harness conventions from
`create-or-reuse-release_test.sh`. In this task cover the four `<behavior>` rows: a happy-path
scratch dir of three fake executables (assert `tar tzf` lists exactly the three names in manifest
order and the `.sha256` file is non-empty and names the archive), the missing-binary failure
(assert exit 1, the `::error::` substring naming the absent binary, and that no `.tar.gz` was
created), and the portability branch (prepend a scratch `PATH` directory that shadows `sha256sum`
with a non-executable stub or runs the script under a `PATH` from which `sha256sum` is absent, and
assert the digest still matches the one `shasum -a 256` produces). Use a `--strip-cmd` pointing at
a no-op stub in the scratch dir so the test does not require a real object file.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| matrix values / tag ref → `run:` body | Target triple, archive name and version reach shell steps in `contents: write` jobs |
| build output → published release asset | A file produced on a runner becomes a consumer-downloadable artifact |
| runner → api.github.com / uploads.github.com | Credential-bearing (`GITHUB_TOKEN`) upload from a `contents: write` job |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-21-05 | Tampering | `Package release binaries` step | high | mitigate | Target, archive name and strip command reach the script through `env:` (CR-01) and are quoted in every expansion; the script never `eval`s or word-splits an operator-derived value |
| T-21-06 | Spoofing | published binary archives | medium | mitigate | Per-asset `.sha256` files are produced on the same runner that built the archive, from the archive bytes, with a command that exists on that OS — the macOS legs stop silently having no checksum path at all |
| T-21-07 | Elevation of Privilege | `build-binaries` / `sbom` holding `contents: write` | high | mitigate | No new Action is added; the only third-party ref in a write-permission job (`dtolnay/rust-toolchain`) stays SHA-pinned (WR-02); uploads run on the runner-preinstalled first-party `gh` CLI authenticated by the job's own scoped `GITHUB_TOKEN` |
| T-21-08 | Repudiation | a leg producing no artifact and ending green | high | mitigate | The existence assert fails the leg with a named error before any archive is created; `fail-fast: false` means one bad leg no longer hides behind a sibling's success |
| T-21-09 | Information Disclosure | `gh release upload` following a redirect with a credential header | medium | mitigate | `-L`/`--location` is not passed anywhere; the `gh` CLI handles the upload-host hop itself with its own credential scoping, and no hand-rolled `curl` upload is introduced |
| T-21-SC | Tampering | package installs | low | accept | RESEARCH.md's Package Legitimacy Audit records **no new packages and no new Actions**; the only install steps are pre-existing (`cargo install cross --locked --version 0.2.5`, `binutils-aarch64-linux-gnu` from the runner's distro repo), unchanged in version by this plan |
</threat_model>
